## 3. Sonnet 실행 방식

사용자의 Sonnet 설정을 유지한다. 정확한 모델 버전은 실행 환경에서 확인해 보고하고 추정하지 않는다.
개발용 Claude 모델은 앱 내부 OpenAI 모델·키·예산과 별개다.

**사용자 자원 배분 지시:** Codex의 계획·검증 사용량을 최소화하고 필요한 상세 작업은 Sonnet에 최대한 맡긴다.
Sonnet은 위임 범위의 코드 조사·세부 실행계획·구현·디버깅·전체 회귀·증거/보고서 정리를 자율적으로 끝낸다.
Codex는 목적·범위·수용 조건을 정하고 최종 판정한다. 하위 단위마다 재보고·확인을 요구하지 않는다.
Sonnet은 최종 요약 20줄/2,000자 이내와 커밋·검사·증거 색인을 제출하고 긴 로그·분석은 별도 파일에 둔다.
Codex는 요약→범위 이탈/실패→위험 diff 순으로 읽고 필요할 때만 원문·로그를 추가로 읽는다.
같은 전체 회귀를 자동으로 반복하지 않으며 저장/복원·revision·격리·보안 변경 등 실제 위험에 필요한 독립 검사를 고른다.
이는 사용자 선호를 기록한 것이며 구독별 실제 사용 한도 비교를 검증한 것은 아니다.

- 지시서마다 읽을 파일·변경 범위·수용 조건·제외 범위·검사·중단 조건·제출 형식을 적는다.
- 큰 과제는 최대 세 하위 단위로 나눠 Sonnet이 순차 자율 처리하고 결과를 한 번에 제출한다. 사용자 동작·의미·보존을 검사한다.
- 새 근거 없이 같은 수정을 반복하거나 기대값·검증 강도를 낮추지 않는다.
- 서로 다른 수정 시도 두 번에도 원인이 불명확하거나 저장 계약 변경이 필요하면 재현·가설·영향을 제출한다.
- Codex가 범위·설계를 보완한다. 필요하면 Opus 분석을 제안하지만 임의로 모델을 변경하지 않는다.
- Haiku는 단순 목록/요약 보조, Fable은 긴 복합 문제의 후속 후보다. T-01은 Sonnet으로 시작한다.

이 분류는 프로젝트 운영 제안이며 모델별 실제 성공률·비용 측정 결과가 아니다.

산출물은 [P-08 판정](p08-report.md), M/R 증거표, [iPhone 절차](phase-2-prime-runbook.md)의 응답 기록이다.
필수 미처리·설명 없는 손실·핵심 사용/데이터 훼손 결함을 해소하고 제약을 제시한 뒤 사용자가 G2/G2′를 판정한다.
복원 1회 성공·알려진 결함 0건·자동 검사 통과만으로 이행 완료를 선언하지 않는다.

## 6. 단계 C · 별도 여행의 작성·현장 기록·회고

10/29 우선순위 변경으로 B 잔여를 [후속 목록](change-log.md)에서 추적하며 C의 작성 흐름을 먼저 완성한다. 첫 작업은 [C-01](claude-task-c01-authoring.md)이다. 대상은 가상 검토 시나리오를 우선 사용하고 실제 자료는 별도 확인한다.
시뮬레이션을 실제 방문으로 기록하지 않으며 수 주의 실제 여행을 필수 검사 기간으로 요구하지 않는다.

- C-1: 필요한 기능 범위에서 ContentApp/저장소 책임을 별도 구조 커밋으로 분리한다. 전체 파일 분해를 필수 선행으로 두지 않는다.
  v1은 이미 별도 경로로 유지 중이다. 삭제·자동 변환·기존 접근 경로 제거는 별도 범위다.
- C-2: 새 장소/가이드의 최소 수동 작성·일정 연결·수정·재조회·백업/복원을 먼저 구체화한다.
  이는 G-08의 최소 흐름이다. 편집 형식·화면은 검토안으로 제시한다.
- C-3: 다른 여행을 앱에서 생성해 준비→조회→계획 변경/현장 기록→정정→회고→빈 공간 복원까지 수행한다.
  양 여행의 본문·계획·기록·출처·첨부 격리를 확인한다. 새 가이드 작성 완료는 C-2 뒤에 판정한다.
- C-4: 실제 타임라인·정정·당시 맥락에서 현재/과거 계획·변경 이유를 이어 읽게 한다.
  한 화면 비교는 UI 후보이며 확정 요구가 아니다. 첫 화면의 기술 문구도 사용 증거에 따라 조정한다.

F-03의 이름·날짜·지역 탐색과 아직 미확정인 전체 본문 검색을 구분한다.
지도 목록·외부 링크 우선과 초기 자동 동기화 제외를 유지한다. F-14의 PAT 방식을 자동 복구하지 않는다.
F-17의 실제 기록/이력은 기본 요구이고 고급 비교 화면 범위만 후속 정의한다.
G-01·02·08 증거를 갱신하되 실제 AI가 필요한 S-01/04는 단계 D까지 미완료로 남긴다.

## 7. 단계 D · 실제 v2 AI 운영·사용 검증 (기존 Phase 3)

2026-10-30 상세 [D 설계서](phase-d-design.md)·[D 개발계획](phase-d-plan.md)을 작성했다. 현재 코드/모의 증거와 모바일 접근·인증·금액 예산·전송 최소화의 공백을 구분한 제안이다. 문서 검토 준비이며 구현·키 변경·외부 접속·유료 호출/배포 승인이 아니다. C-06 작업과 제품 코드를 동시에 수정하지 않는다.
같은 날 사용자 지시로 [Triple·Wanderlog 벤치마킹](design/여행계획앱%20벤치마킹%20Triple%20vs%20Wanderlog.md)을 두 문서에 반영했다(설계서 §11, 계획 §7, 결정 U-D5 추가). D 범위 밖 항목(시드 일정 템플릿·지도+리스트 화면·공유 링크·PDF 내보내기)은 설계서 §11.3에 전달 목록으로 두었고 C/E 계획 갱신 시 반영한다.

운영안 작성은 A부터 가능하다. 실제 실행은 이행 마감과 필요한 사용자 결정 뒤 진행한다.
PC 한정 실험은 중간 기술 검증이다. 모바일 우선·여행 중 재계획 목표의 축소로 자동 해석하지 않는다.
필요한 것은 휴대폰에서 인증해 접근할 실행 경로이며 공개 서버를 유일한 해법으로 미리 정하지 않는다.

필수 결정: 실행 위치/기기 접근, 인증/접근 제한, 키/작업 결과 보관, OpenAI 모델·비용 한도·중복 과금 보호,
일정·예약 요약·현장 기록 전송 범위와 명시적 실행 동의. 기존 v2는 기본 비활성을 유지한다.

실제 조사→근거/초안 자동 저장→승인 전 계획 유지→확인/거절→저장·재조회를 검증한다.
실패·중단·실제 서버 재시작·결과 재회수·중복·stale·저장 실패도 확인한다.
유료 오류를 재현하려고 무제한 호출하지 않고 모의 실패와 실제 서버/연결 검사를 구분한다.
실제 호출 1회·v1 성공·모의 응답만으로 G3를 닫지 않는다. 해당 기기 환경에서 사용자 확인을 받는다.

## 9. 전달·검증·Git

지시서에는 ID·기준 커밋·의존 작업·변경 범위·수용 조건·제외·검사·중단 조건을 적는다.
결과에는 커밋별 파일·명령/exit code/로그·직접 볼 산출물/확인 동작·실패/미검증/대기·다음 제안을 구분한다.
실제 자료·키·백업은 공개 보고서/픽스처에 넣지 않는다. 새 작업은 Codex 검토 뒤 지시서를 발행한다.
T-01 작성은 이후 작업 전체의 구현 지시를 대신하지 않는다.

- pnpm12.14.0·Node24.13.1·프로젝트 `.venv`, 캐시 `.cache/corepack`·`.cache/ms-playwright` 사용.
- 의미 있는 변경은 `pnpm run check`, UI/저장 흐름은 빌드와 `pnpm run test:e2e`, 이행은 `check:pilot` 포함.
- 최종 일괄 검사는 `pnpm run check:deferred`. 기존 preview는 4173 소유 확인 뒤에만 재사용한다.
- 사용자 변경·미추적 검토 문서를 보존한다. worktree·강제 push·실제 자료 공개·키 변경은 실행하지 않는다.
- 단위별 커밋/push 원칙을 유지한다. Pages 유발 변경은 별도 검토 경로를 먼저 정한다.
- Codex는 제출 커밋과 diff를 고정해 필요한 검사를 직접 실행한다. Claude의 성공 문구만으로 판정하지 않는다.
- handoff는 50줄·2,500자 이내로 교체하고 이전 현재 요약은 history에 보존한다.
