# travel-app 개발 실행계획

2026-10-23 · G0·G1·Phase 2 B-01 사용자 확인 완료

현재 실행 순서는 이 문서 한 곳에서 관리한다. [전체 점검](status-review-2026-10-22.md) §7·§8의 결정과 이번 세 요구를 반영했다. [이전 계획](history/development-plan-2026-10.md)은 이력이다. 기존 P-01~P-08, R/M/G 식별자는 유지한다.

## 출발점과 실행 원칙

- P-01~P-06은 가상 데이터로 구현·검증했다. Phase 1의 실제 3일 검증 뒤 사용자 ‘백업 메뉴가 없다’ 수정 요청과 SP-FR UI/UX 보존 결정을 반영해 상단 백업·5개 탐색·읽기 흐름을 보완했다. **G1은 2026-10-23 사용자 ‘확인 완료’로 종료**이며 P-08은 잠정 판정이다.
- 실제 31입력 파일에서 콘텐츠 245개, 미디어 46파일+대응표 1파일을 만들었다. `packageReady=true`다. 표본 밖 필드는 다음 배치 보류로 추적하며 전체 여행 이행 완료는 아니다. [실행 보고](phase-1-report.md).
- PC 웹 실제 데이터 검증을 먼저 한다. iPhone Chrome은 Phase 2′에서 검증하고 Phase 1 종료 때 앞당길 필요를 재판단한다. 모바일 우선 요구는 유지한다.
- v2 이행 후 AI를 재구현한다. v1은 격리·유지하고 확장하지 않는다. 이미지의 사용자 기준은 **앱 화면에서 조회·점검**이며 작성자는 OPFS 파일+DB 참조를 선택·검증했다. 사용자가 기술 제품을 선택한 것으로 기록하지 않는다. [재점검](media-storage-review.md).
- G0 확인 뒤 Phase 1을 실행했고 실제 원천의 격리 DB 반영과 PC 검사를 마쳤다. 평소 사용자 DB를 초기화하지 않았다. G1 확인과 단위별 GitHub push를 완료했다. 전체 확대·앱 배포는 아직이다. 고정 주수 대신 실제 결과로 후속 작업량을 산정한다.

## 단계 완료와 다음 단계 진입

**자동 검증 통과 + 직접 확인할 실제 산출물 + 그 산출물에 대한 사용자 확인**을 모두 만족해야 완료다. 보고서 작성·테스트 통과·무응답으로 다음 단계를 시작하지 않는다. 실제 코드를 읽거나 앱을 조작할 경로를 제공한다.

각 보고서는 범위·기술 판단/이유·산출물 위치/버전·확인할 동작·검사 결과·남은 제약·사용자 확인 상태를 담는다. 상태는 `검토 준비 / 확인 대기 / 수정 요청 / 확인 완료`다. 실제 사용자 응답과 날짜만 확인 기록으로 남긴다. 수정 요청이면 같은 단계에서 수정·재검증·재제시한다. 개발 산출물 확인은 앱 안의 여행 변경안 적용 승인을 대신하지 않는다.

|---|---|---|
| 0 안정화 | 대표 소스 전후 비교와 포맷된 실제 파일 읽기, 가상 화면 조작 | G0: 가독성 확인 후에만 Phase 1 위임·진입 |

## Phase 0 · 복구 기준점과 코드 가독성 (I-1~I-7)

목표는 사람이 검토하고 수정할 수 있는 출발점을 만드는 것이다. 지침·문서 정리는 선반영했으며 이번 사용자 지시로 코드·Git 작업에 착수한다. 실제 완료 결과는 단계 보고서에 기록한다.

1. **기준점(I-1/I-1b).** Git, 포트/프로세스, pnpm 버전, 로컬 원천·데이터를 확인한다. 비밀값·실제 여행 자료·캐시 제외를 검증하고 첫 로컬 기준 커밋을 만든다. 사용자 후속 답변에 따라 `travel-app/backup/`에 Git 제외 로컬 복구 사본을 만들고 검증한다. 같은 디스크의 사본은 디스크 장애 대비 별도 매체 백업과 구분한다.
2. **문서(I-3).** handoff는 현재 상태 1쪽으로 유지하고 과거 기록은 history에 보존한다. 상세는 단계 보고서에 둔다. 이번 선반영분의 분량·링크·이력 보존을 확인한다.
3. **포맷(I-4/I-7).** Prettier 버전·설정·명령을 pnpm으로 고정하고 `printWidth: 120`을 적용한다. 생성물·캐시·실제 데이터는 제외한다. 우선 `src/content/ContentApp.tsx`, `src/storage/content-repository.ts`, `src/transfer/spfr-candidate.ts`의 대표 구간 전후를 제시하고 관리 소스 전체에 일관되게 적용한다. 사람이 함수·분기·JSX를 읽을 수 있는지 확인한다. 포맷만으로 해결되지 않는 책임 분리는 별도 개선 목록에 둔다.
4. **재발 방지(I-7).** 포맷 검사를 로컬 검사·CI에 연결하고 ESLint의 한 줄 다중 문장 등 가독성 검사를 추가한다. 불가피한 긴 URL·문자열 등은 예외로 기록한다. Prettier, ESLint 자동 수정은 별도 변경·커밋으로 분리한다. 구조 리팩터링은 Phase 1 이후 별도 범위로 둔다. 설정 전에는 재발 방지 검사가 동작한다고 하지 않는다.
5. **검증(I-5).** Windows에서 `pnpm run check`, `pnpm run test:e2e`, `pnpm run check:pilot` 및 새 포맷/린트 검사를 실행한다. 포맷과 린트 수정 각각의 변경 후 검사해 원인을 분리한다. 기능 변경은 포맷에 섞지 않는다.
6. **공개·키(I-2/I-6).** 공개 저장소 유지 결정을 따른다. push는 별도 실행 범위로 관리하고 수행 전 공개 대상의 개인 맥락·비밀값·원문 제외를 점검한다. 원격 CI는 실제 실행한 경우에만 완료로 기록한다. 첫 실패 키 폐기는 생성일로 구분해 사용자가 수행할 항목으로 남긴다.

**G0 산출물:** 읽을 수 있는 소스 3개와 전후 비교, 포맷/린트 설정·검사 결과, 가상 화면 조작 경로, 1쪽 handoff, 기준 커밋/별도 백업 상태. 실행 시 `docs/phase-0-report.md`를 만든다. **사용자가 포맷 결과를 확인하기 전에는 G0를 통과시키거나 Phase 1에 맡겨진 것으로 간주하지 않는다.** 미완료 외부 항목은 차단 여부와 사유를 구분한다.

## Phase 1 · 실제 3일 DB 반영과 PC 웹 확인 (P-07 실제 표본)

**결과(구현·검증·사용자 확인 완료):** 사용자 확정인 ‘가능한 SP-FR-guidebook UI/UX 경험 보존’을 반영한다. 원본의 오늘·전체 일정·가이드·지도·준비, 날짜 이동, 다음 일정/당일 예약/시간표, 읽기 폭·색·서체, 장소에서 일정 복귀를 3일 표본에 적용한다. 원천 점검은 보조 영역으로 모으고 DB·저장/복원 계약은 유지한다. [대조·결과](phase-1-uiux.md)를 기록하고 사용자에게 화면을 다시 제시한 뒤 G1을 판정한다. 진행 요청과 별개로 2026-10-23의 사용자 ‘확인 완료’ 응답을 받아 G1을 닫았다.

1. 고정 원천의 34개 조사 파일/31개 표본 입력과 해시·manifest를 다시 확인한다. 원천은 읽기 전용으로 보존한다.
2. XLSX 12시트 열·행 의미, 지역/언어/현장 상태, 원천 leaf 필드 전체를 DB 필드·본문·관계에 대응한다. 누락·변환·보류를 원천 locator로 추적한다.
3. 미디어 46파일을 독립 이미지/해상도로 구분한다. U-03의 앱 화면 점검 기준에 맞춰 선택한 OPFS와 DB 참조에 해시·원천·권리를 보존한다. 필수 오프라인 첨부를 외부 링크나 빈 파일로 대체하지 않는다. 미확보는 차단·검토 사유로 남긴다.
4. Notre-Dame Fact 근거 누락은 원천 재조사와 불확실성 처리로 해결한다. 근거·확인 시각을 발명하지 않는다. 범위 제외가 필요하면 사용자 결정 항목으로 제시한다.
5. 5개 차단 해소와 `packageReady=true`를 확인해 ZIP 생성·재검증 후 별도 검증용 DB에 가져온다. 스키마 통과와 DB/화면 사용 성공을 구분한다.
6. PC 공통 화면에서 원천과 표시·의미를 대조한다. 일정·날짜 경계·긴 본문·Fact·예약·이동·사진/지도·언어/상태를 포함한다. 본문 편집, 현장 기록, 재시작, 백업 파일 보관/재선택·빈 검증 저장소 복원을 확인한다. 기존 작업 DB를 초기화하지 않는다.
7. **사용자가 PC 브라우저에서 표본을 직접 확인한다.** 실행 중인 정확한 로컬 URL, 선택할 여행/날짜, 해볼 동작과 원천 대비 차이를 제시한다. 원문·예약·화면 증거는 Git 제외 경로에 보관한다. 보고서만 전달하고 넘어가지 않는다.

**검증:** `check`(타입·빌드 포함), `test:e2e`, `check:pilot`, 실제 필드/수량/참조/해시/복원 대조. 회귀 픽스처에는 실제 여행 원문을 커밋하지 않는다.

**G1 산출물:** 실행되는 PC 3일 표본 화면, 로컬 ZIP, 원천→DB→화면 대조표, [P-07 보고](p07-report.md)의 최신 판정, 43일 지역별 작업 분해표. 사용자 확인 후 G1을 닫고 실기기 1차를 Phase 2 전에 앞당길 필요를 재판단한다. PC 통과를 P-07 실기기 통과로 기록하지 않는다.

## Phase 2 · 전체 SP-FR 이행 (지역별 반복)

2026-10-23 사용자 ‘계속 진행’으로 착수했다. 첫 B-01은 Barcelona Day 1~3이며 [지역별 실행 보고](phase-2-report.md)에서 수량·기술 판단·산출물·검증·배치별 사용자 확인을 관리한다.

B-01의 실제 변환·검증을 통과하고 [사용자 확인 안내](phase-2-b01-review.md)의 별도 Chromium 창을 제시했다. 33입력·3일/17활동/14이동·장소/주제22개·콘텐츠383개·52파일이다. 123개 단위/38개 E2E, 실제 전체 행/해시·오프라인 복원·기존 G1 호환을 확인했다. **2026-10-23 사용자 ‘확인 완료’로 B-01 확인을 닫았다.** 다음은 기존 지역별 작업표의 B-02 Girona Day 4~6이며 아직 착수 전이다. 다음 배치도 실제 화면을 제시하고 별도 확인을 받는다.

G1은 2026-10-23 사용자 ‘확인 완료’로 종료됐다. 기술 재판단으로 iPhone 1차를 앞당기는 안을 권장하되, 기존 PC 우선 결정을 유지한다. U-04 미결정은 원천 조사·배치 준비의 차단 조건이 아니며 실제 기기 접속·파일 전달 전에 해소한다. 이번 G1 기록 갱신에서는 지역별 실행을 새로 완료했다고 기록하지 않는다.

1. 조사 기준 43일·9지역·166장소를 고정 원천으로 재산정한다. 배치별 입력 수량·본문/예약/상태·첨부 수/용량·권리 상태를 기록한다. 기존 조사 수치를 보존 대조 없이 확정 총량으로 쓰지 않는다.
2. 배치마다 `추출 → 필드 대응 → 후보/ZIP → 검증 DB → 원천 대조 → 사용자 화면 확인`을 반복한다. 확인한 배치만 승인된 적용 범위로 반영하고 다음 지역으로 간다. 미해결 항목을 묵시적 제외로 만들지 않는다.
3. 실제 원천 변경을 검증 사본으로 만들어 B/L/R 재가져오기를 검사한다. 앱 편집·실제 기록·보류 항목을 보존하며 원본 SP-FR은 변경하지 않는다.
4. 다른 여행 추가·전환·본문 수정·재시작을 프로그램 코드 수정 없이 확인한다. 전체 첨부 용량과 백업/빈 검증 저장소 복원을 측정한다. v1은 격리하며 제거를 이행 완료 필수 조건으로 삼지 않는다.
5. 지역별 선택 추출과 별도로 원천 코드 안의 공통 준비/비상·화면 문구 및 남은 참조를 전수 대조한다. AST 허용 상수의 미대응0을 원천 코드의 모든 콘텐츠 이행 완료로 확대하지 않는다. 전체 통합 패키지와 G2 판정 전에 잔여 항목을 해소하거나 사용자 결정으로 명시한다.

**G2 산출물:** 지역별 실제 앱 화면과 전체 여행 화면, 수량·필드·첨부 대조 및 복원 자료, [이행 판정](p08-report.md). M-01~M-11과 R-01~R-09를 증거로 갱신한다. M-05의 휴대폰 사용 부분과 M-06·M-10, R-07~R-09의 실기기 부분은 미검증으로 남긴다. 사용자 전체 PC 이행 확인 후 Phase 2′로 간다. 최종 ‘이행 완료’는 아직 아니다.

## Phase 2′ · iPhone Chrome과 이행 완료 판정

1. 접근 경로(로컬 HTTPS·허용한 터널·정적 앱 셸 제공 등)를 결정한다. 공개 저장소 유지와 앱 공개 배포를 같은 승인으로 취급하지 않는다. 여행 파일 전달 범위도 구분한다.
2. 모델·iOS·Chrome·앱 버전·origin을 기록한다. 실제 기기에서 사전 준비 → 통신 차단 → 일정/본문/이미지 조회 → 현장 입력 → 종료·재실행을 수행한다.
3. 백업 ZIP을 파일 앱에 보관·재선택하고 빈 검증 저장소에 복원한다. 기존 사용 데이터를 삭제하지 않는다. 첨부 포함 용량·메모리·파일 한도, 취소/중단·공간 부족을 실측하거나 미검증으로 남긴다.

**G2′ 산출물:** 사용자가 직접 조작하는 iPhone 앱, 실제 백업/복원 결과, 기기별 증거·제약. M-05/06/10 등 잔여 휴대폰 조건과 R-07~R-09를 판정하고 사용자가 ‘이행 완료’를 확인한다. 모바일 viewport로 대체하지 않으며 필수 조건이 남으면 완료를 유보한다.

## Phase 3 · v2 AI 재구현 (이행 완료 후)

서버 위치·인증·모델·예산·전송 범위를 구체화한 뒤 v2 콘텐츠/계획/실제 기록에서 조사·변경안을 생성한다. 유료 호출은 승인된 범위에서만 한다. 사용자가 앱에서 변경안을 읽고 승인/거절하며 적용 후 재조회한다. 실패·중단·중복·오래된 revision 거부도 보여준다.

**G3 산출물:** 실제 API가 연결된 앱의 전체 흐름, 비용·전송 범위·실패 복구 기록. `check`·빌드·E2E와 실제 API 검증을 구분하고 사용자가 확인한다. 모의 응답·JSON 교환·v1 성공은 v2 AI 완료 증거가 아니다. 새 가이드 작성은 G-08 범위를 구체화해 같은 방식으로 확인한다.

## Phase 4 · 운영과 선택 확장

호스팅 정식화·운영 복구·새 가이드·사진/지출·내장 지도 조작 중 합의한 범위만 기능별로 계획한다. 이미 이행에 포함된 기존 이미지 보존·본문 편집을 선택 확장으로 미루지 않는다.

**G4 산출물:** 선택 기능이 동작하는 앱과 사용자가 따라 해본 복구/운영 자료. 기능별 검사와 직접 사용 확인 후 완료한다. 일정·비용·배포 범위는 해당 작업을 정의할 때 산정한다.

## 사용자 결정·실행 대기 항목

답할 항목은 이 절에서 모아 관리한다. 사용자 선택과 작성자의 기술 판단을 구분한다. 이미지의 앱 화면 조회·점검 답변은 반영했고 OPFS를 구현했다. 2026-10-23 G1에서 실제 표시 확인을 완료했다.
