## 1. 지금 상태 (사실 — 코드 확인)

| 자료 | 있는 곳 | 한계 |
|---|---|---|
| 준비 초안 1건(답·가이드 원문·고른 것) | 이 기기 브라우저 설정(`localStorage`, 키 `travel-app.prep-draft.v1`) | 백업 ZIP에 없다. 다른 기기로 가지 않는다. 사이트 데이터를 지우면 사라진다 |
| 지난번 답(취향 8칸) | 같은 곳(키 `travel-app.last-answers.v1`) | 같음 |

- 여행 DB의 표 20개 가운데 자료를 담는 16개는 모두 "여행 하나"에 딸린 구조다(`spaceId+tripId`). 나머지 4개는 공간 정보와 백업·가져오기 작업 관리용이다. 여행에 속하지 않는 자료를 둘 자리가 없다.
- 전체 백업에 담는 표는 15개로 고정돼 있고(`exchangeCollections`), 표를 늘리면 저장 계약·백업 검증·복원·이행 검사를 함께 바꿔야 한다.
- 전체 백업 복원은 **빈 공간에서만** 된다([운영 설명서](phase-4-operations.md) C). 그래서 준비 자료를 백업에 넣어도, 여행이 이미 있는 다른 기기의 평소 공간으로는 들어가지 않는다.
- 기기 사이를 자동으로 맞추는 기능(동기화)은 앱에 없다. 계획 글도 사용자가 복사·파일로 옮긴다.

## 4. 추천 (Codex 제안 — 사용자 합의 아님)

**두 단계로 나눈다. 지금은 1단계(안 1)만 한다.**

- 이유 ①: 요청의 핵심이 "기기 간"이라면 안 2만으로는 풀리지 않는다(복원이 빈 공간 전용). 안 1은 풀린다.
- 이유 ②: 안 1은 데이터 경계를 건드리지 않아 실제 여행 자료에 위험이 없다. 안 2는 백업 형식을 바꾸므로 실사용 점검·단계 E(복구 훈련) 전에 하기에는 위험이 크다.
- 이유 ③: 안 1에서 만든 "글 ↔ 준비 자료" 변환은 나중에 안 2를 해도 그대로 쓴다.
- 알림: 계획서의 P2 이름은 "DB 저장"이었다. 이 추천은 1단계에서 DB 저장을 **하지 않는다**. b(지워져도 잃지 않기)는 사용자가 파일을 보관할 때만 풀린다.

### 1단계 P2-1 — 준비 자료 내보내기·가져오기

- 위치: "AI로 계획 만들기" 화면. 단추 2개 — **준비 자료 내보내기**(복사 · 파일 저장), **준비 자료 가져오기**(붙여넣기 · 파일 선택).
- 담는 것: 조건·취향 답, 가이드 원문, 고른 것, 지난번 답. 양식 이름 `travel-app-prep/1`. 사람이 읽을 수 있는 글(표)로 만들고, 메모 앱이 따옴표·줄바꿈을 바꿔도 읽히게 한다(세부는 지시서에서 정함).
- 가져오기: 미리보기(답 몇 칸, 가이드 목적지·항목 수, 고른 것 수)를 보여 주고 승인하면 반영. **이 기기에 초안이 이미 있으면 덮어쓰기 전에 확인**한다. 양식이 다르거나 깨진 글은 거절하고 기존 초안을 그대로 둔다. 계획 글·가이드 글을 잘못 넣으면 맞는 화면을 안내한다.
- 옮기는 일은 사용자가 한다(메일·메신저·iCloud 등). 자동 동기화는 없다.
- 안내 문구: 파일에는 예산·동행 같은 답이 그대로 들어간다는 것을 내보내기 옆에 적는다.
- 데이터 경계(`src/contracts`·`src/storage`·`src/transfer`·`src/repository.ts`)·Worker 변경 0건.

## 10. 2단계 P2-2 — DB 저장 (v0.3, 2026-11-27 · Codex 작성, 사용자 승인 11/27 13:33)

사용자 지시(11/27 10:51): "P2-2를 지금 진행". 풀려는 문제는 **목적지별 보관함 · 여행에 기록 남기기 · 지워져도 잃지 않기**(§2의 c 확장·d·b). 기기 간 이어하기(a)는 고르지 않았다 — P2-1 파일이 그 역할을 그대로 한다. 순서: "바로 설계 시작"(백업 먼저를 고르지 않음).

### 10.1 무엇을 저장하나

| 이름 | 단위 | 한 건에 담는 것 | 언제 생기나 |
|---|---|---|---|
| **보관함**(`prep_library`, 새 표) | 공간(여행에 속하지 않음). 키 `[spaceId+entryId]`, 색인 `[spaceId+destination]` | 이름, 목적지, 가이드 원문, 고른 것, 취향 답 8칸, 저장 시각, 판 번호. 여행지·날짜 같은 여행별 답은 넣지 않는다(P2-1과 같은 규칙) | 사용자가 "보관함에 저장"을 누를 때 |
| **여행의 준비 기록**(`trip_prep_records`, 새 표) | 여행. 키 `[spaceId+tripId+recordId]` | 그 여행을 만들 때의 준비 초안 전체(여행지·날짜를 포함한 답, 가이드 원문, 고른 것) | "AI 결과 붙여넣기 → 새 여행" 저장과 **같은 트랜잭션**에서 1건. 이후 바꾸지 않는다(읽기 전용) |

- 준비 초안(이 기기 `localStorage` 1건)과 지난번 답은 지금처럼 남긴다. 보관함은 사용자가 고를 때만 저장한다(자동 저장 없음).
- 이미 있는 여행에는 준비 기록이 없다(그때의 초안이 남아 있지 않다).

### 10.2 화면 (Codex 제안)

- 가이드 구역: **보관함에 저장**(이름 기본값 `<목적지> <날짜>`), **보관함에서 불러오기**(목록: 이름·목적지·저장일·항목 수·고른 것 수 → 미리보기 → 반영. 덮어쓰기 확인은 P2-1과 같다).
- 보관함 목록에서 이름 바꾸기, 삭제(확인 뒤), 파일로 저장(P2-1 양식 `travel-app-prep/1` 그대로 — 다른 기기로 옮길 때).
- 여행의 더보기 → **이 여행의 준비 자료**: 보기, "보관함으로 복사", "준비 초안으로 불러오기".

### 10.3 저장과 백업

| 항목 | 설계 |
|---|---|
| DB | Dexie 판 2 → **3**. 표 2개 추가만, 기존 자료 변환 없음. 배포되면 평소 공간이 판 3으로 열리고 **되돌릴 수 없다**(이전 앱은 판 3 DB를 열지 못한다) |
| 저장 경로 | `src/repository.ts` 트랜잭션을 거친다. 보관함 덮어쓰기·이름 바꾸기·삭제는 판 번호를 비교해 오래된 판을 덮어쓰지 않는다. 준비 기록은 `ImportNewTrip` 명령 입력에 선택 칸으로 더한다 |
| 전체 백업 | 두 표 모두 포함. 준비 기록은 `tripId`가 있어 기존 방식(`exchangeCollections`)에 더한다. 보관함은 여행에 속하지 않아 **백업 형식을 바꾼다**: 매니페스트 `version 3` + `records/prep_library.ndjson`. 새 앱은 판 2·3 백업을 모두 읽는다. 이전 앱은 판 3 백업을 읽지 못한다 |
| 복원 | 빈 공간 전용 그대로. 그래서 "지워져도 잃지 않기"는 **브라우저 자료가 지워진 뒤 빈 공간에 전체 복원**할 때 풀린다. 여행이 있는 공간에 보관함만 더하려면 P2-1 파일을 쓴다 |
| 여행 1건 보내기·이행 패키지 | 준비 기록은 포함, 보관함은 포함하지 않음 |

### 10.4 영향과 위험

- 데이터 경계 4곳(`src/contracts`·`src/storage`·`src/transfer`·`src/repository.ts`)을 **모두** 바꾼다 — 지금까지 AI 개편에서 0건이던 경계다. 백업 검증·복원·이행 검사·DB 판 올림 시험이 필요하다.
- 실제 여행 자료 백업은 같은 PC의 사본뿐이다(11/24 알림). DB 판 올림은 되돌릴 수 없으므로 **main 병합·배포 전에** 현재 형식 전체 백업을 다른 매체에 두는 것을 병합 조건으로 제안한다([단계 E](stage-e-plan.md) E-1의 1~2단계). 설계·구현은 지금 진행한다.
- 이 배포가 단계 E의 E-2(업데이트 뒤 보존) 확인 기회가 된다.
