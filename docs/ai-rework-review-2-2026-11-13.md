```text
Q2. ID가 있는 행의 빈 칸을 삭제로 해석해도 되는가?

판정: 변경 권고.

현재 방식은 사용자가 의도하지 않은 데이터 삭제를 유발할 가능성이 높다.

예를 들어 기존 일정이 다음과 같다고 가정한다.

ID	제목	메모	예약	링크
A01	저녁 식사	창가 좌석 요청	예약 완료	기존 URL

챗봇에게 메모만 수정하도록 요청했는데 다음 행을 반환할 수 있다.

| A01 | 18:00-19:00 | 저녁 식사 | 식사 | 식당 A | 19시 방문 예정 | | |

현재 규칙에서는 예약과 링크가 삭제된다.

권장 계약:

* ID 없는 행: 새 항목 생성
* ID 있는 행: 기존 항목의 일부 필드 수정
* 빈 칸: 변경 없음
* ~ 등 별도 기호: 명시적 값 삭제
* 파일에 없는 행: 변경 없음
* ## 삭제에 있는 ID: 항목 삭제

단, ~가 실제 데이터 값으로 쓰일 가능성을 고려해 이스케이프 규칙도 정의해야 한다.

이 방식은 R-06의 챗봇 기반 반복 수정에 더 적합하다.

Q3. 미리보기 상태를 저장하지 않아도 되는가?

판정: 초기 버전에서는 수용 가능.

개인용 앱에서 미리보기 상태 저장까지 구현하는 것은 현재 단계에서 과할 수 있다.

다만 iPhone Chrome에서는 파일 선택 후 앱 전환이나 새로고침이 발생할 수 있다.

따라서 다음 정도면 충분하다.

1. 미리보기는 임시 상태로 유지한다.
2. 적용 전 종료하면 DB가 변경되지 않는다.
3. 같은 파일을 다시 선택하면 동일한 미리보기를 재생성할 수 있다.

별도의 미리보기 영속 저장 기능은 초기 범위에 넣지 않는 것을 권장한다.

Q4. 장소 생성과 계획 저장을 분리해도 되는가?

판정: 현재 명세 그대로는 수용하기 어렵다.

v0.2는 다음 실패를 허용한다.

새 장소 생성
    ↓ 성공
계획 변경
    ↓ 실패
연결되지 않은 장소가 DB에 남음

이는 데이터가 삭제되는 문제는 아니지만, 실패한 가져오기가 DB를 변경한다는 점에서 AC-14와 충돌한다.

권장 순서

파일 해석
    ↓
전체 변경안 구성
    ↓
참조 및 데이터 검증
    ↓
사용자 승인
    ↓
원자적 저장
    ↓
성공 결과 표시

현재 저장 명령이 장소와 계획을 하나의 트랜잭션에서 처리할 수 있는지는 문서에서 확인 불가다.

가능하다면 통합 저장이 가장 명확하다. 불가능하다면 장소 생성의 보상 삭제나 임시 저장 방식을 검토해야 한다.

다만 개인용 앱에 복잡한 분산 트랜잭션 체계를 도입할 필요는 없다.

3. 수용 기준 추가·수정 제안

기존 AC-01~14는 상당히 개선됐다. 다음 다섯 가지를 보완하면 된다.

기준	추가 또는 수정할 내용
AC-15	기존 항목의 메모만 수정한 파일을 가져와도 예약·링크·기타 필드가 의도 없이 삭제되지 않는다.
AC-16	장소 생성 후 계획 저장 실패를 주입해도 승인 전 상태와 동일한 DB가 유지된다.
AC-17	짧은 ID 충돌, 다른 여행 ID, 잘못된 기준 revision을 거부한다.
AC-18	삭제 구역에서 활동·숙소·이동·장소를 정확히 구분하고, 허용되지 않는 삭제는 거부한다.
AC-01 보완	챗봇 출력 6개 중 5개 이상 형식 통과와 별도로, 조용한 데이터 손실 0건을 필수 조건으로 한다.

특히 AC-16은 실제 실패 주입으로 확인해야 한다. 정상 경로 테스트만으로 원자성을 입증할 수 없다.

5. 최종 권고

E0 착수 전 필수 수정 3건

1. 빈 칸 의미 변경: 기존 항목 수정에서 빈 칸은 변경 없음으로 처리하고, 명시적 값 삭제 방법을 정의한다.
2. 식별 계약 확정: 여행ID·기준 revision·항목 ID의 문법과 고유성 범위를 명시한다.
3. 장소 저장 실패 처리: 장소와 계획을 함께 적용하거나, 실패 시 생성된 장소가 남지 않도록 한다.

E0에서 검증할 사항

Markdown 표 형식의 실제 챗봇 생성 성공률, 특수문자 처리, 수정 시 기존 값 보존, 삭제 명령 해석을 시험한다.

A안이 안정적으로 동작한다면 JSON 블록으로 변경할 이유는 없다.

이후로 미뤄도 되는 사항

미리보기 상태 저장, 비용·좌표·예약번호 필드 추가, 기존 AI 기능 제거 여부는 현재 개발의 필수 선행 조건이 아니다.

최종 판단: v0.2는 재설계가 필요한 상태는 아니다. 위 필수 수정 3건을 반영하면 E0에 착수할 수 있다.
```
