# travel-app 요구사항과 MVP 범위

작성일: 2026-10-21 · 상태: 핵심 제품 정책 사용자 확정, 상세 구현 범위 일부 제안

> 계획 재정의 중: 사용자가 전체 개발전략과 목표·이행 완료 기준을 먼저 정하도록 지시했다. 최신 검토 초안은 [최종 목표와 이행 완료 기준](goal-and-migration-criteria.md)이다. 아래 첫 구현 범위와 초기 제외 항목은 기존 프로토타입의 범위이며, SP-FR의 최종 보존 범위나 새 전략의 사용자 합의로 간주하지 않는다.

> 후속 검토: [기능·콘텐츠 이행표](migration-inventory.md)에 원본 조사와 항목별 처리·단계 제안을 정리했다. 예약·장소 장문·지역·기존 미디어를 포함한 이행 범위를 재검토하며, 개별 포함·제외는 아직 합의되지 않았다.

> 설계 검토: [공통 데이터 구조·정본/편집 책임](target-architecture.md)에 새 목표 구조를 제안했다. 기존 프로토타입 구현과 구분한다.

> 구체 대응: [원천 콘텐츠→DB→공통 화면 설계](content-db-mapping.md)에 코드 내 콘텐츠를 포함한 필드/관계 변환과 공통 화면의 조회·저장을 연결했다. 대상 테이블명·필드·화면 구성은 아직 설계안이다.

> 구현 전 계약: [저장·명령·파일 계약](storage-and-exchange-contracts.md), [대표 구간 이행 계획](pilot-migration-plan.md)에 물리 구조와 검증 순서를 제안했다. 기술 한도·복사형 패키지 범위·성능 목표는 작성자의 설계안이며 추가 사용자 정책 합의가 아니다.

## 확정 요구와 첫 사용자 흐름

UI/UX 후속 확정(2026-10-23): **가능한 SP-FR-guidebook의 UI/UX 경험을 살린다.** DB화·공통 프로그램 전환과 함께 원본의 탐색 구조·현장 일정 우선순위·가이드 열람 경험을 보존한다. 추가 편집/기록/백업 기능을 연결하며 기술 점검이 기본 여행 흐름을 지배하지 않도록 한다. 원본과의 차이는 명시하고 실제 표본 화면에서 사용자 확인을 받는다.

이행의 중심 목표(사용자 명확화): 기존 콘텐츠를 코드에 포함된 것까지 데이터화하고, 매번 다른 여행계획을 DB에 저장해 공통 프로그램으로 조회·편집한다. 여행별 데이터와 화면/저장 로직을 분리하며, 새 여행이나 콘텐츠 수정 시 프로그램 코드 변경·여행별 HTML 생성·재빌드를 일상 절차로 요구하지 않는다. SP-FR은 첫 여행 데이터로 사용한다. 구체 DB 제품·스키마·기능별 보존 범위는 별도 설계/검토 항목이다.

확정 요구: 여러 여행, AI의 반복 조사·변경·검증·저장, 여행 중 현장 기록과 재계획 병행, 계획으로 덮어쓰지 않는 실제 기록, 근거와 변경 이유 추적, 기존 콘텐츠 가져오기 경로.

개발전략 후속 확정: SP-FR 이행 완료 수준은 가이드북 조회·핵심 현장 사용까지로 하며 신규 AI 기능 등 최종 목표 달성은 별도로 관리한다. 최종 목표에 장소 설명·여행 가이드 같은 상세 콘텐츠의 앱 내부 작성·수정을 포함한다. 기존 장소 본문 편집은 이행에 포함하고 새 가이드 작성은 이후 확장한다. 지도는 장소·동선 목록과 외부 지도 링크 우선, 내부 지도 조작은 후속이다. 별도 보존할 기존 기기 데이터가 없어 저장소 원본만 이행한다. 저장소에 반영된 현장 상태는 조사하며 새 앱의 현장 기록·백업 기능은 유지한다. 그 외 기능별 세부 범위는 검토 중이다.

콘텐츠 소유·편집 기준 후속 확정: 같은 장소도 여행별 독립 사본으로 관리해 한 여행의 설명 수정이 다른 여행에 자동 반영되지 않게 한다. 이행 후 콘텐츠 편집은 travel-app에서 수행하고 SP-FR은 읽기 원본으로 보존한다. 재가져오기는 앱 편집본과 차이를 확인한 뒤 적용한다.

추가 사용자 확정: 개인용·모바일 우선, 오프라인 일정 조회·현장 기록 저장·백업 파일 제공, 앱 내부 AI 실행, 모든 변경안 확인 후 적용. 이후 OpenAI API의 새 키 안전 생성을 선택했다. 기기 간 자동 동기화는 첫 MVP에 포함하지 않는다. AI 제공자는 OpenAI API로 진행하되 서버 실행 위치·호스팅은 별도 결정이다.

대표 흐름: 여행 생성 또는 가져오기 → 날짜별 일정 조회 → 방문 실패·예정 외 활동 기록 → 현재 계획과 기록을 AI 실행기에 전달 → 조사 근거와 변경안 생성 → 필요한 사용자 결정 → 현재 revision 재확인·검증 → 새 계획 버전 원자 저장 → 재실행 → 실제 타임라인과 변경 이유 조회.

여행 전·중·후는 사용 맥락이다. 날짜가 지났다는 이유로 기능을 잠그지 않는다. 계획과 실제 방문은 각기 다른 시각·시간대를 가질 수 있다.

## 범위 제안

| 기능 | 첫 구현 | MVP 완료에 필요한 후속 |
|---|---|---|
| 여러 여행 | 생성·선택·범위별 저장, 두 가상 샘플을 명시적으로 불러오기 | 사용자 기기 검증 |
| 일정 | 날짜별 조회, 일정 추가·수정·제거를 계획 버전으로 저장 | 대량 편집 UX |
| 실제 기록 | 방문/건너뜀/예정 외 활동, 실제 시각, 메모, 추가식 정정 이력 | 사진·지출 제외 |
| 변경안 | 이유·근거·영향 대상·예약 영향 문구, 미적용 초안, 확인 후 적용/거절 | 모든 변경안 사용자 확인 후 적용으로 확정 |
| 충돌 | 계획과 실제 기록을 포함한 여행 revision 일치 검사, 중복 요청 방지, 복수 탭 트랜잭션 | 다른 기기 충돌은 서버 동기화 단계 |
| 근거 | URL/로컬 출처, 확인 시각·적용 날짜·대상·확인 상태 | 실제 조사 실행기·신선도 판단 |
| 가져오기/백업 | 버전 있는 JSON, SP-FR 일일카드 변환, 미리보기 후 추가, 전체 데이터 백업·빈 저장소 복원 | 원본 예약/사진/장소 장문은 제외 |
| 오프라인 | 설치된 앱 셸 조회·현장 기록·재로드, 온라인 없이 로컬 저장 | 백업 파일 제공까지 포함. 자동 기기 동기화는 제외 |
| AI | 앱 내부 웹 조사·구조화 작성·제한된 보정·초안 자동 저장·확인 적용, 상태·중단·재시작 복원 | 로컬 개발에서 구현·검증. 휴대폰 외부 접속용 인증·호스팅·배포 후속 |

AI 자동 조사 기능을 JSON 교환만으로 완료했다고 보고하지 않는다. 현재 로컬 실행기로 조사·작성·검증·초안 저장을 연결했고, 서버에서 키를 관리한다. queued/researching/planning/validating/awaiting-decision/failed/cancelled/interrupted 상태를 제공한다. applying/succeeded는 별도 서버 쓰기가 아니라 브라우저의 원자적 승인 적용과 적용된 변경안 상태로 표현한다. 공개 서버·실기기 검증까지 완료한 것은 아니다.

## 첫 구현 완료 기준

1. 여행 A/B 사이 일정·기록·변경안이 섞이지 않는다.
2. 새 계획을 적용해도 실제 기록과 과거 계획 버전이 유지된다.
3. 건너뛴 방문과 예정 외 활동을 실제 타임라인에서 날짜·시간순으로 확인한다.
4. 정정은 기존 기록을 보존하고 새 기록이 이전 기록을 참조한다.
5. 초안은 현재 계획을 바꾸지 않는다. 확인 후 적용 시 근거와 이유가 버전에 남는다.
6. 초안 생성 뒤 현장 기록 또는 다른 탭의 변경이 생기면 적용을 거부한다. 최신 컨텍스트로 새 초안을 만들어야 한다.
7. 같은 요청을 재시도해도 버전·실제 기록이 중복 생성되지 않는다.
8. 잘못된 날짜/시간대/DST/참조/중복 ID/빈 변경안을 거부하고 기존 데이터는 보존한다.
9. 앱을 닫았다 열거나 오프라인 재로드해도 데이터가 복원된다. 브라우저 저장소 삭제는 별개이며 백업 파일로 복원한다.
10. SP-FR 형태의 두 일일카드와 별도 짧은 여행을 화면 코드 수정 없이 가져온다. 불확실한 출처·실제 방문 시각을 추정하지 않는다.

## 보류 결정과 제외

개인용·모바일 우선, 오프라인 조회·현장 기록·백업, 앱 내부 OpenAI API 실행과 모든 변경안 확인 후 적용은 사용자 확정이다. 공개 서버·호스팅 위치, 서버 인증, 예산 한도·모델 선택 등은 별도 결정이다. 오프라인에서는 AI 호출 대신 조회·현장 입력을 제공한다.

초기 제외: 계정·공동 편집, 클라우드 자동 동기화, 결제/예약 실행, 사진·지출, 라이브 지도/길찾기, 실시간 위치, 공개 여행 공유, 원본 전체 마이그레이션. GitHub는 소스 저장소로만 사용한다. 공개 앱 번들과 개인 브라우저 데이터는 별개이며 실제 여행 백업·예약·자격증명은 커밋하지 않는다.
