# D단계 개발계획 · 실제 AI 운영·모바일 사용 검증

2026-10-30 · 작성: Codex · **계획 제안 / 사용자 검토 준비 / 구현 미착수**

[설계서](phase-d-design.md)와 [상위 계획](development-plan.md) §7을 실행 가능한 단위로 나눈다.
Codex는 계획/지시·독립 검토, Claude Sonnet은 조사/구현·자체 검사/증거, 사용자는 비용/외부 영향 결정·실기기 확인을 맡는다.
현재 C-06은 진행 중이다. 이번 문서 작성은 D 구현·외부 공개·실제 호출·키 설정·C/B 관문 완료 승인이 아니다.

## 1. 착수·우선순위

- 설계·가상 데이터 기반 준비는 C와 분리 가능하나, 같은 체크아웃의 C-06 코드/검사와 D 편집/검사를 동시에 수행하지 않는다.
  C-06 결과·기준 커밋을 고정하고 필요한 C 보존 회귀를 확보한 뒤 D 구현 지시를 발행한다.
- 기존 운영 순서상 실제 D 실행은 이행 마감과 필요한 사용자 결정 뒤다. 앞당길 경우 미완료 B/C 항목과 실행 범위를 명시적으로 별도 결정한다.
  C 개발을 먼저 하기로 한 10/29 요청을 유료 AI/외부 접속 승인으로 확대하지 않는다.
- 소액 호출 이전에도 가상 E2E·예산/전송/인증·서버 재시작 경계를 먼저 검증한다. PC 실제 성공만으로 D 종료하지 않는다.
- 과거 v1 성공·10/26 v2 모의 통과는 기반 증거다. 최신 C 계약과 새 실행 경로에서 필요한 회귀를 확인한다.
- CL-08/CL-14 같은 후속을 무조건 먼저 전부 수정하지 않는다. 다만 실제 AI의 시간 검증/적용·근거 표시·보존 안전성을 깨뜨리는 경로는
  T-D0에서 재현/분류하고 해당 실제 실행 전에 해결한다. 데이터·비용·권한·충돌 문제는 경미한 항목으로 넘기지 않는다.

## 2. 작업 단위·산출물

각 행은 이후 발행할 구현 지시 단위다. 문서만으로 전체 행을 Sonnet에 자동 위임하거나 외부 실행 권한을 부여하지 않는다.
세부 작업은 최대 3개로 묶고 계약/보안/화면/보고를 검토 가능한 커밋으로 분리한다.

T-D1/2/3은 논리적으로 일부 독립이지만 같은 체크아웃 동시 수정 지시가 아니다.
T-D3의 호스팅/외부 접속·T-D6 호출·T-D7 실자료 시험은 리뷰 가능한 산출물과 승인 범위를 먼저 갖춘 뒤 실행한다.

## 3. 의존 관계

```text
C-06 기준/관련 회귀 → T-D0 ─┬→ T-D1 ─┐
                          ├→ T-D2 ─┼→ T-D4 → T-D5 → T-D6 → T-D7 → G3 사용자 판정
                          └→ T-D3 ─┘
U-D1 → 접근/인증·origin       U-D2/3 → 실제 비용·보관/전송 설정
U-D1~4 + 실제 실행/한도 승인 → T-D6/7
```

새 장소/가이드·숙박/이동의 AI 제안은 **D-X 선택 확장**이다. 현재 item 연산 중심 핵심 흐름에 자동 포함하지 않는다.
D-X를 요청하면 생성/연결·복합 변경·미리보기/승인·revision·재시도·백업의 별도 설계/지시를 작성한다.
선택 확장을 보류한 상태에서는 해당 최종 요구 부분을 미구현으로 표시한다.

## 4. 단계별 결정·사용자 확인

| 관문 | 결정/조건 | 기다리는 범위 |
|---|---|---|
| Q-D0 설계/범위 검토 | 현재 문서의 운영 후보·핵심/확장 구분, C/B 미완료 상태를 확인 | 문서/가상 조사에는 실키·호스팅 결정 불필요 |
| Q-D1 운영 경로 | U-D1: 서버 기기/호스팅·인증·origin·운영 책임 | 외부 공개/접속·자료 origin 이동은 결정 전 실행하지 않음 |
| Q-D2 유료 준비 | U-D2: 모델/통화·요청/기간 한도, U-D3: 전송/보관, U-D4: 시험 자료/시나리오 | 실제 요청 전 동의한 모델/자료/횟수/금액 범위를 고정 |
| Q-D3 최초 실제 결과 | 가상 여행의 실제 호출·초안·거절/확인 적용·사용량을 제시 | 한 번 성공을 모바일/운영 완료로 승격하지 않음 |
| Q-D4 모바일 사용 | 확정 기기에서 실경로·인증/재회수·실행/적용/오프라인 유지·복원 사용자 확인 | G3는 검증 범위·알려진 한계와 함께 판정 |

세부 UI·수치는 제안이다. 사용자 무응답·Claude 완료·자동 검사 통과를 정책/사용자 확인 완료로 기록하지 않는다.
기존에 승인된 설정/범위는 다시 묻지 않되 모델/서버/전송 내용·상한이 바뀌면 해당 동의를 갱신한다.
사용자에게 실제로 보여줄 파일·화면·재현 동작을 각 단위 보고서에 남긴다. 상태는 검토 준비/확인 대기/수정 요청/확인 완료를 쓴다.

## 5. 검증 행렬

| 계층 | 필수 사례·증거 |
|---|---|
| 전송/동의 | 가상 민감 문자열·다른 날짜/여행·원본 정정 이력 제외, 검색 질의에 비공개 값 없음, 입력/서버/모델/기준 변경 시 동의 무효 |
| 비용/요청 | 요청 지문·재전송/다른 본문 재사용 오류, 일일/기간 예약 경쟁, 과금 불명 유지, 금액/도구/보정 한도 도달 전 차단 |
| 권한 | 무인증/만료·소유자 바꿔 get/list/cancel/회수·v1 우회·잘못된 origin·CSRF 거부, 브라우저/로그/번들 키 없음 |
| AI 응답 | 거부·미완성·잘못된 JSON·날짜/시간대/DST·잘못된 ID/기존ID add·없는 URL·가짜 주장·prompt injection·예약 영향 불명 |
| 저장/확인 | 근거+초안 전부 성공/롤백·동일 결과 재회수 1회 저장·저장 실패 후 무료 재회수·실제 기록/메모 이후 stale·거절 시 계획 불변 |
| 장애 | 실제 서버 강제 종료·jobs/원장 파일 손상/쓰기 실패·브라우저/네트워크 종료·취소/결과 도착 경쟁·세션 만료·다른 공간 회수 차단 |
| 사용자 흐름 | 실모바일 조사→근거/영향 검토→확인/거절→회고 당시 근거·오프라인 기록/온라인 복귀·재실행·빈 공간 복원 |

실제 실패/과금 경계를 재현하려고 불필요한 유료 호출을 반복하지 않는다. 불명 결과·소진/오류는 먼저 모의로 검사한다.
실제 시험은 승인 범위 안의 최소 호출로 기능·usage·오류 전달을 확인하고 관찰되지 않은 경계는 모의 증거로 분리한다.
단위·통합·화면의 fixture는 비식별 가상 데이터만 커밋한다. 실제 자료/비용 영수증/로그는 Git 제외 위치에 보관한다.

## 6. 실행·제출·위험 관리

Sonnet은 중간 하위 단계마다 확인을 요구하지 않고 지정 범위를 완료한다. 외부 영향 결정이 필요한 부분만 보류하고 독립 작업을 계속한다.
요약은 20줄/2,000자와 증거 색인으로 제한한다. Codex는 요약→실패/범위→전송·비용·인증·저장 diff→필요한 독립 검사만 읽는다.

- 대상 단위 검사 후 의미 있는 변경은 `pnpm run check`, UI/저장 흐름은 build·E2E. 최종 `check:deferred`로 묶고 포함 검사 중복을 피한다.
- 소유한 서버·포트·테스트 프로필을 확인하고 사용자 데이터/다른 프로세스를 종료·초기화하지 않는다.
- 운영/기능·포맷·구조·보고 커밋을 분리하고 작업 브랜치 push. 코드 push를 main/Pages·AI 서버 공개 승인으로 해석하지 않는다.
- 결과는 `docs/claude-task-dXX-result.md` 형식으로 기준/종료 SHA·실행 환경·모의/실제 구분·비용/승인 범위·명령/exit code·증거·미검증을 적는다.
- 모델/가격/계정 가능 여부는 구현/호출 시 [공식 문서](phase-d-design.md)와 계정 결과로 재확인한다. 개발용 Sonnet 구독과 API 모델/요금을 혼동하지 않는다.

| 위험 | 대응 |
|---|---|
| Pages→새 origin에서 기존 여행이 안 보임 | 데이터 손실로 단정하거나 자동 초기화하지 않고 별도 백업/빈 공간 복원. 이전 origin 보존 |
| 응답 유실 후 이중 과금 | durable intent/in-flight·금액 예약·자동 재호출 금지·불명 결과 표시·새 시도 동의 |
| 기록/검색에 비공개 정보 유출 | allowlist DTO·공개 조사 입력 분리·payload 미리보기 지문·실제 egress 모의 대조 |
| 서버 JSON 완료를 적용으로 오인 | 서버 준비/브라우저 초안 저장/사용자 적용의 세 상태를 분리 |
| C 계약/새 회고와 AI의 차이 | item 허용 범위 고정·수동 연산 자동 편입 금지·당시 revision/실제 기록 보존 회귀 |
