## 계약 결정

- `ChangePlan`만 새 연산 `upsert-stay` / `remove-stay` / `upsert-leg` / `remove-leg`를 받는다(`planEditOperationSchema`). 변경안·AI 경계(`planOperationSchema`, `SaveProposal`/`StageAiProposal`/`DecideProposal`)는 항목 연산 그대로이며, 숙박·이동 연산은 변경안 스키마에서 거부된다(시험). `commandVersion` 2·패키지 v2 불변.
- 숙박 날짜는 `planStay.time.start/end`의 `date`에 대응한다(새 필드 없음). 입실/퇴실 날짜 필수, 퇴실≥입실, `plannedNights`가 있으면 날짜 차이와 일치, 입실·퇴실 시간대가 서로 다르면 날짜 대응이 모호하다고 거부, 지역은 활성 region이어야 함.
- 계산(`src/plan/manual-stays.ts`, SP-FR `spfr-stays`와 분리): 하루 지역=입실≤날짜≤퇴실, 야간 지역=입실≤날짜<퇴실, 0박은 하루 지역에만, 지역 없는 숙박·날짜를 읽을 수 없는 숙박은 지역을 만들지 않음, 같은 밤 서로 다른 지역이 겹치면 고르지 않고 거부(같은 지역 겹침 허용), 방문 장소 지역은 쓰지 않음. 숙박이 바뀐 날짜(이전·새 기간의 합집합)의 `regionIds`/`overnightRegionId`만 같은 새 계획에서 갱신하고 다른 날·필드는 그대로 둔다.
- 이동: 같은 날 두 활동(서로 다른)만 연결. 활동을 제거하거나 다른 날로 옮기면 연결된 이동은 같은 새 계획에서 함께 제거되며, 화면이 "연결된 이동 N개"와 날짜 변경 경고로 미리 알린다(기존 `remove-item`의 이동 제거 동작은 그대로).
- 시간 검증: `timeRangeReversal`(같은 시간대 또는 둘 다 미확인인 현지 시각끼리, 날짜끼리 비교; 서로 다른 시간대는 변환하지 않음)을 **`ChangePlan` 쓰기에만** 적용한다. 가져온 원천의 시간 범위가 든 다른 명령(예약 상태 등)과 읽기 경로는 바꾸지 않아 구 파일·백업 읽기 호환을 유지한다(역전 범위 읽기 시험 포함). DST 건너뛴 시각 거부·겹친 시각을 instant로 확정하지 않음은 기존 스키마가 이미 보장함을 시험으로 고정했다.
- 저장은 기존 `execute()` 트랜잭션: 새 계획 버전·모든 행·현재 계획 포인터·영수증이 함께 저장/롤백, `expectedDomainRevision`·`currentPlanVersionId` 검사, replay.

## 미검증·한계·경미한 발견

- 사용자 화면 확인·Codex 독립 검토·iPhone 실기기 확인 대기. 원격 CI는 push 후 아래에 기록.
- 숙박 편집 화면은 입실·퇴실에 시간대를 하나만 받는다. 서로 다른 시간대 입력(모호성 거부)은 명령 수준에서만 시험했고 화면에서 만들 수 없다. 영향: 시차 있는 이동 숙박은 날짜만 입력해야 한다. 재개: 시차 이동 숙박 UI가 필요할 때.
- 숙박 `bookingId`는 UI에서 만들지 않는다(예약 작성 범위 밖). 저장 시 존재하는 활성 예약이어야 한다.
- 이동의 지도 대상·경로 정보·자동 길찾기는 만들지 않았다(기존 필드는 수정 시 보존).
- 기존 가져온 SP-FR 날은 열거나 저장해도 재계산하지 않는다. 숙박을 편집한 경우에만 그 숙박이 닿는 날짜가 수동 규칙으로 갱신되며, 그날의 원천 숙박 간 겹침이 다른 지역이면 저장이 거부된다.
- 상위 설계/계획 문서는 수정하지 않았다. 제안: 설계 §5의 "복수 지역이 겹치면 검토 오류" 기본안을 그대로 구현했으므로 CL-05 항목을 "시간대 이름 검증은 이미 충족, 역전 검증 보강 완료"로 정정 권고.
