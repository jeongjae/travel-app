## 2. 설계·수용 조건

현재 ci.yml은 전체 검사를 실행하지만 pages.yml은 별도로 포맷/린트·빌드 후 배포한다.
전체 회귀 실패가 Pages를 막는 의존 관계는 없다. 다음 조건을 만족하는 가장 작은 구조를 선택한다.

1. Pages 업로드와 배포는 같은 소스 커밋에 대한 `pnpm run check`, `pnpm run check:pilot`,
   `pnpm run test:e2e`의 성공 뒤에만 실행된다. 검사는 기존 package.json 명령과 고정 버전을 따른다.
2. 실패·취소·필수 검사 생략이면 업로드/배포를 진행하지 않는다.
   `continue-on-error`, `always()` 등으로 이 조건을 우회하지 않는다.
3. 검사한 소스와 공개 빌드 소스가 동일 SHA임을 workflow의 checkout/ref와 의존 관계로 설명한다.
   다른 실행의 ‘최신 성공’이나 검증하지 않은 artifact를 신뢰하는 방식은 사용하지 않는다.
4. 공개 빌드는 `/travel-app/` base·정적 호스팅 설정을 유지하고 앱/가상 자료만 포함한다.
   개인 자료·server·키 제외 검사와 deployment.json의 SHA 기록을 보존한다.
5. 토픽 브랜치/PR 검사에서 Pages 배포가 실행되지 않도록 한다. 실제 배포는 main만 대상으로 보호한다.
   현재 배포 트리거/동시성 설정은 필요한 변경만 한다. 태그 전용 정책 등 별도 운영 결정을 추가하지 않는다.
6. 권한을 필요한 job에만 둔다. 검사 job에 Pages 배포 권한을 확대하지 않는다.
7. ci/pages 사이의 중복은 재사용 workflow 등으로 줄일 수 있으나 구조를 복잡하게 만들지 않는다.
   체크 job과 빌드 job을 분리하면 build가 필수 검사 전체에 의존하는지 확인한다.

대안은 최대2개만 비교하고 선택 이유·실행 그래프·실패/취소/브랜치별 흐름을 결과 보고서에 적는다.
현행 Node/pnpm/Python/Playwright 설정과 가상 검사 정책을 재사용한다. Action 버전은 특별한 이유 없이 바꾸지 않는다.
새 job 분리로 빌드/브라우저/가상환경이 자동 공유된다고 가정하지 않는다.

## 3. 검증과 산출물

- YAML 문법과 job/ref/needs/if/권한을 검사한다. 기존 로컬 검사기가 있으면 사용하고 설치하지 않는다.
- 명령 순서와 실패/취소/생략 시 차단 경로를 검토한다. 정적 검사만으로 GitHub 런타임 실패 주입까지 검증했다고 하지 않는다.
- 실제 workflow에서 쓸 필수 명령을 확인한다. 소스가 같고 유효한 기존 실행 증거를 쓰면 SHA·환경·한계를 적는다.
  명령/환경 변경이나 실패가 있으면 영향 있는 검사를 실행한다. 무관한 전체 검사를 반복하지 않는다.
- 작업 브랜치를 push하고 그 커밋의 CI를 확인한다. 자동 CI 실행은 실제 Pages 배포 성공과 구분한다.
  분리한 재사용 workflow도 검사 경로에서 실행되는지 확인한다.
- 테스트 실패가 업로드/배포를 막는 실제 원격 실행은 배포 없는 검토 경로로만 확인한다.
  안전한 경로가 없으면 미검증으로 남긴다. 검증을 위해 main에 합치거나 실제 공개 배포하지 않는다.
- 사람이 확인할 산출물: workflow diff, 짧은 의존 그래프, 성공/실패/취소/브랜치별 판정표,
  실행 커밋의 CI 링크와 로그 색인. 계획·검사 결과·실제 배포 상태를 구분한다.
