## 2. 해석 — 무엇이 문제인가

> 아래는 작성자의 판단이다. 사용자 확정이 아니다.

### 2.1 가치가 아직 발생하지 않았다
사용자가 확정한 "이행 완료" 수준은 **SP-FR 가이드북 조회 + 핵심 현장 사용**이다. 지금은 43일 중 3일분이 "후보" 상태이고, 휴대폰에서 한 번도 열어 보지 않았다. 설계·검증 문서의 밀도와 비교하면 **실제 사용 가능성 쪽 진척이 극단적으로 뒤처져 있다.**

### 2.2 커밋 0건은 가장 큰 운영 리스크
약 4,000줄 코드와 2,500줄 문서가 단일 PC 디스크에만 존재한다. 디스크 장애·실수 삭제 한 번으로 전부 사라진다. 또한 "어느 시점에 무엇이 바뀌었는가"를 추적할 수 없어, 문서 안의 "과거 이력" 서술로만 변경을 재구성하고 있다. **이것이 handoff.md가 비대해지는 근본 원인이다.** Git 이력이 있으면 handoff는 "현재 상태"만 담아도 된다.

### 2.3 코드 밀도는 유지보수 불가 수준
한 줄 2,000자짜리 JSX는 사람이 diff(변경 비교)를 볼 수 없고, 코드 리뷰·버그 추적·부분 수정이 모두 어렵다. AI 세션이 생성 토큰을 절약하려는 패턴으로 추정된다(가정). 기능 변경 없이 **포매터(Prettier)만 적용**하면 해결되며, 테스트가 있으므로 안전하게 할 수 있다.

### 2.4 문서가 "읽기 비용"이 됐다
매 세션이 handoff 맨 위에 새 절을 추가하는 방식은 투명성은 높지만, 7겹의 "최신"은 다음 세션의 토큰과 시간을 소모한다. 다른 문서들도 "~하지 않았다", "~로 보고하지 않는다"류 부정 서술이 많아 핵심 상태를 찾기 어렵다. 보존은 유지하되 **이력을 별도 파일로 이동(archive)** 해야 한다.

### 2.5 v1/v2 이중 구조와 AI 경로의 불일치
v1은 "전환 후 읽기 전용"으로 계획되어 있는데 AI 서버는 v1 전용이다. 즉 v2로 전환하면 **앱 내부 AI 기능이 사실상 없어진다.** 최종 목표(G-03)로 가려면 v2 AI 실행기를 새로 설계·구현해야 하며, 이는 작은 작업이 아니다.

### 2.6 휴대폰 접근 경로가 미결정이라 실기기 검증이 막힌다
PWA(홈 화면에 설치해 오프라인에서 동작하는 웹앱)의 서비스 워커(오프라인 캐시 담당 스크립트)는 **HTTPS에서만 등록**된다(localhost 예외). 즉 iPhone에서 PC의 `127.0.0.1:4173`을 열 수 없고, LAN IP로 열어도 HTTP라서 오프라인 설치가 안 된다. **호스팅/접근 방식을 결정하지 않으면 R-07~09 실기기 검증은 시작할 수 없다.** 문서들은 이 결정을 계속 "후속"으로 미루고 있다.

### 2A.4 층 사이의 불일치 (가장 중요)

```
사용자 확정 목표          설계가 다루는 범위          구현이 검증한 범위
────────────────        ──────────────────        ──────────────────
모바일 우선        ───→  로컬 PC loopback만   ───→  PC Chromium viewport만
앱 내부 AI 사이클  ───→  v1에만 존재          ───→  v1 모의/실API 1회, v2 없음
SP-FR 가이드북 조회 ──→  23컬렉션 전체 모델    ───→  3일/43일 후보, 적용 0
여러 여행 재사용   ───→  여행별 독립 사본      ───→  가상 A/B만, 실제 2번째 원천 없음
```

한 문장으로: **설계는 최종 목표(G)를 향해 넓게 지었고, 구현은 그 설계를 가상 데이터로 깊게 검증했지만, 사용자가 확정한 중간 목표(이행 완료 = 휴대폰에서 SP-FR 가이드북을 본다)로 가는 직선 경로는 어느 층에서도 우선되지 않았다.**

### 7.2 사용자 질문: "사진/지도 이미지는 별도 파일로 저장하고, 지도는 해당 파일의 링크를 저장하는 방식은 어떨까?"

**결론(작성자 의견): 그 방식이 맞고, 현재 v2 설계가 이미 그 구조다.** 다만 "별도 파일"이 어디에 있는 파일인지에 따라 세 가지로 갈리며, 추천은 ①이다.

| 방식 | "파일" 위치 | 콘텐츠·지도가 보유하는 것 | 장점 | 단점 |
|---|---|---|---|---|
| **① DB 내 별도 레코드** (현재 v2 설계) | IndexedDB의 asset store에 이미지 바이트(Blob)를 **별도 레코드**로 저장 | 참조: asset id + SHA-256 해시 + 원천 경로 | 오프라인 보장, 백업 ZIP에 바이트 포함, 해시로 손상 검증, 같은 이미지 중복 저장 안 함 | DB 용량 증가(43일 전체 시 수백 MB 가능), 백업 파일도 커짐 |
| ② 외부 URL 링크 | GitHub Pages 등 웹 서버의 파일 | URL | DB·백업 작음 | **오프라인에서 안 보임**, 링크 깨짐 위험, 공개 저장소 의존 |
| ③ 기기 파일 시스템(OPFS) | 브라우저 전용 파일 영역 | 파일 경로 | 대용량에 유리 | iPhone Chrome 지원·백업 경로 별도 구현 필요, 복잡도 증가 |

- 사용자 결정 U-5("DB로 저장")는 ①과 일치한다. ①에서 이미지는 콘텐츠 본문·지도 레코드 **안에** 들어가지 않고 **별도 레코드**로 존재하며, 장소 본문·지도 대상·일별 카드는 그 레코드를 **참조(링크)** 한다. 즉 "별도 파일 + 링크"라는 사용자 의도가 DB 안에서 구현된 형태다.
- 보강 제안: 각 asset 레코드에 **원천 URL(공개 저장소 raw 경로)과 권리 표기를 함께 보존**해, 바이트를 확보하지 못한 항목은 참조만 두고 "원문 링크 보존" 상태로 표시한다(②를 예외 경로로만 사용). 지도 이미지도 같은 asset store를 쓰고 `map-target`이 참조한다.
- 수량 정정: 46개는 **variant(해상도별 파생본) 수**다. 독립 자산 수와 파생본을 먼저 구분하고, 앱에 필요한 해상도만 DB에 넣는 것을 기본으로 한다(§8 보정).
- 용량 관리: Phase 2에서 전체 미디어 총 용량을 측정하고, 필요하면 **원본 + 축소본(썸네일) 2단 저장** 또는 "여행별 선택 다운로드"를 Phase 2'에서 검토한다. 이는 제안이며 아직 결정이 아니다.
