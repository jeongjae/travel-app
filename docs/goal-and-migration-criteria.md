# travel-app 최종 목표와 이행 완료 기준

작성일: 2026-10-21 · 상태: 검토 초안 v0.5 · 콘텐츠 DB화·공통 프로그램 전환을 이행 중심 목표로 명시

이 문서는 개발전략 1단계인 최종 목표와 이행 완료 기준을 정의한다. 상세 기능별 이행표, 설계, 기술 스택, 구현 일정은 후속 단계에서 다룬다. 사용자 확정 요구와 이번에 제안하는 기준을 구분한다. 기준을 적었다는 것이 구현·검증 완료를 뜻하지 않는다.

## 1. 확정된 방향

- 특정 SP-FR 여행에 고정되지 않고 여러 여행에 재사용하는 독립 앱이다.
- 이행의 핵심은 기존 콘텐츠를 코드에 포함된 것까지 데이터화하고 여행별 DB에 저장해, 기존 정적 웹페이지의 조회·편집을 공통 프로그램으로 제공하는 것이다. SP-FR은 첫 여행 데이터이며 이후 다른 여행도 같은 구조로 사용한다.
- 개인용·모바일 우선이다.
- 여행 전 계획, 여행 중 실제 기록과 재계획, 여행 후 조회를 지원한다. 날짜에 따라 기능을 잠그지 않는다.
- 계획과 실제 기록을 구분하며 계획 변경으로 실제 기록을 덮어쓰지 않는다.
- 앱 내부 OpenAI API로 조사·변경안 작성·검증·저장을 연결하고, 모든 AI 변경안은 사용자 확인 후 적용한다.
- 오프라인 일정 조회·현장 기록 저장·백업 파일을 제공한다.
- SP-FR 이행 완료 수준은 가이드북 조회·핵심 현장 사용까지다. 신규 AI 기능 등 최종 목표 달성은 별도로 관리한다.
- 최종 목표에 장소 설명·여행 가이드 같은 상세 콘텐츠의 앱 내부 작성·수정을 포함한다. 기존 장소 본문 편집은 이행에 포함하고 새 가이드 작성은 이후 확장한다.
- 지도는 장소·동선 목록과 외부 지도 링크를 우선 이행한다. 앱 내부 지도 조작은 이후 구현한다.
- 별도로 보존할 기존 기기 데이터는 없어 저장소 원본만 이행한다. 저장소에 반영된 현장 상태는 조사 대상이며 기존 기기 DB·저널·캐시·자격증명 추출은 제외한다. 새 앱의 현장 기록·백업 지원은 유지한다.
- 같은 장소도 여행별 독립 사본으로 관리한다. 한 여행에서 고친 설명을 다른 여행에 자동 반영하지 않는다.
- 이행 후 콘텐츠는 travel-app에서 관리한다. SP-FR은 읽기 원본으로 보존하고, 재가져오기는 앱 편집본과 차이를 확인한 뒤 적용한다.
- 기존 SP-FR-guidebook은 보존한다. 기존 콘텐츠를 가져오는 범위와 형식은 요구사항 정의에서 확정한다.
- 사용자 지시로 구현 중심 진행을 멈추고 개발전략을 먼저 검토한다. 전체 방향과 핵심 구조를 정한 뒤 단계별 이행·검증·확장을 진행하는 전략을 바탕으로, 현재는 목표·완료 기준부터 논의한다.

근거: PROJECT_INSTRUCTIONS.md, SESSION_HANDOFF.md 및 후속 사용자 답변. 문서의 권고·설계 후보는 사용자 확정으로 간주하지 않는다.

## 2. 최종 목표 문장 — 제안

> 기존 콘텐츠를 코드에 포함된 것까지 데이터화하고, 서로 다른 여행계획을 DB에 저장해 공통 프로그램에서 조회·편집하는 개인용 여행 앱을 만든다. 여러 여행의 가이드와 일정을 관리하고 상세 콘텐츠를 앱 안에서 작성·수정한다. 여행 중 실제 활동을 기록하면서 AI와 남은 계획을 수정하며, 여행 후에는 실제 여정과 변경 이유를 확인할 수 있어야 한다. 필요한 현장 정보와 기록은 오프라인에서도 사용할 수 있고, 데이터를 백업·복원할 수 있어야 한다.

앱 내부 상세 콘텐츠 작성·수정은 사용자 확정이다. 편집 형식, AI의 본문 작성 지원, 오프라인 본문 편집, 콘텐츠 재사용·변경 이력의 구체적인 방식은 후속 요구사항에서 정한다. 목표 문장의 나머지 세부 표현과 아래 검증 기준은 검토안으로 유지한다.

### 목표 사용자 시나리오 — 요구에서 도출한 검토안

| ID | 상황 | 사용자가 얻어야 할 결과 |
|---|---|---|
| S-01 | 여행 준비 | 새 여행을 만들거나 기존 자료를 가져와 날짜별 일정과 관련 가이드·제약을 확인한다. AI 조사 결과와 변경안을 검토해 계획에 반영한다. |
| S-02 | 현장 조회 | 휴대폰에서 오늘 일정과 필요한 장소·이동·예약 정보를 찾는다. 미리 저장한 범위는 통신 없이도 조회한다. |
| S-03 | 실제 기록 | 방문·건너뜀·예정 외 활동을 기록하고, 잘못 입력한 기록을 원래 이력을 남기며 정정한다. |
| S-04 | 여행 중 재계획 | AI가 현재 계획·실제 기록·관련 제약을 읽고 근거와 영향이 있는 변경안을 만든다. 사용자가 확인하면 검증 후 반영하며 과거 기록은 유지한다. |
| S-05 | 여행 후 회고 | 계획과 실제 여정을 구분해서 조회하고 무엇을 왜 바꿨는지 확인한다. |
| S-06 | 재사용·복구 | 다른 여행도 프로그램 코드 수정 없이 사용한다. 백업을 복원해 콘텐츠·계획·기록·연결 관계를 다시 확인한다. |
| S-07 | 콘텐츠 작성·수정 | 앱 안에서 장소 설명과 여행 가이드를 작성·수정하고 저장 후 다시 조회한다. 외부 원고 수정이나 프로그램 재빌드를 필수 작업으로 요구하지 않는다. |

장소·이동·예약 정보의 구체적인 보존 범위는 다음 단계의 기존 자산 조사에서 항목별로 확정한다. S-02가 외부 예약 실행이나 오프라인 지도 전체 저장을 뜻하지는 않는다.

## 3. 완료 시점의 구분 — 수준 사용자 확정·세부 판정 기준 검토 중

| 구분 | 의미 | 의존 관계 |
|---|---|---|
| 기존 자산 이행 완료 | 합의한 SP-FR 콘텐츠와 핵심 현장 사용을 새 앱에서 이어갈 수 있고, 데이터 보존·오프라인·복구를 검증한 상태 | 상세 이행표와 원본 기준본 확정 후 판정 |
| 최종 목표 달성 | 여러 여행에서 콘텐츠 작성·수정, 준비·현장 기록·재계획·회고가 연결되고 앱 내부 AI를 포함한 목표 시나리오가 실제 사용 환경에서 검증된 상태 | 이행 완료만으로 달성했다고 하지 않음 |

사용자가 이행 완료 수준을 가이드북 조회·현장 사용까지로 선택했다. 이행 자체에 신규 AI 기능 전체의 완성을 묶지 않는다. 기존 장소 본문 편집은 이행, 새 가이드 작성과 내장 지도 조작은 후속이며 지도 목록·링크를 우선한다. 이행 원본은 저장소로 한정한다. 두 단계에서 공통으로 쓸 데이터 경계는 설계 단계에서 먼저 정한다.

다음 표는 판정 기준의 초안이다. 실제 대상 목록과 예외가 승인되기 전에는 이행 범위가 확정된 것이 아니다.

| M-01 기준본·범위 | 원본 저장소 revision, 가져올 파일·콘텐츠·기능, 보류·제외 항목과 이유가 식별된다. 저장소에 반영된 현장 상태를 분류한다. 사용자 답변에 따라 별도 기기 데이터 추출은 제외한다. | 원본 목록과 기능·콘텐츠 이행표. 기존 조사 수량은 참고이며 선택한 기준본으로 다시 산정 |

| M-08 백업·복원 | 이행된 콘텐츠, 계획, 기록과 연결 관계를 백업하고 새 저장 환경에서 복원해 확인한다. | 백업 전후 데이터 대조와 복원 후 핵심 조회·기록 흐름 확인 |
| M-09 독립성·원본 보존 | 다른 여행을 추가할 때 코드나 고정 SP-FR 경로를 수정하지 않는다. 원본은 변경하지 않고 복귀용 자료를 유지한다. | 원본 변경 없음 확인, 두 번째 여행 시나리오, 복귀 절차 확인 |
| M-10 실사용 전환 | 합의한 휴대폰 환경에서 핵심 흐름을 검증하고 개인 정보·비밀값을 공개하지 않는다. 알려진 제약과 운영·복구 방법을 설명할 수 있다. | 실기기 검증 기록, 접근·저장 범위 확인, 사용자 전환 판단 |
| M-11 데이터화·프로그램 전환 | 선택 범위의 파일/코드 내 여행 콘텐츠가 DB 필드·본문·관계·첨부 참조로 대응되고 공통 프로그램이 이를 조회·편집한다. 다른 여행 추가와 데이터 수정이 여행별 코드 변경·HTML 재생성·재빌드 없이 해당 화면에 반영된다. | 원천→DB→화면 대응표, 프로그램 소스 변경 없이 두 여행의 추가/전환/수정·재실행 검증. HTML 보관이나 일부 일정 변환만으로 완료하지 않음 |

### 판정 규칙

- 합의한 이행 대상의 미처리 항목과 설명 없는 데이터 손실은 0건이어야 한다.
- 핵심 시나리오를 막거나 데이터를 훼손하는 미해결 결함은 0건이어야 한다. 그 외 잔여 결함·제약은 영향과 처리 방침을 명시해 사용자에게 확인받는다.
- 누락 항목을 사후에 임의로 제외해 통과시키지 않는다. 범위 변경은 이유와 사용자 결정을 기록한다.
- 자동 대조와 사용자 관점 표본 검증을 함께 수행한다. 표본 대상은 도시·날짜 경계·재방문·긴 본문·예약·기존 수정 등 실제 원본의 특성을 반영해 정한다.
- GitHub 동기화 같은 기존 구현을 그대로 옮겨야 하는지는 기능별 조사에서 정한다. 사용자에게 필요한 결과와 이를 구현하는 수단을 구분한다.
- 외부 연동을 아직 검증하지 않았다면 미검증으로 남긴다. 사용자 결정으로 제외한 기존 기기 데이터 추출은 미완료 대기 조건으로 두지 않는다. 새 앱의 실제 휴대폰 사용 검증은 필요하다.
- 위 조건의 검증 결과와 남은 제약을 검토한 뒤 사용자가 실사용 전환 여부를 판단한다. 이 문서 작성 자체는 이행 승인이나 배포 승인이 아니다.

| ID | 완료 조건 |
|---|---|
| G-01 범용성 | SP-FR 및 별도의 짧은 여행에서 S-01~S-07을 코드 수정 없이 수행하고 여행 간 콘텐츠·계획·기록이 섞이지 않는다. 같은 장소의 설명을 한 여행에서 편집해도 다른 여행의 독립 사본은 바뀌지 않는다. |
| G-02 계획·실제·이력 | 현재 계획, 과거 계획, 실제 기록, 미승인 변경안을 구분한다. 일정 변경·삭제와 기록 정정 후에도 실제 여정과 연결된 이력을 조회한다. |
| G-03 AI 전체 흐름 | 앱 안에서 조사→근거·이유·영향이 있는 변경안→사용자 확인→검증→저장→재조회가 연결된다. 사용자가 조사 결과를 수동 복사해 저장해야 하는 구조만으로 완료하지 않는다. |
| G-04 사용자 통제 | 미승인 AI 변경안은 현재 계획을 바꾸지 않는다. 생성 중 계획·현장 기록이 바뀌면 오래된 결과를 무단 적용하지 않는다. 중복 요청도 중복 적용되지 않는다. |
| G-05 실패 대응 | AI 실패·중단·재시작·검증 오류·결정 대기를 구분한다. 실패 시 기존 데이터를 유지하고, 재시도 여부와 불확실한 근거를 사용자가 알 수 있다. |
| G-06 현장 지속성 | 확정한 휴대폰 환경에서 오프라인 조회·기록·재실행·온라인 복귀 및 백업·복원을 검증한다. 온라인 AI 접근과 앱 업데이트 후 데이터 보존도 확인한다. |
| G-07 실사용 가능성 | 휴대폰의 AI 접근 방식, 인증·개인 데이터 전송 범위·키 관리·비용 제한·운영 방법을 결정하고 해당 환경에서 검증한다. 로컬 PC 동작이나 모바일 화면 너비 검사만으로 완료하지 않는다. |
| G-08 콘텐츠 편집 | 앱 안에서 장소 설명·여행 가이드를 작성·수정·저장하고 재실행 후 조회한다. 편집 결과와 관련 일정·장소의 연결을 유지하며 백업·복원 후에도 확인한다. 구체적인 편집 형식과 이력 정책은 후속 정의한다. |

최종 목표 달성은 모든 미래 기능의 구현을 의미하지 않는다. 사진·지출·공동 편집·자동 동기화·예약 실행 등의 포함 여부는 별도 결정한다. 내장 지도 조작은 이후 구현하며 제공자·기능·시점은 후속 정의한다. 미정 기능을 확정 목표에 추가하거나 영구 제외한 것으로 간주하지 않는다.

## 6. 현재 상태와 다음 논의

- 현재 코드는 기술 검증용 프로토타입이다. 기존 단위·브라우저·실 API 검사 결과는 docs/handoff.md에 있으며, 전체 SP-FR 이행과 실기기 여행 사용을 검증한 결과는 아니다.
- 이전 명세의 일정 중심 가져오기와 장문·예약·전체 이행 제외는 당시 첫 구현 범위다. 이번 전략의 최종 보존 범위로 확정하지 않는다.
- 사용자 답변 반영: SP-FR 이행 완료는 가이드북 조회·현장 사용까지이며, 상세 가이드 콘텐츠의 앱 내부 작성·수정은 최종 목표에 포함한다.
- 후속 답변 반영: 기존 장소 본문 편집은 이행에 포함, 지도 목록·외부 링크 우선, 새 가이드 작성·내장 지도 조작은 후속이다. 별도 기기 데이터가 없어 저장소 원본만 이행한다.
- 남은 정의: 다른 핵심 현장 기능의 세부 범위, 저장소의 기존 콘텐츠·현장 상태·미디어 목록, 본문 편집의 상세 동작. 위 사용자 선택 외 M-01~M-11, G-01~G-08 및 목표 시나리오의 세부 조건은 아직 제안이다.
- 2단계 [기능·콘텐츠 이행표](migration-inventory.md) v0.2에 원본 조사와 후속 사용자 결정을 반영했다. 다른 개별 항목의 제안이 일괄 확정되거나 실제 이행이 완료된 것은 아니다.
- 3단계 [공통 데이터 구조·정본/편집 책임](target-architecture.md) v0.3에 목표 논리 모델·시간·저장·이행/백업 설계와 기술 대안을 제안했다. 여행별 독립 사본·앱 중심 편집 및 콘텐츠 DB화·공통 프로그램 전환의 중심 목표를 사용자 확정으로 반영했다. M-11은 이 목표의 검증 방법 제안이며 나머지 세부 설계와 함께 검토안이다.
- 다음 구체화는 필드별 스키마·명령/파일 계약·물리 저장·기술 선택과 대표 구간 선정이다. 파일별 상세 목록은 실제 이행에 앞서 구체화한다. 구현 작업은 아직 재개하지 않는다.
