# travel-app 개선 제안: 여행 취향 진단 + 목적지 가이드 + AI 여행계획 수립

## 1. 핵심 제안

말씀하신 두 가지 기능을 도입하면 travel-app의 여행계획 수립 방식이 한 단계 발전할 수 있습니다.

1. **여행 취향·조건 설정(Travel Profile)**: 질문에 답하거나 선택지를 고르는 방식으로 여행의 기본 조건을 빠르게 결정합니다.
2. **목적지 탐색 가이드(Destination Guide)**: 해당 목적지에서 무엇을 보고, 먹고, 경험할 수 있는지 미리 보여주고 관심 항목을 선택하게 합니다.

이 두 기능을 결합해 **AI에게 전달할 여행계획 요청서(Travel Brief)**를 자동으로 생성하는 구조를 권장합니다.

핵심은 사용자가 처음부터 AI에게 모든 조건을 설명할 필요가 없도록 하는 것입니다.

> **여행 조건 선택 → 목적지 탐색 → 관심 항목 선택 → AI와 일정 구체화 → travel-app에 반영**

이렇게 하면 AI는 여행 취향을 처음부터 파악하는 데 시간을 쓰기보다, 이미 정리된 조건과 관심 장소를 바탕으로 실제 여행계획을 만드는 데 집중할 수 있습니다.

# 3. 기능 A: 여행 취향·조건 질문 템플릿

## 3.1 질문을 세 가지 유형으로 구분

모든 질문을 한꺼번에 제시하면 설정 자체가 번거로워집니다.

따라서 다음 세 단계로 구성하는 것이 좋습니다.

| 구분 | 내용 | 입력 방식 | 권장 여부 |
|---|---|---|---|
| 기본 조건 | 목적지, 여행 기간, 인원 | 짧은 입력·선택 | 핵심 |
| 여행 성향 | 관광 스타일, 음식, 이동, 예산, 숙소 | 선택형 질문 | 선택 |
| 세부 선호 | 특정 관심사, 제한사항, 특별 요청 | 선택·자유 입력 | 선택 |

**설계 원칙은 '필수 질문 최소화, 선택형 질문 최대화'입니다.**

### 3.2 질문 템플릿 예시

| 영역 | 질문 | 선택지 예시 |
|---|---|---|
| 여행 목적 | 이번 여행에서 가장 중요한 것은? | 관광 / 휴식 / 미식 / 자연 / 문화·예술 / 쇼핑 / 특별 체험 |
| 여행 속도 | 어느 정도의 일정이 좋은가? | 여유롭게 / 보통 / 알차게 |
| 여행 경험 | 해당 목적지 방문 경험은? | 처음 / 재방문 / 여러 번 방문 |
| 예산 | 예산 수준은? | 절약형 / 보통 / 여유형 / 직접 입력 |
| 숙소 | 선호 숙소 유형은? | 호텔 / 리조트 / 료칸 / 아파트형 / 게스트하우스 |
| 숙소 위치 | 무엇이 가장 중요한가? | 교통 편리 / 관광지 접근 / 조용한 지역 / 가격 |
| 교통 | 선호 이동 방식은? | 도보+대중교통 / 렌터카 / 택시 중심 / 혼합 |
| 음식 | 음식에 대한 관심은? | 현지 음식 / 유명 맛집 / 고급 식당 / 간편한 식사 |
| 관광 | 관심 분야는? | 역사 / 건축 / 미술 / 자연 / 도시 풍경 / 쇼핑 |
| 체험 | 어떤 활동을 원하는가? | 현지 투어 / 쿠킹 클래스 / 공연 / 액티비티 / 체험 없음 |
| 동행 | 누구와 여행하는가? | 혼자 / 부부·연인 / 가족 / 친구 |
| 제약사항 | 반드시 고려할 사항은? | 이동 제약 / 식이 제한 / 어린이 동행 / 기타 |

여기서 예산은 '절약형' 같은 상대적 표현만으로 끝내지 않는 것이 좋습니다.

AI가 실제 계획을 만들려면 다음 정보가 유용합니다.

- 총예산 또는 1인당 예산
- 항공권 포함 여부
- 숙박비 포함 여부
- 사용 통화

이 항목들은 상세 설정에서 추가로 입력하도록 합니다.

## 3.3 사용자 입력 부담을 줄이는 방법

**① 기본값 제공**

예를 들어 여행 속도는 '보통', 이동은 '대중교통 중심'을 초기값으로 제시합니다. 단, 이 값은 사용자가 선택한 선호와 구별해 저장합니다.

**② 복수 선택 허용**

관광 스타일은 미식과 문화·예술을 동시에 선택할 수 있어야 합니다.

**③ 중요도 선택**

단순히 관심 여부만 묻지 않고 중요도를 설정합니다.

| 항목 | 중요도 |
|---|---|
| 미술관 | 꼭 포함 |
| 현지 음식 | 꼭 포함 |
| 자연 관광 | 가능하면 |
| 쇼핑 | 관심 없음 |

**④ 이전 여행 설정 재사용**

한 번 설정한 취향은 다음 여행에서 불러올 수 있도록 합니다.

다만 모든 여행에 동일한 취향을 강제로 적용하지는 않습니다.

예를 들어 평소에는 미술관을 선호하더라도 가족여행에서는 다른 활동을 우선할 수 있기 때문입니다.

따라서 다음 두 개념을 구분하는 것이 좋습니다.

- **기본 여행 프로필:** 사용자에게 비교적 지속적인 선호
- **이번 여행 설정:** 특정 여행에만 적용되는 조건과 우선순위

# 4. 기능 B: 목적지 탐색 가이드

이 기능은 단순한 관광지 목록이 아니라 **여행의 전체 구도를 잡기 위한 의사결정 도구**로 설계하는 것이 중요합니다.

사용자가 여행지에 대해 충분히 알지 못하는 상태에서는 AI에게 무엇을 요청해야 할지도 모를 수 있습니다.

목적지 가이드는 그 문제를 해결합니다.

## 4.1 가이드의 기본 구성

예를 들어 교토 여행을 준비한다고 가정하겠습니다.

| 가이드 영역 | 제공 내용 | 사용자가 결정할 사항 |
|---|---|---|
| 목적지 개요 | 지역 특성, 주요 관광 구역, 권장 체류 기간 | 여행의 큰 방향 |
| 꼭 볼 것 | 대표 명소, 역사·문화 유산, 전망 | 방문 후보 |
| 꼭 먹을 것 | 지역 음식, 식사 유형, 음식 문화 | 먹거리 후보 |
| 꼭 체험할 것 | 전통문화, 공방, 공연, 액티비티 | 체험 후보 |
| 미니투어 | 반나절 도보, 음식 투어, 역사 투어 | 투어 참여 여부 |
| 지역별 특징 | 구역별 분위기와 주요 볼거리 | 숙소·관광 거점 |
| 추천 동선 | 인접 명소 조합, 이동 시간 | 일정 구성 |
| 여행 팁 | 계절, 혼잡, 예약 필요 여부 | 준비 사항 |

### 핵심: 정보 나열보다 선택을 지원

예를 들어 '교토에서 볼거리 50곳'을 보여주는 것보다 다음처럼 정리하는 편이 효과적입니다.

**교토를 처음 방문한다면 고려할 대표 경험**

| 경험 | 대표 예시 | 예상 소요 | 선택 |
|---|---|---|---|
| 전통 거리 산책 | 기온·히가시야마 | 반나절 | 꼭 가기 |
| 사찰·문화유산 | 기요미즈데라 일대 | 2~4시간 | 관심 |
| 자연 풍경 | 아라시야마 | 반나절 | 관심 |
| 전통 음식 | 교토식 요리 | 식사 1회 | 꼭 하기 |
| 전통문화 체험 | 다도 체험 | 1~2시간 | 제외 |

*위 항목과 시간은 가이드 UI를 설명하기 위한 예시이며, 실제 추천 정보는 별도 검증이 필요합니다.*

이러한 방식으로 사용자가 선택하면 AI가 계획을 세우기 위한 입력 데이터가 자연스럽게 쌓입니다.

## 4.2 목적지 가이드는 계층적으로 구성

여행지 정보를 한 화면에 모두 보여주면 정보가 너무 많아집니다.

따라서 다음 구조를 권장합니다.

```text
목적지: 일본
    │
    ├── 간사이
    │     ├── 교토
    │     │    ├── 대표 볼거리
    │     │    ├── 음식
    │     │    ├── 체험
    │     │    ├── 미니투어
    │     │    └── 여행 구역
    │     │
    │     ├── 오사카
    │     └── 나라
    │
    └── 홋카이도
          └── 삿포로
```

이 구조의 장점은 여행 기간에 따라 추천 범위를 조절할 수 있다는 점입니다.

예를 들어 3박 4일이면 교토 중심으로, 7박 8일이면 교토·오사카·나라를 함께 검토하도록 안내할 수 있습니다.

단, 국가·지역·도시가 항상 일정한 계층을 이루는 것은 아니므로 데이터 모델에서는 유연한 목적지 관계를 지원하는 것이 좋습니다.

# 5. 기능 C: 목적지 가이드를 여행계획으로 연결

이 부분이 가장 중요합니다.

가이드를 읽고 끝나는 것이 아니라 **선택한 항목이 AI 여행계획 요청서에 자동 반영**되어야 합니다.

## 5.1 관심 항목의 세 가지 상태

각 항목에 다음 상태를 제공합니다.

| 상태 | 의미 | AI에게 전달하는 지침 |
|---|---|---|
| **꼭 포함** | 반드시 방문하거나 경험하고 싶음 | 일정에 우선 반영 |
| **관심** | 여건이 되면 포함 | 동선·시간을 고려해 추천 |
| **제외** | 이번 여행에서는 원하지 않음 | 원칙적으로 추천하지 않음 |

예를 들어 사용자가 다음과 같이 선택했다고 가정합니다.

```text
[꼭 포함]
- 기요미즈데라
- 기온 산책
- 교토 전통 음식

[관심]
- 아라시야마
- 다도 체험

[제외]
- 쇼핑 중심 일정
```

이 정보를 취향 설정과 결합하면 다음과 같은 요청서를 만들 수 있습니다.

---

## 5.2 AI 여행계획 요청서 예시

**여행 기본 정보**

| 항목 | 값 |
|---|---|
| 목적지 | 교토·오사카 |
| 기간 | 3박 4일 |
| 동행 | 성인 2명 |
| 여행 속도 | 보통 |
| 예산 | 중간 수준 |
| 교통 | 대중교통 중심 |
| 숙소 | 교통 편리한 호텔 |

**선호 및 선택 항목**

- 문화유산과 전통 거리 산책을 우선합니다.
- 지역 음식 경험을 중요하게 생각합니다.
- 기요미즈데라와 기온은 반드시 포함합니다.
- 아라시야마와 다도 체험은 일정에 여유가 있으면 포함합니다.
- 쇼핑 중심 일정은 제외합니다.
- 하루에 지나치게 많은 관광지를 넣지 않습니다.

**AI에게 요청할 작업**

1. 여행 기간에 맞는 지역별 일정 구도를 제안합니다.
2. 숙소를 어느 지역에 잡는 것이 효율적인지 설명합니다.
3. 선택한 방문지와 체험을 고려해 날짜별 일정을 작성합니다.
4. 이동 동선과 소요 시간을 검토합니다.
5. 미정인 항목은 추측해서 확정하지 않고 질문합니다.
6. 계획이 정리되면 travel-app Markdown 양식으로 출력합니다.

이 요청서는 사용자가 직접 작성하지 않습니다.

**travel-app이 입력된 조건과 선택 결과를 조합해 자동 생성합니다.**

# 6. 목적지 가이드는 어떻게 준비할 것인가?

여기에는 세 가지 접근 방식이 있습니다.

## 대안 A. 목적지별 가이드를 미리 제작

교토·오사카·도쿄·파리 등 주요 목적지의 가이드를 직접 준비하는 방식입니다.

**장점**
- 내용의 품질을 관리하기 쉽습니다.
- 인터넷 연결 없이 열람할 수 있습니다.
- 같은 정보를 반복 생성할 필요가 없습니다.
- 개인적으로 축적한 여행 자료를 재사용할 수 있습니다.

**단점**
- 목적지가 늘어날수록 제작·관리 부담이 증가합니다.
- 영업시간이나 가격 등 변경되는 정보의 최신성을 유지하기 어렵습니다.

## 대안 B. AI로 목적지 가이드 생성

사용자가 목적지를 입력하면 AI에게 해당 지역의 가이드를 작성하도록 요청합니다.

**장점**
- 새로운 목적지를 빠르게 지원할 수 있습니다.
- 여행 취향에 맞는 가이드를 만들 수 있습니다.
- 기존에 준비하지 않은 목적지에도 대응할 수 있습니다.

**단점**
- AI가 잘못된 정보를 제공할 수 있습니다.
- 정보 출처와 최신성 검증이 필요합니다.
- 호출 방식에 따라 비용과 네트워크 연결이 필요합니다.

## 대안 C. 기본 가이드 + AI 보완

**가장 권장하는 방식입니다.**

```text
사전에 준비한 목적지 가이드
             │
             ▼
사용자 취향에 맞게 항목 선별
             │
             ▼
부족한 정보는 AI에게 조사 요청
             │
             ▼
사용자가 관심 항목 선택
             │
             ▼
AI 여행계획 요청서 생성
```

기본 가이드는 안정적인 정보를 중심으로 구성합니다.

예를 들어 다음 정보는 비교적 오래 활용할 수 있습니다.

- 대표 관광지
- 지역의 역사·문화적 특징
- 주요 관광 구역
- 지역 음식 종류
- 대표적인 체험 유형
- 일반적인 여행 동선

반면 다음 정보는 여행 시점에 다시 확인해야 합니다.

- 영업시간
- 입장료
- 예약 가능 여부
- 교통 운행 시간
- 계절별 행사 일정

이처럼 **안정적인 정보와 변동성이 높은 정보를 분리**하면 관리 부담을 줄일 수 있습니다.

# 7. 목적지 가이드를 데이터베이스로 관리하는 구조

현재 travel-app의 목표가 여러 여행에서 재사용 가능한 데이터베이스 기반 앱이라는 점을 고려하면, 목적지 가이드를 단순한 Markdown 문서로만 관리하는 것보다 **재사용 가능한 콘텐츠 데이터**로 관리하는 방향이 적합합니다.

다만 처음부터 복잡한 데이터베이스를 만들 필요는 없습니다.

## 7.1 권장 개념 모델

```text
Destination
목적지
    │
    ├── GuideItem
    │    ├── 볼거리
    │    ├── 먹거리
    │    ├── 체험
    │    └── 미니투어
    │
    ├── Area
    │    └── 지역별 특징
    │
    └── GuideSource
         └── 정보 출처·확인일

TravelProfile
기본 여행 취향
    │
    ▼
TripPreferences
이번 여행 설정
    │
    ▼
TripSelections
선택한 가이드 항목
    │
    ▼
TravelBrief
AI 여행계획 요청서
    │
    ▼
TripPlan
여행 일정
```

여기서 중요한 설계 원칙은 다음과 같습니다.

**목적지 가이드와 실제 여행계획을 분리합니다.**

예를 들어 기요미즈데라는 목적지 가이드에 한 번 등록되어 여러 여행에서 활용할 수 있습니다.

반면 특정 여행에서 기요미즈데라를 방문할 날짜와 시간은 그 여행의 일정에만 속합니다.

이렇게 해야 같은 장소 정보를 여러 여행에 중복 저장하는 문제를 줄일 수 있습니다.

## 7.2 기존 데이터 모델과의 관계

현재 설계서에는 `place`와 `placeLinks` 개념이 있습니다.

따라서 새로운 가이드 기능을 설계할 때는 기존 장소 데이터를 최대한 재사용하는 것이 좋습니다.

| 데이터 | 역할 |
|---|---|
| `place` | 실제 장소 정보 |
| `GuideItem` | 장소·음식·체험·투어를 추천하는 콘텐츠 |
| `TripSelection` | 특정 여행에서 선택한 관심 항목 |
| `TripPlan` | 실제 날짜·시간이 정해진 여행계획 |

음식이나 미니투어는 반드시 하나의 장소에 대응하지 않을 수 있습니다.

예를 들어 '교토 전통 음식 체험'은 특정 식당을 선택하기 전에도 관심 항목으로 등록할 수 있어야 합니다.

따라서 **GuideItem을 place와 동일한 개념으로 취급하지 않는 것**이 좋습니다.

이 모델은 신규 제안이며, 기존 코드와의 상세 호환성은 별도 검토가 필요합니다.

# 8. 사용자 편의성을 더 높이는 추가 아이디어

## 8.1 여행 스타일 프리셋

사용자가 모든 질문에 답하지 않아도 되도록 대표적인 여행 스타일을 제공합니다.

| 프리셋 | 기본 설정 |
|---|---|
| 첫 방문 핵심 관광 | 대표 명소 우선, 보통 일정 |
| 여유로운 휴식 | 하루 일정 적게, 이동 최소화 |
| 미식 중심 | 음식·시장·식당 우선 |
| 문화·예술 탐방 | 박물관·미술관·건축·역사 중심 |
| 자연·풍경 | 자연 명소·산책·전망 중심 |
| 가족여행 | 이동 부담 최소화, 휴식 시간 확보 |

프리셋은 설정을 빠르게 시작하기 위한 초기값일 뿐이며, 사용자가 자유롭게 변경할 수 있어야 합니다.

## 8.2 목적지 가이드의 추천 코스

개별 관광지만 보여주는 대신 미리 구성된 코스를 제공합니다.

예를 들어 다음과 같습니다.

**교토 전통문화 반나절 코스**
- 기요미즈데라
- 히가시야마 거리
- 기온

**교토 자연·풍경 반나절 코스**
- 아라시야마 일대
- 산책 및 경관 감상

사용자는 개별 장소를 하나씩 선택하지 않고 코스 전체를 선택할 수 있습니다.

AI는 이를 실제 여행 일정에 맞게 조정합니다.

이 기능은 특히 처음 방문하는 여행지에서 유용합니다.

## 8.3 선택 항목의 일정 적합성 표시

사용자가 관심 장소를 너무 많이 선택하면 여행 일정에 모두 넣기 어렵습니다.

따라서 선택한 항목의 대략적인 소요 시간을 합산해 다음과 같이 보여줄 수 있습니다.

```text
여행 기간: 3박 4일

꼭 포함한 항목: 7개
관심 항목: 5개

예상 관광 소요: 약 22시간
이동·식사·휴식 시간: 별도

[일정 구성 가능성 검토]
```

이때 단순 소요 시간 합계만으로 가능·불가능을 단정하지 않고, AI가 동선과 영업시간을 고려해 검토하도록 합니다.

# 9. 개발 단계 제안

기존 설계서의 E0~E4를 유지하면서 **여행계획 사전 준비 기능을 점진적으로 추가**하는 것을 권장합니다.

| 단계 | 기존 설계 | 추가 제안 |
|---|---|---|
| **E0** | Markdown 계약·챗봇 출력 검증 | 질문 템플릿, Travel Brief 형식 설계 |
| **E1** | 새 여행 가져오기 | 텍스트 붙여넣기, 기본 조건 입력, AI 요청서 복사 |
| **E2** | 기존 여행 수정·내보내기 | 현재 계획 기반 AI 수정 요청 |
| **E3** | 직접 입력·세부 자료 | 여행 취향 프로필, 목적지 가이드 MVP, 관심 항목 선택 |
| **E4** | AI 기능 재평가 | 가이드 AI 보완, 추천 코스, 개인화 기능 |

다만 E3에서 목적지 가이드를 처음 제공하면 그전까지는 핵심 사용성을 검증하기 어렵습니다.

따라서 **목적지 가이드의 최소 버전은 E1과 병행해 별도로 시험**하는 것이 좋습니다.

초기에는 교토처럼 하나의 목적지만 선정하고 다음 항목으로 제한할 수 있습니다.

- 대표 볼거리 10개
- 대표 음식·식사 경험 5개
- 대표 체험 5개
- 반나절 추천 코스 3개

이 숫자는 초기 검증을 위한 예시입니다.

# 10. 우선 구현할 MVP

여러 아이디어를 한꺼번에 구현하기보다 다음 네 가지로 시작하는 것을 권장합니다.

| 우선순위 | 기능 | 이유 |
|---|---|---|
| **1** | 여행 기본 조건·취향 질문 템플릿 | 입력 부담이 작고 구현이 쉬움 |
| **2** | 목적지 가이드 카드와 관심 항목 선택 | 사용자가 여행의 전체 구도를 잡을 수 있음 |
| **3** | 선택 결과 기반 AI 요청서 자동 생성 | 사전 준비와 실제 AI 계획 수립을 연결 |
| **4** | AI 결과 붙여넣기·검증·저장 | 계획 수립부터 앱 반영까지 흐름 완성 |

MVP에서 가장 중요한 검증 질문은 다음과 같습니다.

> **사용자가 AI와 대화를 시작하기 전에 여행의 주요 조건과 관심 항목을 충분히 결정할 수 있는가?**

이것이 확인되면 목적지 가이드의 범위를 확대하고, 이후 여행별 선호 학습이나 AI 기반 맞춤 추천을 추가할 수 있습니다.

## 최종 권고: travel-app을 'AI 여행계획 준비 플랫폼'으로 발전

이번 아이디어를 반영하면 travel-app의 역할은 다음처럼 확장됩니다.

| 단계 | travel-app의 역할 | AI 챗봇의 역할 |
|---|---|---|
| **탐색** | 목적지 가이드 제공 | 부족한 정보 조사 |
| **선택** | 취향·조건·관심 항목 관리 | 선택지 설명 및 비교 |
| **계획** | AI 요청서 생성 | 일정·동선·숙소·교통 구체화 |
| **확정** | 계획 검증·미리보기·저장 | 수정 결과 생성 |
| **실행** | 오프라인 일정 조회·기록 | 필요시 대안 제시 |
| **회고** | 여행 기록·평가·재사용 | 필요시 요약 지원 |

**가장 중요한 설계 방향은 'AI에게 질문하는 방법을 개선하는 것'이 아니라, '사용자가 AI에게 질문하기 전에 여행의 큰 그림을 쉽게 결정하도록 돕는 것'입니다.**

이를 위해 **여행 취향 질문 템플릿 + 목적지 가이드 + 관심 항목 선택 + AI 요청서 생성**을 하나의 연결된 기능으로 설계하는 것이 적절합니다.

이 구조는 기존의 Markdown 기반 데이터 교환 방식을 유지하면서도, travel-app을 단순한 AI 결과 저장 앱이 아닌 **여행 탐색·계획·실행·회고를 연결하는 앱**으로 발전시키는 기반이 됩니다.
