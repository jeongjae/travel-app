# C단계 설계서 · 별도 여행의 작성·현장 기록·회고

2026-10-28 · 상태: **Codex 수정 요청 / 사용자 미확정** · 초안: Claude(10/28) · 근거: [실행계획](development-plan.md) §6, [요구사항](product-requirements.md), [최종 목표/이행 기준](goal-and-migration-criteria.md) S-01~S-07·G-01/02/08·M-09, [데이터 모델](data-model.md), `src/contracts/v2/*`, `src/storage/schema.ts`

2026-10-29 Codex [검토 결과](phase-c-review.md)·[문서 보완 R1](phase-c-r1.md)을 우선 적용한다. 아래 본문은 보완 전 초안이며 구현 기준으로 확정하지 않았다.

이 문서는 C단계의 사용자 시나리오·화면 흐름·저장 규칙·완료 조건을 정한다. 구현 단위와 검증 순서는 [C단계 개발계획](phase-c-plan.md)에 둔다. **확정 요구**는 사용자가 이미 밝힌 것, **제안**은 작성자의 설계안, **미결정**은 사용자 결정이 필요한 항목이다. 제안을 사용자 합의로 기록하지 않는다.

## 1. 목적과 전제

C단계의 중심 질문: **"SP-FR과 별도인 여행 하나를 앱 안에서 만들고, 준비 → 현장 기록·계획 수정 → 회고 → 백업·복원까지 코드 수정 없이 이어서 쓸 수 있는가."**

| 구분 | 내용 |
|---|---|
| 확정 요구 | 여러 여행(G-01), 계획·실제·이력 구분(G-02), 앱 안의 장소 설명·여행 가이드 작성·수정(G-08, 최종 목표), 여행별 독립 콘텐츠 사본, 개인용·모바일 우선·오프라인 조회·백업, 모든 변경안 확인 후 적용 |
| 확정 순서 | AI 재구현은 이행 완료 뒤(D단계). C의 기본 흐름은 **수동으로 완결**되어야 하며, AI는 같은 저장 명령을 쓰는 계약만 정의한다 |
| 전제(사실) | 현재 v2 명령은 기존 콘텐츠 편집(`EditContentSection`/`UpdateContent`)·계획 항목 변경(`ChangePlan` upsert-item/remove-item)·현장 기록(`RecordActual`/`CorrectActual`/`AddNote`)·여행 생성(`CreateTrip`, 초기 계획 일괄)까지 있다. **새 지역·장소·가이드를 만드는 명령, 날짜·숙박·이동을 바꾸는 연산은 없다** |
| 경험 반영 | 메모 결함(저장됐으나 재조회 안 됨) → 작성 기능은 재조회까지 완료 조건. REG-01 → 지역·숙박·장소·계획·실제의 의미를 먼저 구분. 재가져오기·복원 → 새 작성 기능도 revision 충돌·과거 보존·격리·백업을 처음부터 포함 |

## 2. 용어와 의미 구분 (REG-01 교훈)

| 용어 | 의미 | 현 저장 위치 | 주의 |
|---|---|---|---|
| 지역 (region) | 여행 안의 도시/권역 콘텐츠. 이름·소개·가이드 목록 | `content_revisions` kind `region` | 여행별 사본. 다른 여행과 공유하지 않음 |
| 숙박 (stay) | 지역에 checkin~checkout으로 머무는 계획 행 | `plan_stays` | 숙박이 지역을 정하며 반대가 아님 |
| 하루 지역 `day.regionIds` | 그날 닿는 숙박 지역 전부(`checkin ≤ 날짜 ≤ checkout`), 이동일은 출발·도착 둘 다 | `plan_days` | T-04 기준. 길이 1로 야간 지역을 추정하지 않음 |
| 야간 지역 `day.overnightRegionId` | 그날 밤 자는 지역(`checkin ≤ 날짜 < checkout`의 마지막), 없으면 미설정 | `plan_days` | 종료일·숙박 없는 날은 미설정 |
| 장소 (place) | 방문할 수 있는 곳의 설명 콘텐츠. 지역 참조 | `content_revisions` kind `place` | 장소 자체와 그 장소의 방문 계획을 구분 |
| 방문 계획 (plan item) | 특정 날짜·순서의 활동. 장소를 참조할 수 있음 | `plan_items`(계획 버전별) | 같은 장소 여러 번 가능. 계획 버전은 불변 |
| 이동 (leg) | 날짜 안의 구간 이동 계획 | `plan_legs` | 현재 편집 연산 없음 |
| 실제 활동 (actual) | 방문/건너뜀/예정 외의 실제 기록. 계획 항목·장소를 선택 참조 | `field_records` kind `actual` | 계획 변경이 실제 기록을 바꾸지 않음 |
| 정정 (correction) | 이전 실제 기록을 `supersedes`로 가리키는 새 기록 | `field_records` kind `actual` | 원본 삭제·수정 없음 |
| 가이드 (guide) | 지역/여행 수준의 읽을거리 섹션 본문 | `content_revisions` kind `guide`, `region.guideIds`로 연결 | 장소 설명과 구분 |
| 메모 (note) | 대상(날짜·장소·항목 등)에 붙는 현장 메모 | `field_records` kind `note` | 저장 후 대상에서 다시 열어 읽혀야 함 |
| 변경안 (proposal) | 미적용 계획 변경 초안. 확인 후 적용 | `proposal_heads/revisions` | 수동·AI 모두 같은 구조 |

## 3. 사용자 시나리오 — 사용자가 볼 산출물을 먼저 정한다

각 시나리오의 **산출물·확인 동작**이 완료 조건이다. 자동 검사·보고서만으로 완료하지 않는다.

| ID | 시나리오 | 사용자가 직접 볼 산출물 | 확인 동작 |
|---|---|---|---|
| C-S1 새 여행 만들기 | 이름·기간·시간대·지역 1개 이상·숙박을 입력해 여행을 만든다 | 여행 목록에 새 여행, 일정 탭에 기간만큼의 날짜, 각 날짜의 하루/야간 지역 | 여행 전환 시 SP-FR 콘텐츠가 섞이지 않음. 앱 재실행 후 유지 |
| C-S2 장소·가이드 작성 | 지역 안에 장소를 만들고 설명을 쓴다. 지역 가이드를 쓴다 | 장소·지역 탭에서 새 장소 카드, 준비·회화 탭에서 새 가이드 | 다른 탭에서 찾기 → 열어 읽기 → 재실행 후 읽기 |
| C-S3 일정 연결·수정 | 장소를 날짜에 방문 계획으로 넣고 순서·시간을 바꾼다. 숙박·이동을 추가한다 | 일정 탭의 해당 날짜에 항목, 전체 일정의 요약, 계획 버전 번호 증가 | 이전 계획 버전을 열면 변경 전 내용이 그대로 보임 |
| C-S4 현장 기록·정정 | 방문/건너뜀을 기록하고 예정 외 활동을 새 장소 또는 기존 장소로 기록한다. 잘못 쓴 기록을 정정한다 | 실제 기록 탭의 날짜별 타임라인, 정정 전·후 둘 다 표시 | 계획을 바꿔도 기록이 남음. 오프라인에서 기록 후 재실행 |
| C-S5 회고 조회 | 여행 뒤 날짜별로 계획·실제·변경 이유를 이어 읽는다 | (후보) 실제 기록 탭의 날짜 보기에 당시 계획 버전과 변경 이유 링크 | 날짜·항목에서 변경안·이유로 이동 가능 |
| C-S6 백업·복원·격리 | 두 여행(SP-FR 사본 + 새 여행)을 전체 백업하고 빈 공간에 복원한다 | 복원된 공간에서 C-S1~C-S5 산출물이 그대로 보임 | 새 여행 콘텐츠·기록이 SP-FR 여행에 나타나지 않음(역도 같음) |

## 5. 저장·이력 규칙

### 5.1 현재 명령의 공백 (사실)

- 새 `region`/`place`/`guide`를 만드는 명령이 없다. `UpdateContent`는 `expectedRevisionId`가 필수라 기존 revision에만 쓴다.
- `ChangePlan`은 `upsert-item`/`remove-item`만 있다. `plan_days`·`plan_stays`·`plan_legs`는 `CreateTrip`의 초기 계획 또는 가져오기로만 만들어진다.
- `CreateTrip`은 초기 계획 전체를 한 번에 받는다. 화면에서 날짜·지역을 입력해 계획을 구성하는 변환층이 없다.

### 5.2 제안 명령·연산

| 제안 | 내용 | 규칙 |
|---|---|---|
| `CreateContent` | `region`/`place`/`guide`(필요 시 `booking`/`task`) 새 entity 생성 | entityId 신규·중복 거부, 참조(`regionIds`·`guideIds`) 존재 검사, `actor: 'user'`, 새 revision 1 |
| `ChangePlan` 연산 확장 | `upsert-day`/`remove-day`, `upsert-stay`/`remove-stay`, `upsert-leg`/`remove-leg` | 하루 지역·야간 지역은 **숙박에서 계산**(T-04 helper와 같은 규칙)하고 사용자가 직접 입력하지 않음. 날짜 삭제 시 그 날의 항목·이동 처리 방침 명시 |
| 여행 생성 변환층 | 화면 입력(기간·지역·숙박) → `CreateTrip` 초기 계획 | 저장 계약은 유지, 화면 쪽 변환만 추가 |
| 연결 규칙 | 항목은 `placeRef`로 장소 참조, 가이드는 `region.guideIds`로 연결 | 비활성 콘텐츠를 새로 참조하지 않음 |

### 5.3 변하지 않는 규칙 (기존 계약 유지)

- **revision 충돌**: 콘텐츠는 `expectedRevisionId`, 계획은 `currentPlanVersionId`, 변경안은 `expectedProposalRevision`으로 최신 여부를 검사한다. 오래된 기준의 저장은 `CONFLICT`로 거부하고 기존 데이터는 그대로 둔다.
- **불변 revision·과거 보존**: 계획 버전·콘텐츠 revision·실제 기록은 수정하지 않는다. 정정은 새 기록, 삭제는 비활성화다.
- **격리**: 모든 행은 `[spaceId+tripId]` 키 안에 있다. 새 여행의 콘텐츠는 SP-FR 여행과 entityId가 같아도 다른 행이다. 장소 설명을 한 여행에서 고쳐도 다른 여행은 바뀌지 않는다(G-01).
- **백업·복원**: 전체 백업은 컬렉션 단위로 모든 kind를 담으므로 새 kind/연산도 포함돼야 한다. **자동 포함을 가정하지 않고** 새 콘텐츠·연산·정정이 빈 공간 복원 뒤 그대로 조회되는지 검사한다. 여행 패키지(ZIP) 내보내기에 수동 작성 여행을 넣을지는 미결정.
- **재가져오기와의 관계**: 수동 작성 여행은 `import_heads`/lineage가 없어 재가져오기 대상이 아니다. SP-FR 여행에 수동으로 추가한 콘텐츠·항목은 재가져오기 검토에서 `app-only`로 보존돼야 한다. 다만 T-04가 발견한 **F-4(항목 `order`만으로 정렬해 같은 패키지도 `app-only` 차이로 보임)**가 남아 있으면 이 검사가 오탐하므로 F-4 수정이 선행한다.
- **메모 교훈**: 저장 성공 응답은 완료가 아니다. 작성·기록의 모든 기능은 **저장 → 다른 화면에서 찾기 → 다시 열어 읽기 → 앱 재실행(또는 오프라인 재로드) 후 읽기** 4단계를 E2E에 넣는다.

## 7. D단계 AI 계약 연결점 (제안)

- AI는 C에서 추가한 **같은 명령**(`CreateContent`, 확장된 `ChangePlan` 연산)을 변경안 payload로만 쓰고, 저장은 `StageAiProposal` → `DecideProposal(confirmedByUser: true)`로만 이뤄진다. 수동 경로와 저장 코드를 공유하므로 C의 검증이 D의 저장 안전성 증거가 된다.
- 변경안 payload 스키마(`planOperationSchema`)의 확장은 C에서 정하고, D는 조사·근거·실행 운영만 추가한다.
- AI가 새 장소·가이드를 제안하는 범위(콘텐츠 생성 변경안)는 D의 별도 결정으로 남긴다.
