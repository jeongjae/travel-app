## 1. 목표·범위

SP-FR과 별도인 여행을 코드 수정 없이 만들고 준비→현장 기록·계획 수정→회고→백업·복원까지 수동으로 완결한다.
사용자 확정은 여러 여행, 여행별 독립 콘텐츠, 앱 내부 장소 설명·가이드 작성/수정, 계획·실제·이력 분리,
개인용·모바일 우선·오프라인 조회/기록·백업, 변경안 확인 후 적용이다. 실제 AI 실행은 D에서 따로 검증한다.

| 구분 | C의 범위 |
|---|---|
| 최소 흐름 | 콘텐츠 없는 여행 생성, 지역/장소/가이드 작성·재조회, 장소의 일정 연결·순서/시각 수정, 숙박/구간 이동의 최소 편집, 실제 기록·정정, 회고, 두 여행 복원 |
| 기존 호환 기본안 | 지역 없는 여행 허용, 콘텐츠 제거는 비활성화, 이름·날짜·지역 탐색, 현행 섹션 편집, 전체 백업 우선 |
| 별도 확장 | 여행 기간/날짜 삭제, 새 예약·할 일 작성, 전체 본문 검색, 수동 여행 ZIP 내보내기, 고급 비교 UI |
| C에 추가하지 않음 | 새 사진·지출 입력, 내부 지도 조작, 자동 동기화, AI 콘텐츠 생성 변경안. 기존 첨부 보존·조회·백업 회귀는 유지 |

기본안은 호환성을 위한 작성자 제안이며 새 사용자 합의로 기록하지 않는다. 기존 동작을 바꾸는 정책은 해당 작업 전에 확인한다.
새 여행 검사에는 현실적인 가상 시나리오를 먼저 사용한다. 실제 여행 대상은 사용자 자료를 받았을 때 정하며 가상 기록을 실제 방문이라고 보고하지 않는다.

## 2. 현 구현과 추가할 기능

2026-10-29 계약 조사 기준: `src/contracts/v2/exchange.ts`, `content.ts`, `planning.ts`, `validate.ts`,
`src/storage/content-repository.ts`와 `src/content/Journey.tsx`를 대조했다. 이후 구현 시 기준 커밋을 다시 확인한다.

- `CreateTrip`은 초기 계획을 받지만 `contents`/`heads`는 빈 배열로 시작한다. 초기 날짜는 콘텐츠 참조 없이 생성한다.
- 기존 편집은 `EditContentSection`/`UpdateContent`, 계획 변경은 `upsert-item`/`remove-item`이다.
- 현장 기록·정정·메모·비활성화 명령은 있다. 새 콘텐츠 생성 및 날짜/숙박/이동 편집 연산은 아직 없다.
- 현재 v2 저장 경로는 `ContentRepository`(`src/storage/content-repository.ts`, `src/repository.ts`에서 연결)다.
  UI에서 테이블을 직접 쓰거나 v1 경로에 새 v2 명령을 우회 구현하지 않는다.

| 개념 | 의미·연결 |
|---|---|
| 지역 | 여행별 `region` 콘텐츠. 숙박·장소가 선택 참조하며 지역 자체가 숙박을 의미하지 않는다 |
| 장소 | `place.regionIds`와 선택 `guideId`를 가진 설명 대상. 방문 계획과 별도다 |
| 가이드 | `place-guide`·`region-guide`·`preparation` 등 기존 문서 kind를 따른다. 장소 설명도 guide일 수 있다. `ownerRef`와 소유자의 연결이 일치해야 한다 |
| 계획 | 불변 버전의 날짜·항목·이동·숙박. 장소 연결은 실제 필드 `placeLinks`를 사용한다 |
| 실제·정정 | 추가식 현장 기록. 정정은 `supersedes`로 이전 기록을 가리키며 원문을 덮어쓰지 않는다 |
| 변경안 | 현재 스키마는 계획 연산 중심이다. 콘텐츠 생성 명령을 그대로 담을 수 있는 범용 승인함으로 가정하지 않는다 |

## 3. 사용자 시나리오·화면

기본 탐색은 **오늘(일정)·전체 일정·가이드(장소·지역)·지도·준비(준비·회화)**의 5개 축이다.
예약·실제 기록·변경안은 보조 도구, 가져오기 기록·백업은 해당 기존 경로를 유지한다. 탭 추가를 선행 조건으로 두지 않는다.

| ID | 사용 흐름·산출물 | 화면 위치 제안·확인 동작 |
|---|---|---|
| C-S1 | 이름·기간·확인한 시간대로 콘텐츠 없는 여행 생성, 날짜 카드 조회 | 기존 새 여행 모달→오늘/전체 일정. 지역/숙박 없이 저장하고 여행 전환·재실행 후 확인 |
| C-S2 | 지역, 장소와 설명, 지역 가이드 작성 | 가이드에서 지역/장소 작성, 준비 또는 소유 지역에서 가이드 접근. 저장→다른 화면에서 찾기→열기→재실행 후 읽기 |
| C-S3 | 장소 일정 연결·순서/시간 수정, 숙박·이동 편집 | 오늘/전체 일정에서 새 계획과 이유 확인. 이전 버전·실제 기록이 그대로인지 확인 |
| C-S4 | 방문/건너뜀/예정 외 활동·메모·정정 | 실제 기록 보조 도구. 기존 장소 선택 또는 장소 없이 기록 가능. 오프라인 저장·재실행·정정 전후 조회 |
| C-S5 | 날짜별 당시 계획·실제·변경 이유 이어 읽기 | 실제 기록의 날짜 보기 확장을 기본 후보로 제시. 현재/당시 계획 구분, 정정 원문·변경 이유로 이동 |
| C-S6 | SP-FR 사본과 새 여행을 백업·빈 공간 복원 | 두 여행의 본문·계획·기록·이력·첨부 재조회. 한 여행 편집이 다른 여행에 누출되지 않음 |

작성/기록은 DB 행 존재가 아니라 4단계 재조회를 완료 조건으로 둔다. 새 장소가 필요한 예정 외 활동은 먼저 장소 작성을 완료한 뒤 기록하며,
두 작업을 한 버튼의 단일 저장으로 표현한다면 콘텐츠와 기록을 묶는 원자 명령을 별도 설계해야 한다. 최소 C는 두 명시적 저장을 사용한다.

## 4. 생성·연결과 저장 경계

### 4.1 생성 순서

1. 기존 `CreateTrip`으로 콘텐츠 없는 여행과 기간의 날짜 행을 생성한다. `regionIds=[]`, 야간 지역 미설정, 항목/숙박/이동은 빈 배열이다.
2. 지역 콘텐츠를 만든다. 장소·가이드는 독립 초안으로 편집할 수 있으나 저장 시 최종 참조 그래프가 유효해야 한다.
3. 장소와 장소 본문, 지역과 지역 가이드 등 서로 연결되는 생성/갱신은 아래 단일 명령으로 저장한다.
4. 저장된 콘텐츠를 확인한 뒤 별도 `ChangePlan`으로 장소·숙박·이동을 연결한다. 실패해도 유효한 미배치 장소가 남는 것은 정상이다.

### 4.2 최소 새 명령 제안: `CreateContentBatch`

이름은 구현 전 확정한다. 범용 임의 쓰기 배치가 아니라 **신규 region/place/guide와 그 소유 연결 갱신**에 한정한다.
입력은 envelope의 tripId/requestId/normalizationVersion/expectedDomainRevision,
신규 콘텐츠 목록, 기존 소유자 연결 갱신 목록과 각 expectedRevisionId다. UI가 commitSeq·저장 시각·actor를 지정하지 않는다.

- 신규 entity/revision ID 중복·다른 여행 참조·비활성 대상의 신규 연결을 거부한다.
- 기존 데이터와 신규 목록을 합친 최종 그래프에서 모든 참조와 kind·ownerRef·역방향 소유 연결을 검사한다.
- `place.guideId`↔장소 guide의 ownerRef, `region.guideIds`↔지역 guide의 ownerRef를 함께 검증한다.
  여행 수준 가이드는 기존 ownerRef/documentKind 규칙을 따르며 존재하지 않는 지역에 억지로 연결하지 않는다.
- 저장소의 한 트랜잭션에서 새 revision/head·소유자 revision·여행 revision·receipt를 함께 쓴다. 어느 검사/쓰기든 실패하면 전부 롤백한다.
- 같은 저장 단위에서 참조할 ID를 미리 정하되 행을 순차 공개하지 않는다. 모든 생성과 참조 검사를 마친 최종 상태만 노출한다.

다음은 **문서상 계약 예시이며 실행한 테스트나 현존 JSON 스키마가 아니다**.

| 입력 예 | 성공/실패 기대 |
|---|---|
| 새 장소 P1(guideId=G1) + 새 place-guide G1(owner=P1) + 기존 지역 R1 참조 | 같은 저장에서 두 콘텐츠가 조회된다. 장소 본문은 기존 필수 why_go/deep/practical 섹션을 포함한다 |
| 기존 지역 R1의 revision r1→r2(guideIds에 G2 추가) + 새 region-guide G2(owner=R1) | r1의 일치와 여행 revision을 모두 검사하고 r2/G2를 함께 저장한다 |
| 위 입력 중 G2가 없는 owner·다른 여행을 참조하거나 R1 revision이 stale | 콘텐츠·head·여행 revision·receipt 변화 0 |
| 동일 requestId·동일 입력 재시도 / 동일 ID·다른 입력 재사용 | 기존 결과 replay, 중복 revision 없음 / 재사용 오류·기존 데이터 보존 |

### 4.3 계획 편집의 최소 확장

장소 연결·순서·시간은 기존 item 연산을 우선 사용한다. 날짜 추가/기간 변경 없이 숙박·이동의 upsert/remove만 별도 작은 단위로 확장한다.
항목을 제거할 때 참조하는 leg가 있으면 관련 변경을 같은 ChangePlan에 포함시키거나 전체 거부한다. 조용한 연결 삭제는 하지 않는다.
숙박 변경에 따른 날짜의 지역 표시는 같은 새 계획 버전에 반영한다. 과거 계획·콘텐츠 pin·실제 기록은 바꾸지 않는다.
여행 기간/날짜 삭제와 연쇄 제거는 후속 설계로 남긴다. 초기 날짜 생성은 새 여행 생성에만 적용한다.

## 5. 날짜·숙박·지역 규칙

SP-FR의 T-04 규칙은 원천 보존용이다. checkout 포함 하루 지역, checkout 미포함 야간 지역, 마지막 원천 숙박 선택을
일반 사용자 입력의 정책으로 자동 승격하지 않는다. 기존 SP-FR의 day 지역·숙박·출처는 C 진입만으로 재계산하지 않는다.

C 수동 입력의 계산 기본안은 다음과 같다. 새 도메인 검증을 거친 입력에만 적용하고 구현 전 가상 예제를 제출한다.

- 날짜는 기존 `date`/Temporal 검증으로 실재하는 달력 날짜인지 검사한다. 2026-02-30과 역전 기간을 거부한다.
- 기존 timeSpec/timeRange를 사용한다. 숙박 모델에 없는 checkin/checkout 필드를 그대로 저장하지 않고 time 범위에 명시적으로 대응한다.
- IANA 시간대와 날짜만 있는 입력·시각까지 확인된 입력을 구분한다. 미확인 시간대·DST 중복/누락 시각을 임의 보정하지 않는다.
- 확인된 지역/현지 날짜의 숙박만 하루 지역(퇴실일 포함)·야간 지역(퇴실일 제외)에 사용한다. 장소 방문 지역을 숙박 지역으로 합치지 않는다.
- 같은 밤 복수 지역이 겹치면 원천 배열의 마지막 지역으로 고르지 않고 검토 오류로 돌려 저장을 보류한다(수동 입력 기본안).
- 같은 날 입퇴실은 하루 지역에는 포함하되 야간 지역은 만들지 않는다. 숙박 없음/지역 미확정은 빈 지역·야간 미설정을 허용한다.
- 시간대가 다른 숙박/이동은 각 입력의 확인된 현지 날짜를 보존한다. 날짜 대응이 모호하면 관련 자동 계산을 적용하지 않고 사용자에게 확인한다.

일반 규칙은 순수 계산 모듈로 분리할 수 있으나 `spfr-stays`를 그대로 공통 정책으로 쓰지 않는다.
가져오기 어댑터의 원천 규칙은 별도 유지하고, 실제 달력·범위·모호성 검증을 공용화할 수 있는지 구현 시 판단한다.

## 6. 충돌·이력·보존

- 기존 여행을 수정하는 새 명령은 **expectedDomainRevision**을 필수로 검사한다.
  콘텐츠 연결 갱신에는 expectedRevisionId, ChangePlan에는 currentPlanVersionId를 추가 검사한다. 계획 ID만 같아도 현장 기록이 바뀌었으면 stale 저장을 거부한다.
- 기존 SaveProposal/DecideProposal의 별도 revision·기준 검사 규칙을 보존한다. 모든 기존 명령의 envelope가 같다고 가정하지 않는다.
- 동일 요청 replay는 기존 receipt 규칙을 따른다. 검증 실패 후 부분 receipt를 남기거나 재시도 시 ID를 새로 만들어 중복을 숨기지 않는다.
- 콘텐츠 revision·계획 버전은 불변, 정정은 추가식이다. 비활성화는 기존 명령을 사용하며 과거 계획/기록의 참조를 계속 읽는다.
- [spaceId+tripId] 격리·기존 사용자 DB·v1/SP-FR 원본·출처·첨부 보존을 유지한다. 실패 시 입력을 보존하고 최신 상태 재검토를 제공한다.
- 수동 생성 여행은 lineage 없이 시작한다. 가져온 여행에 새로 작성한 콘텐츠/항목은 재가져오기에서 app-only로 보존한다.
  F-4 오탐 수정(T-05)이 해당 검사의 선행 조건이며 실제 사용자 후보 적용은 별도 결정이다.
- 전체 백업 후 빈 검토 공간에서 새 콘텐츠/연결·계획 이력·정정·회고·기존 첨부까지 복원한다. 새 명령이 자동으로 백업 호환이라고 가정하지 않는다.

## 7. 수용 기준과 D 경계

| 영역 | 수용 기준 |
|---|---|
| 작성 | 지역 없는 여행부터 생성, 장소/가이드의 4단계 재조회·비활성 과거 참조 유지 |
| 저장 | 참조 실패·stale·동시 현장 기록·중복 요청·중간 실패의 원자성 검증, 구 v2 패키지/백업 읽기 유지 |
| 계획/실제 | 새 계획만 변경, 이전 계획·정정 원문 보존, 모호한 숙박 자동 추정 없음 |
| 회고 | 날짜별 당시/현재 계획·실제·정정·변경 이유를 구분해 이어 읽음. 없던 근거를 생성하지 않음 |
| 복원 | C-S1~C-S5를 두 여행 백업/빈 공간 복원 뒤 조회, 여행 간 누출 0 |
| 확인 | Claude 자체 검사·Codex 검토·사용자 화면 확인을 별도 기록. PC/모바일 가상 검사와 iPhone 실제 확인을 구분 |

현재 StageAiProposal·planOperationSchema는 계획 중심이다. CreateContentBatch를 기존 변경안에 넣을 수 있다고 쓰지 않는다.
D에서 콘텐츠 생성 제안을 지원하려면 payload·승인 단위·ID/연결·revision·재시도·전송/비용 정책을 별도 설계한다.
C의 수동 저장 검증은 재사용 가능한 기반이며 실제 AI 실행이나 AI 콘텐츠 승인이 검증된 증거는 아니다.

## 8. 제안 기본안과 확인 시점

| 항목 | 기본안·필요한 확인 |
|---|---|
| 편집기 | 기존 Markdown 섹션 편집을 확장. T-C3 전에 실제 입력/재조회 시제품을 제시하고 사용자 확인. 새로운 폼/리치 에디터는 별도 제안 |
| 회고 | 실제 기록의 날짜 보기 확장. T-C6에서 화면 후보를 보고 확인. 새 탭을 확정하지 않음 |
| 여행 대상 | 자동 검사는 가상 여행. T-C8에서 실제/가상 사용자 시나리오를 명시하고 수행 |
| 지역·삭제·검색·백업 | 빈 지역 허용·비활성화·이름/날짜/지역 탐색·전체 백업을 유지하는 기본안. 정책 변경을 원할 때만 별도 확인 |
| 추가 범위 | 사진/지출·새 예약/할 일·날짜 삭제·전체 본문 검색·수동 ZIP은 C의 기본 완료 조건에 추가하지 않음 |

예전 U-C1~U-C8은 이 표로 대체한다. 기존 호환 동작을 다시 승인받는 8개 선행 질문으로 작업을 막지 않는다.
