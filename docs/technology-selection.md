# travel-app 저장 방식·기술 선정안

작성일: 2026-10-21 · 상태: 기술 검토안 v0.1 · 개발전략 3단계

> 2026-10-22 구현 갱신: P-01~P-05에 이 선정안을 적용했다. 설치 버전/실행 계약은 [P-01](p01-contracts.md), 저장/추출/화면/현장 검증은 [최신 인계](handoff.md)와 단계별 보고서를 따른다. 아래의 ‘미설치/미구현’은 원래 검토 시점 기록이다. 전체 백업/복원·실제 원천·실기기 검증까지 완료한 것은 아니다.

## 1. 선정 결과와 적용 범위

**여행 데이터는 브라우저의 IndexedDB에 저장하고 Dexie로 조회·트랜잭션을 관리한다. React·TypeScript·Vite로 여행과 무관한 공통 프로그램을 만들고, 기존 원천은 별도 추출·검증 도구로 DB에 가져온다.** SP-FR은 첫 데이터셋이며 다른 여행도 같은 프로그램을 사용한다.

이는 확정 요구를 충족하기 위한 작성자의 기술 선정안이다. 사용자 정책의 추가 합의나 설치·구현 완료를 의미하지 않는다. 이번에는 앱 코드·의존성·DB·환경·원본을 변경하지 않았다. 물리 스키마·명령·패키지 계약은 다음 단계에서 정한다.

입력 문서: [목표·완료 기준](goal-and-migration-criteria.md), [이행표](migration-inventory.md), [공통 구조](target-architecture.md), [원천·DB·화면 대응](content-db-mapping.md). 현재 코드의 구조와 검사 이력은 [프로토타입 모델](data-model.md), [인수인계](handoff.md)에 별도로 있다.

## 2. DB 대안 비교

평가 기준은 오프라인 현장 조회·입력, 본문·첨부를 포함한 여행별 독립 데이터, 원자 저장·충돌 검사, 다른 여행으로의 재사용, 초기 운영 복잡도다. SQL 사용 자체나 기존 프로토타입 유지 자체를 목적에 두지 않는다.

| 대안 | 이 요구에 맞는 점 | 추가 비용·조건 | 판단 |
|---|---|---|---|
| IndexedDB + Dexie | 브라우저에서 구조화 데이터·Blob·인덱스·트랜잭션 사용. 서버 없이 오프라인 저장 가능. 현재 저장 검증 경험 재사용 | SQL JOIN/FK 대신 명시적 조회·참조 검증 필요. 기기·브라우저·origin별 DB, 용량·삭제·복구 관리 필요 | **초기 선정**. 여행별 조회 단위를 나누고 성능·용량을 대표 구간에서 확인 |
| SQLite WASM + OPFS | SQL·관계형 제약과 SQLite 생태계 활용 가능 | WASM/Worker/VFS·복수 탭 잠금과 브라우저 조건 검토 추가. VFS별 헤더 조건이 다르고 브라우저 저장 공간 제약도 남음 | 초기 보류. 실제 관계 조회·성능 요구가 Dexie 설계로 충족되지 않을 때 비교 실측 |
| Node 서버 + SQLite | 개인 서버의 중앙 DB·파일 관리에 적합한 후보 | 휴대폰 오프라인에는 로컬 DB·동기화가 추가로 필요. 서버 가용성·접속·인증·운영 위치 결정 필요 | 서버 중심·다중 기기 요구를 확정하면 재검토 |
| 서버 PostgreSQL | 중앙 저장·여러 클라이언트의 동시 접근에 적합한 후보 | 오프라인 복제·충돌 해결은 별도 설계. 호스팅·인증·운영 범위 추가 | 현재 범위에서 도입하지 않음. 자동 동기화·공유 필요가 확인되면 검토 |

IndexedDB는 구조화 데이터와 파일/Blob을 저장하는 트랜잭션 DB이며 동일 origin 단위로 접근한다. Dexie는 여러 테이블을 함께 쓰는 트랜잭션을 제공한다. 위 적합성 판단은 그 기능과 프로젝트 요구를 비교한 설계 판단이다. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [Dexie 트랜잭션](https://dexie.org/docs/Dexie/Dexie.transaction()).

SQLite의 `opfs` VFS는 SharedArrayBuffer와 COOP/COEP 헤더 조건이 있고, `opfs-sahpool` 등은 다른 조건·동시 접근 특성을 가진다. 모든 SQLite WASM 구성이 같은 헤더를 요구한다고 일반화하지 않는다. 서버 SQLite·PostgreSQL은 DB 서버 선택만으로 모바일 오프라인 동기화를 제공하지 않는다. [SQLite 브라우저 영속 저장](https://sqlite.org/wasm/doc/trunk/persistence.md), [SQLite 적용 범위](https://sqlite.org/whentouse.html), [PostgreSQL 서버 구조](https://www.postgresql.org/docs/current/tutorial-arch.html).

### 로컬 DB 선택에 따라 필수로 설계할 것

- **정본의 위치:** 이행 후 편집 기준은 사용 중인 기기의 travel-app DB다. SP-FR 원본은 대조 자료다. 휴대폰·PC에 각각 가져오면 독립 사본이며 자동 동기화되지 않는다. 별도 기기로 옮기려면 검증된 내보내기·가져오기 절차를 사용한다. 이 전달 절차를 양방향 병합으로 설명하지 않는다.
- **origin 유지:** 개발 5173, 미리보기 4173, 향후 HTTPS 서비스 주소는 서로 다른 DB가 될 수 있다. 주소·브라우저를 바꿀 때 데이터가 따라온다고 가정하지 않고 이전 origin에서 백업 후 새 origin에서 복원한다. 사용자에게 데이터의 저장 위치와 마지막 백업 상태를 보여 준다.
- **저장 공간·삭제:** `navigator.storage.estimate()`로 예상 여유를 확인하고 영속 저장을 요청할 수 있지만 승인·보존을 보장하지 않는다. 저장 실패는 성공으로 표시하지 않는다. 사용자의 사이트 데이터 삭제·기기 분실까지 대비하려면 DB 밖에 보관한 백업이 필요하다. [MDN 저장 공간·삭제 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- **원자성:** 참조·기준 revision 검사, 새 콘텐츠/계획 revision, 현재 포인터, 영수증을 한 DB 트랜잭션에 묶는다. 네트워크·압축·대용량 해시 계산은 트랜잭션 밖에서 준비한다. 첨부 staging과 활성화 실패 시 노출/정리 규칙은 물리 계약에서 정한다.
- **조회 크기:** 여행 하나의 전체 본문·첨부·모든 이력을 매번 역직렬화하는 현재 단일 aggregate 구조를 최종 구조로 유지하지 않는다. 논리 D-01~23을 필요한 object store·복합 키·인덱스와 읽기 모델로 구체화한다. 논리 컬렉션 수와 물리 store 수는 같을 필요가 없다.

## 3. 앱·본문 기술의 적용 방식

### 공통 앱과 PWA

React·TypeScript·Vite는 현재 프로젝트 기반을 활용한다. 이 요구에는 서버 렌더링이 필수적이지 않아 Next.js 전환의 이점보다 구조 변경 비용이 크다고 판단했다. 화면은 선택한 여행 DB를 실행 시 조회한다. 정적으로 호스팅할 수 있는 앱 번들과, 사용자 입력으로 바뀌는 DB 데이터를 구분한다. **새 여행 추가·본문 수정은 데이터 저장이며 앱 재빌드 절차가 아니다.** [Vite 빌드·정적 호스팅](https://vite.dev/guide/build.html).

Service Worker는 공통 앱 셸을 설치한다. 개인 여행 데이터·첨부를 빌드 프리캐시에 넣지 않는다. 오프라인 이용 가능 표시는 필요한 본문·첨부의 로컬 존재와 해시 검사를 기준으로 한다. 외부 지도·출처 링크의 온라인 기능까지 오프라인 완료로 세지 않는다. 업데이트는 알림 후 안전하게 전환하며 작성 중 폼을 강제로 새로고침하지 않는다. 앱/DB 업그레이드는 기존 저장소 삭제로 처리하지 않는다. [Vite PWA 업데이트 알림](https://vite-pwa-org.netlify.app/guide/prompt-for-update.html).

Zod는 브라우저·Node에서 같은 패키지/명령 입력 계약을 검증한다. 타입 검사만으로 외부 JSON의 유효성을 보장하지 않는다. 여행 간 잘못된 참조, 복합 식별자, 과거 revision 고정, 명령 충돌은 저장 계층의 별도 도메인 검사다. Temporal은 현재 의존성을 유지하되 날짜만/현지 시각/미정/확정 instant를 구분하는 TimeSpec을 구현한다. [Zod 실행 시 검증](https://zod.dev/basics).

### 본문 표시·편집

본문은 섹션별 Markdown과 순서·제목·사실/링크/첨부 바인딩을 데이터로 저장한다. 표·목록 등은 react-markdown과 remark-gfm으로 표시하고, 기존 본문 편집은 섹션별 텍스트 입력과 미리보기로 시작한다. 풍부한 문서 작성기 도입 여부는 후속 기능과 별도로 판단한다. [react-markdown](https://github.com/remarkjs/react-markdown), [remark-gfm](https://github.com/remarkjs/remark-gfm).

기존 `{{fact:…}}`, 장소 링크, 지역 가이드, 첨부 참조는 명시적 토큰/노드와 공통 컴포넌트로 처리한다. 임의 JavaScript·Python·MDX를 본문 데이터에서 실행하지 않는다. 일반 raw HTML은 표시 경로에서 허용하지 않으며 원본에 있으면 지원 노드로 변환하거나 미해결 이행 항목으로 기록한다. 원문을 보관했다는 이유만으로 표시 동등성을 통과시키지 않는다. URL 변환·플러그인·컴포넌트에도 허용 규칙을 적용하고 앱이 관리하는 첨부만 로컬 Blob URL로 연다. 라이브러리 기본값만으로 확장 코드의 안전성을 보장하지 않는다. [react-markdown 확장 시 주의점](https://github.com/remarkjs/react-markdown#security).

## 4. 코드 안 콘텐츠까지 추출하는 도구

### 실행 경계

`고정 원본의 읽기 전용 사본 → Python 원천 추출 → 출처/원문/필드 경로가 있는 중간 JSON → TypeScript 정규화·공유 Zod/도메인 검사 → manifest·첨부 패키지 → 앱 미리보기 → 확인 후 저장`

- Python은 이행용 PC 도구다. 프로젝트 내부 `.venv/`와 고정 의존성을 사용할 계획이며 현재 설치·실행하지 않았다. 휴대폰·일상 편집·앱 서버에 Python 설치를 요구하지 않는다.
- `ast`는 기존 Python 코드의 허용된 상수 정의를 읽고, `openpyxl`은 XLSX를 읽는다. JSON/Markdown/미디어도 파일별 목록·해시·원천 경로를 함께 남긴다. 원본 코드의 renderer/build/loader 모듈을 import하거나 실행하지 않는다. 특히 원본 파일을 재생성할 수 있는 빌드 경로를 호출하지 않는다.
- **새 앱 의미 규칙은 TypeScript에 둔다.** Python 출력은 원천 사실을 담은 중간 형식이다. 안정 ID 부여, 중복·우선순위 판정, TimeSpec 변환, 참조 해결, 재가져오기 기준 B, 앱 패키지의 유효성은 공유 계약으로 처리한다. 두 언어에 같은 도메인 검증을 따로 작성하지 않는다.

Python을 추가하는 이유는 원천에 Python 코드와 XLSX가 함께 있기 때문이다. Node 도구만 사용하는 대안도 있지만 Python AST 파서와 별도 XLSX 라이브러리를 추가 검토해야 한다. 이행 도구에 한정한 두 실행환경이 원천 특성에 맞는다고 판단했다. pandas나 원본 정적 사이트 빌드 환경 전체를 새 앱에 가져오지 않는다.

### 추출 규칙

| 원천 | 처리 계획 | 미해결 시 처리 |
|---|---|---|
| 코드의 예약 목록·국가 안내·언어 추천 등 | 고정 파일의 허용된 이름/AST 위치에서 문자열·숫자·목록·사전 등 리터럴만 추출. 파일 크기·노드 수·깊이 제한과 출처 위치 기록 | 함수 호출·계산식·동적 템플릿은 실행하지 않고 수동 구조화 또는 명시적 변환 규칙 대상으로 보고 |
| XLSX | read-only로 열고 종료 시 닫음. 원래 셀·시트·행 경로 유지. 수식과 저장된 계산값의 존재를 구분 | openpyxl을 수식 계산기로 취급하지 않음. 캐시값 없음·해석 불가 날짜/셀은 미해결 보고, 임의 빈 값/시각으로 확정하지 않음 |
| Markdown·facts·JSON | 본문/토큰/구조화 값·원문과 출처를 추출. 원본의 43일·특정 언어 제약은 SP-FR 어댑터 내부에만 둠 | 알 수 없는 필드·HTML·끊어진 토큰·ID 대응 실패를 미해결 목록으로 남김 |
| 이미지·PDF·지도 등 | 실제 파일과 출력 경로의 대응, 크기·해시·형식·권리/크레딧·용도 연결 수집 | 원본 경로를 앱 URL로 단순 치환하지 않음. 누락/권리 미확인/중복은 보고 후 범위 판단 |

`ast.literal_eval`은 임의 코드를 실행하는 도구는 아니지만 자원 고갈까지 막는 샌드박스는 아니다. 허용 노드·크기 제한을 둔 고정 원본 추출에만 사용한다. XLSX의 `data_only`는 저장된 계산값을 읽는 옵션이며 수식을 계산하지 않는다. [Python 3.12 AST](https://docs.python.org/3.12/library/ast.html#ast.literal_eval), [openpyxl 읽기 모드](https://openpyxl.readthedocs.io/en/stable/optimized.html), [openpyxl load_workbook](https://openpyxl.readthedocs.io/en/stable/api/openpyxl.reader.excel.html).

## 5. 교환·백업 형식과 첨부

이행 패키지와 백업은 같은 도메인 자료형을 활용하되 목적과 포함 범위를 구분한다. 이행 패키지는 원천→대상 대응·추출 보고서가 필요하고, 전체 백업은 앱에서 생긴 과거 revision·실제 기록·변경안·결정·명령 영수증·재가져오기 기준 B까지 복원할 수 있어야 한다. 상세 목록은 [공통 구조](target-architecture.md)의 백업 계약을 따른다. 비밀키·브라우저 캐시·서버 작업 디렉터리는 넣지 않는다.

형식은 버전 있는 JSON manifest·레코드 파일·상대 경로 첨부를 담은 ZIP을 선정한다. 본문과 미디어를 전부 하나의 JSON/base64 문자열로 묶는 방식을 기본으로 삼지 않는다. ZIP은 프로그램/DB 구현에서 분리된 교환 컨테이너이며, 첨부의 의미·무결성·참조는 앱 계약으로 검증한다. 기존 프로토타입 JSON v1 자료는 필요한 경우 별도 어댑터로 받아들이며 새 백업 계약과 호환된다고 가정하지 않는다.

ZIP 읽기/쓰기는 스트림·Worker를 지원하는 `@zip.js/zip.js`를 후보 중 선정했다. 라이브러리의 스트림 지원이 전체 앱의 낮은 메모리 사용을 자동 보장하지는 않는다. 최종 다운로드가 Blob이면 다시 메모리에 모일 수 있다. 파일 크기·압축 해제 총량·항목 수·경로·해시·저장 여유를 검증하고 브라우저별 저장/공유 흐름을 확인한다. 모바일에서 특정 파일 시스템 선택 API 지원을 전제로 하지 않는다. [zip.js 공식 기능·실행환경](https://gildas-lormeau.github.io/zip.js/).

초기 압축·해시·첨부 staging은 활성 데이터 저장 전에 수행한다. 실패한 패키지는 현재 여행을 바꾸지 않아야 한다. 큰 전체 백업이 목표 휴대폰에서 불가능하면 첨부 분할/내보내기 절차를 재설계하고 재검증한다. 미디어를 조용히 누락한 파일을 전체 백업이라고 표시하지 않는다. 패키지의 정확한 경로·분할·한도·해시 계약은 다음 단계에서 정한다.

## 6. 기존 환경 재사용과 변경 예정

현재 `package.json`·lockfile의 버전은 재사용 출발점이며 최신 버전이라는 주장이 아니다. Node 24.13.1/프로젝트 범위 `>=24.13 <25`, React 19.3.1, TypeScript 7.0.2, Vite 8.3.4, Dexie 4.4.6, Zod 4.6.7, Temporal polyfill 0.5.1, vite-plugin-pwa 2.0.0이 기존 기준이다. 현장 기기의 지원 브라우저 범위는 아직 확정하지 않았다.

| 상태 | 대상 | 후속 처리 |
|---|---|---|
| 기존 구성 재사용 | React/Vite/TypeScript, Dexie·hooks, Zod, Temporal, PWA, Vitest/fake-indexeddb/Playwright, Node AI 서버 | 최종 모델에 맞게 재설계. 현재 단일 aggregate·부분 일정 importer·정확한 시각 필수 조건은 유지하지 않음 |
| 추가 선정, 미설치 | react-markdown, remark-gfm, @zip.js/zip.js | 구현 착수 시 기존 버전과 peer/빌드/브라우저 호환 확인 후 정확 버전·lockfile 고정. 웹 문서의 기능만으로 설치 버전 검증 완료라고 하지 않음 |
| 새 이행 도구, 미설정 | 프로젝트 전용 Python 3.12 계열·openpyxl, 필요 시 원천 JSON Schema 검사 | 설치 가능 버전·의존성 고정과 읽기 전용 샘플 추출 검증을 별도 수행. 다른 프로젝트/전역 Python 환경을 바꾸지 않음 |
| 후속 제품·운영 결정 | AI 서버 실행 위치·인증·휴대폰 HTTPS 접속, 호스팅/공개 범위, 자동 동기화 여부 | 현재 기술 선정으로 공개 배포나 중앙 정본 DB 도입까지 승인된 것으로 취급하지 않음 |

OpenAI 키의 저장·실 API 검증은 과거 프로토타입 이력이다. 이번 단계에서 새 키를 만들거나 유료 실행하지 않았다. PC loopback 서버가 휴대폰 현장 접속까지 해결한 것으로 보고하지 않는다.

## 7. 대표 구간에서 검증할 선택 조건

다음은 구현 후의 통과 조건이며 이번에 실행한 검사 결과가 아니다.

| ID | 검증할 시나리오 | 선택을 유지할 근거 |
|---|---|---|
| K-01 | 서로 다른 두 가상 여행을 같은 빌드에 가져오고 선택·본문/일정 수정·재로드 | 여행별 소스 코드·HTML 재생성 없이 DB 데이터만으로 화면이 바뀜. 여행 간 편집 격리 |
| K-02 | 본문·facts 토큰·코드 안 예약·미정 시각·첨부가 함께 있는 원천 구간 추출 | P/V 대응, 원문·수량·참조·표시를 대조. 원본 파일 해시 불변. 미해결 항목을 누락으로 숨기지 않음 |
| K-03 | 두 탭 저장·오래된 AI 변경안·중복 명령·첨부 준비 중 실패 | 한 번의 유효한 원자 적용, 오래된 revision 거부, 부분 콘텐츠/첨부 비노출, 과거 참조 보존 |
| K-04 | 오프라인 재시작·본문 조회·현장 기록·백업, 다른 빈 저장소로 복원 | 모든 필요한 레코드·과거 revision·B·영수증·첨부 바이트/해시와 기록 관계가 복원됨 |
| K-05 | 목표 휴대폰에서 대표·예상 최대 본문/미디어 묶음, 저장 공간 부족·내보내기 취소 | 저장·검색·본문 열기·백업 시간/메모리·오프라인 용량을 실측. 데이터 유실/오성공 표시 없음 |

검사는 공유 계약·변환·저장 규칙을 Vitest/fake-indexeddb로, 실제 브라우저의 저장/오프라인/복원 흐름을 Playwright로 확인한다. Python 추출기는 코드 리터럴·XLSX의 원천 경로/수식 처리에 필요한 작은 표본 검사를 둔다. 자동화된 모바일 화면 크기 검사는 실제 Safari·Android 저장 공간/파일 공유 검증을 대체하지 않는다. 오프라인 본문 편집은 로컬 저장 구조상 검증할 수 있는 기술 제안이지만 제품 범위는 미확정이므로 K-04의 필수 조건에 넣지 않았다.

K-05의 수치 목표·지원 기기/브라우저·전체 첨부 크기는 원천 manifest와 대표 구간 계획에서 정한다. 기존 43일/장소 수/빌드 크기는 과거 조사 단서이며 현재 DB 적재량·휴대폰 가능 용량의 실측값으로 사용하지 않는다.

## 8. 후속 상세 설계

1. D-01~23 → 물리 object store·복합 키·인덱스·업그레이드 규칙, 읽기 단위와 트랜잭션 범위.
2. 원천 중간 형식·정규화 패키지·전체 백업·명령 입력/결과의 버전/참조/시간/한도 계약.
3. 대표 원천 구간과 두 가상 여행의 추출→미리보기→DB→공통 화면→편집→오프라인→복원 검증 계획 및 구현 순서.

후속 산출물은 [저장·교환 계약](storage-and-exchange-contracts.md)과 [대표 구간 계획](pilot-migration-plan.md) v0.1에 작성했다. 물리 스키마·명령·파일 버전/한도와 구현 순서는 검토안이며 아직 실행하지 않았다. 계획 검토를 마친 뒤 프로젝트 전용 의존성 설정과 대표 구간 구현으로 이어간다. 전체 원천 이행·신규 기능 추가·공개 운영을 한 번에 착수하지 않는다.
