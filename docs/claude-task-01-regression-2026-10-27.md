## 4. 세 하위 작업

먼저 관련 기존 assertion을 읽고 `충분 / 일부 / 없음`을 보고한다. 이름이 비슷하다는 이유로 충분하다고 판단하지 않는다.
충분하면 해당 증거를 재사용하고 부족한 검사만 추가한다. 고정 테스트 개수나 중복 코드를 목표로 삼지 않는다.

### T-01a · 숙박 없는 마지막 귀국일

읽기: `tests/fixtures/spfr-pilot.ts`, `tests/spfr-normalize.test.ts`, `src/transfer/spfr-pilot.ts`와 관련 normalizer.
최소 가상 원천으로 마지막 날의 숙박이 없고 날짜/활동은 명시된 사례를 만든다.

- 해당 날짜·일차·원천의 활동 순서가 유지되고 마지막 날이 누락되지 않는지 확인한다.
- 앞날의 숙박·지역을 임의로 상속하거나 없는 숙박을 생성하지 않는지 확인한다.
- 지역이 원천에 명시돼 있으면 그대로 보존하고, 미상일 때는 임의 추정하지 않는다.
- 패키지 생성→읽기 뒤에도 같은 의미·참조를 유지하는지 확인한다. 기대값은 fixture의 명시 값에서 만든다.
- 다른 날의 데이터가 변하지 않았음을 확인한다. 결과 보고서에 assertion 위치와 한계를 적는다.

### T-01b · 하루 안의 복수 지역 이동

가상 원천에서 같은 날짜에 출발·도착 지역과 이동 구간을 명시한다. 원천의 지역 순서/중복 처리 계약을 먼저 읽는다.

- 하루의 복수 지역 참조·도시/이동 의미가 숙박 지역 하나로 축소되지 않는지 확인한다.
- 활동/이동 연결·날짜·순서가 유지되고 없는 방문·시각이 생성되지 않는지 확인한다.
- 패키지 왕복과 repository 조회 결과를 확인하고 다른 날짜·여행에 지역이 섞이지 않는지 검사한다.
- 지역 순서가 의미를 가지지 않는 계약이면 배열 순서 자체 대신 명시된 의미·연결을 비교한다.

### T-01c · 같은 revision 값의 다른 가이드와 Fact

읽기: `src/content/Guide.tsx`, `src/content/markdown.ts`, 관련 Fact 계약·repository 명령,
`tests/content-repository.test.ts`, `tests/e2e/content.spec.ts`, `tests/fixtures/`의 콘텐츠 factory.
동일 여행에서 서로 다른 가이드가 동일한 revision 문자열(예: `r1`)을 가진 가상 사례를 만든다.
각 가이드는 독립 Fact를 참조하되 같은 본문 토큰 이름을 사용해 잘못된 키/캐시 재사용을 드러낸다.

- 각 가이드가 처음부터 자기 Fact 값·확인 상태를 표시하는지 검사한다.
- 기존 명령으로 A의 Fact만 새 revision으로 바꾼 뒤, 현재 A 표시가 갱신되고 B 값·상태는 유지되는지 검사한다.
- A→B→A 이동·재로드 뒤에도 같은 결과인지 실제 렌더된 텍스트로 확인한다.
- 과거 계획의 고정 context는 이전 Fact를 계속 읽는지 기존 맥락 계약에 따라 확인한다.
- 다른 여행에서 같은 ID/revision/token을 써도 새 값이 섞이지 않는지 확인한다.
- 저장 전후 계획·실제 기록·B의 content head가 유지되는지 비교한다.

T-01c는 단위 검사만으로 UI 캐시/구독 문제를 통과시키지 않는다. PC/모바일 설정에서 렌더 상호작용을 포함한다.
Fact를 바꾸는 공개 UI가 없으면 기존 repository 명령으로 가상 fixture를 갱신하고 조회 UI를 검증한다.
이를 사용자용 Fact 편집 UI 구현이나 실제 여행 편집으로 보고하지 않는다.

## 5. 검사와 눈으로 확인할 산출물

각 하위 단위는 관련 단위 검사를 먼저 실행한다. T-01c는 대상 E2E를 실행한다.
최종 diff가 정리되면 아래를 한 번 실행한다. 새 실패·수정이 생기면 영향 있는 검사부터 재실행한다.

```powershell
$env:COREPACK_HOME = Join-Path (Get-Location) '.cache/corepack'
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) '.cache/ms-playwright'
pnpm run check:deferred
```

`check:deferred`는 check(포맷·린트·단위·타입·빌드)→E2E→pilot 순서로 실행하고 실패 시 멈춘다.
4173 preview 재사용은 소유 확인 후에만 `TRAVEL_APP_REUSE_PREVIEW=1`로 허용한다.
이전 Codex 기준은 단위152개·E2E48개·pilot 통과이며 이번 변경의 성공으로 재사용하지 않는다.
sandbox 권한 실패는 제품 결함과 구분하고 필요한 정상 권한 경로로 재검사한다. 미실행을 성공으로 표시하지 않는다.

산출물은 다음과 같다.

1. 사람이 읽을 수 있는 세 사례의 fixture·테스트 코드, assertion과 대응한 결과표.
2. 가상 화면에서 날짜/지역 의미와 A/B Fact가 구분되는 PC·모바일 스크린샷 및 콘솔 오류 확인.
   기존 화면 로딩 도구를 재사용한다. 스크린샷만을 위해 제품 코드·공개 샘플·영구 서버를 추가하지 않는다.
3. Codex/사용자가 동일 결과를 볼 수 있는 명령·페이지/여행/가이드 선택·기대 문구를 결과 보고서에 기재한다.
   자동 생성한 임시 프로필의 경로·생존 여부를 명시한다. URL만으로 DB가 공유된다고 안내하지 않는다.
4. 검사 exit code·로그 경로·제출 커밋과, 실제 원천/실기기/API를 검사하지 않았다는 범위 표시.

## 6. 실패·범위 재검토 조건

- 제품 코드 결함이 재현되면 실패 테스트/가상 화면·예상/실제·원인 후보·최소 수정 파일을 제출한다.
  실패를 피하려고 fixture를 약화하거나 제품 코드를 조용히 수정하지 않는다. Codex가 수정 지시를 발행한다.
- 새 근거 없는 반복 수정 대신, 다른 접근 두 번에도 원인이 불명확하면 증거와 가설을 제출한다.
- 스키마/백업 계약·데이터 이전·새 의존성·인증/배포 변경이 필요하면 해당 하위 단위를 멈춘다.
- 실패한 하위 단위는 `수정 요청`으로 남기고 독립적인 나머지는 계속할 수 있다.
- 검증되지 않은 diff와 실패 증거는 로컬에서 보존한다. 공개 범위/검사 상태를 명확히 하지 않은 채 push하지 않는다.

## 7. 커밋·push와 결과 제출

성공한 T-01a/b/c를 각각 검토 가능한 테스트 커밋으로 나누고 보고 문서는 별도 커밋으로 둔다.
공통 fixture 변경의 의존 순서를 밝히며, 기존 파일 전체 포맷·자동 린트 수정·구조 리팩터링을 섞지 않는다.
`git add .` 대신 이번 파일을 명시한다. 실제 자료/키/임시 증거가 staged에 없는지 diff를 읽고 확인한다.
현재 브랜치와 원격 상태를 확인해 기존 단위별 push 지시를 따른다. 강제 push·태그·릴리스는 만들지 않는다.
이 범위의 tests/docs만 변경하면 Pages 대상 경로를 바꾸지 않는다. 예상 밖 배포가 보이면 추가 동작을 멈추고 보고한다.
원격 CI는 해당 커밋의 실제 결과를 확인한 경우에만 성공으로 적는다.

`docs/claude-task-01-result.md`와 최종 응답에 아래 내용을 제출한다.

최종 응답은 20줄·2,000자 이내로 아래 항목을 요약한다. 보고서 첫머리에도 같은 짧은 요약/증거 색인을 둔다.
상세 분석·전체 로그·중간 출력은 별도 로컬 파일로 분리하고 필요할 때 읽을 수 있는 경로를 적는다.
Codex가 전체 대화나 모든 로그를 다시 읽지 않아도 변경 범위·성공/실패·잔여 위험을 판단할 수 있게 작성한다.
자율 작업에 필요한 조사·추론·검사는 Sonnet이 충분히 수행한다. 막연한 토큰 소모를 위해 무관한 작업을 추가하지 않는다.

| 항목 | 제출 내용 |
|---|---|
| 실행 기준 | 시작/종료 HEAD·브랜치, 확인 가능한 Claude 모델 버전, 시작 dirty/포트 상태 |

| 산출물 | 가상 화면/스크린샷 위치, 재현 명령과 확인 동작·기대 문구 |
| Git | 커밋별 목적/해시·push 대상/성공 여부, 원격 CI 링크/상태 또는 미확인 |

Claude는 자신의 검사 통과만 기록한다. Codex 검토는 `대기`, 사용자 확인은 `검토 준비`로 제출한다.
Codex는 고정된 제출 커밋에서 코드/diff·assertion·가상 fixture 독립성을 검토하고 필요한 검사를 재실행한다.
이후 사용자에게 실제 산출물·확인 동작을 제시한다. T-01 통과를 G2/G2′/G3 전체 통과로 확대하지 않는다.
