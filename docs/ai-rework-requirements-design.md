## 1. 배경과 문제

travel-app은 개인용 여행 앱이다(계획·준비 → 현장 기록 → 회고). 브라우저 안 DB(IndexedDB, 기기 안에 저장되는 저장소)에 여행을 보관하고 GitHub Pages로 배포한다. AI는 Cloudflare Worker(작은 서버)를 거쳐 OpenAI를 호출한다.

현재 AI 방식(D 단계): 앱 안에서 날짜 범위와 요청을 적으면 → 서버가 웹 조사 → **기존 일정의 항목 단위 변경안** 생성 → 사용자가 확인 뒤 적용.

| 관찰(사실) | 출처 |
|---|---|
| 지난 여행은 AI로 고칠 필요가 없다. AI는 **새 여행 계획**에 쓰고 싶다 | 사용자 11/11 |
| 현재 방식은 너무 경직돼 있다 | 사용자 11/13 |
| 요청 원문이 조사에 쓰이지 않아 조사 질문을 사용자가 고쳐야 했다 | C3 2회차 |
| 장소가 연결되지 않은 활동은 조사 대상에서 빠졌다 | CL-42 |
| 변경안이 길이 0 시각·겹침을 만들었고 검증이 통과시켰다 | CL-43 |
| 응답 형식 실패 1회(4회 중) | C3 2회차 |
| 실제 여행 호출 4회 $0.15 — 비용은 문제가 아니었다 | C3 |

해석: 문제는 비용이 아니라 **방식**이다. 계획을 짜는 대화는 범용 챗봇(ChatGPT·Claude)이 더 유연하다. 앱은 계획을 받아 저장·실행·기록하는 쪽에 집중하는 편이 맞다.

## 2. 요건

### 2.1 확정 [확정]

| ID | 요건 |
|---|---|
| R-01 | 계획 작성은 챗봇에서 한다. 챗봇이 **앱이 정한 양식**대로 파일을 만들고, 앱이 그 파일을 읽어 DB에 넣는다 |
| R-02 | 양식 파일은 **md**(마크다운, 제목·표로 된 글 파일)다 |
| R-03 | 가져오기는 **PC와 iPhone(Chrome) 모두**에서 된다 |

| R-05 | 계획 순서는 여행지 → 기간 → 날짜별 일정(방문지·시간·교통) → 숙소 → 식당·교통·예약이 일반적이다. 일정·숙소·식당·교통·예약은 **정해진 순서 없이** 정할 수 있어야 한다 |

## 3. 사용 절차 [제안]

```
[챗봇]  ① 양식 안내문 붙여 넣기 → 대화로 계획 → md 파일 받기
[앱]    ② 파일 가져오기 → ③ 검사·미리보기 → ④ 확인 뒤 저장(새 여행 또는 새 계획 버전)
[앱]    ⑤ 화면에서 직접 고치기 · 세부 자료 채우기
[반복]  ⑥ 앱에서 현재 계획을 md로 내보내기 → 챗봇에서 조정 → ②로
```

- ①의 "양식 안내문"은 앱이 제공한다(복사 단추). 양식 규칙과 빈 양식이 들어 있어 어느 챗봇에서도 같은 형식이 나오게 한다.
- R-05 대응: 파일은 **구역별 부분 가져오기**가 된다. 숙소 구역만 있는 파일은 숙소만 반영한다. 없는 구역은 "변경 없음"이지 "삭제"가 아니다.

## 4. 설계 [제안]

### 4.1 구조

| 구성 | 역할 | 기존 자산 |
|---|---|---|
| 양식 정의 | md 구조·필드·규칙·버전 | 신규 |
| 가져오기 변환기 | md → 내부 계획 연산. 브라우저 안에서 실행(서버·AI 호출 없음) | 신규. `src/transfer`는 SP-FR 원본 전용이라 재사용 범위가 작다 |
| 검사·미리보기 | 형식·날짜·참조 검사, 추가/수정/삭제를 항목별로 표시 | 변경안 화면·검증(`validate.ts`) 재사용 |
| 저장 | 새 여행은 `CreateTrip`, 기존 여행은 변경안(`origin: 'import'`) → 적용 시 새 계획 버전 | 스키마에 `import` 출처가 이미 있다 |
| 내보내기 | 현재 계획 → 같은 양식의 md | 신규 |
| 직접 입력 | 화면에서 날짜·활동·숙소·이동 편집 | C 단계 작성 화면 재사용·보완 |

핵심 성질: 가져오기는 **결정적**이다(같은 파일이면 항상 같은 결과). AI가 변환하지 않으므로 형식 실패·비용·서버 장애가 없고 오프라인에서도 된다. 해석의 어려움은 챗봇 쪽(양식을 지키게 하는 안내문)과 양식 설계로 옮겨 간다.

### 4.2 양식 초안 (v1)

```markdown
# 여행: 삿포로 겨울
- 양식: travel-app-plan/1
- 기간: 2026-12-31 ~ 2027-01-03
- 시간대: Asia/Tokyo

## 일정
### 2026-12-31 삿포로 도착
| ID | 시간 | 제목 | 종류 | 장소 | 메모 | 예약 | 링크 |
|---|---|---|---|---|---|---|---|
|  | 15:00-16:00 | 호텔 체크인 | 숙박 | 스스키노 | | | |
|  | 18:30-20:00 | 저녁: 징기스칸 | 식사 | 다루마 본점 | 대기 가능 | 필요 | https://… |

## 숙소
| ID | 기간 | 이름 | 지역 | 예약 |
|---|---|---|---|---|

## 이동
| ID | 날짜 | 출발 | 도착 | 수단 | 소요 | 메모 |
|---|---|---|---|---|---|---|

## 장소
| 이름 | 지역 | 설명 | 영업시간 | 링크 |
|---|---|---|---|---|
```

| 규칙 | 내용 | 이유 |
|---|---|---|
| 표 중심 | 한 줄 = 한 항목 | 사람이 읽고 고치기 쉽고 기계가 읽기 쉽다 |
| 양식 버전 줄 | 없거나 모르는 버전이면 가져오기 거부 | 양식이 바뀌어도 옛 파일을 잘못 읽지 않는다 |
| ID 칸 | 새 항목은 비움. 내보내기 파일에는 앱이 짧은 ID를 채운다 | 챗봇이 고친 파일을 다시 넣을 때 **어느 항목을 고쳤는지** 맞춘다 |
| 시간 | `HH:MM-HH:MM`, 비우면 "시간 미정" | 길이 0·역전은 검사에서 잡는다 |
| 모르는 칸·구역 | 무시하고 경고 표시 | 챗봇이 덧붙인 내용 때문에 전체가 실패하지 않게 |
| 내부 필드 대응 | 제목→`title`, 종류→`category`, 메모→`summary`, 예약→`reservationText`, 링크→`officialUrl`, 장소→`placeLinks` | 현재 `planItemSchema`와 맞춘다 |

대안 비교:

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. md 표(위 안) | 읽기·고치기 쉬움, iPhone에서 보기 좋음 | 칸 안의 줄바꿈·`|` 문자 처리 필요 | **채택 제안** |
| B. md 안에 JSON 블록 | 기계 해석이 가장 확실 | 사람이 읽고 고치기 어렵다 | 보류 |
| C. 앱이 임의 파일을 AI로 변환 | 사용자가 가장 편함 | 서버·비용·형식 실패가 그대로 남는다 | 사용자 결정으로 제외 |

### 4.3 가져오기 처리

1. 읽기: 파일 선택(PC·iPhone 모두 `파일 선택` 사용). 글자 수·줄 수 상한을 둔다.
2. 해석: 구역·표를 읽어 중간 구조로 만든다. 실패한 줄은 줄 번호와 이유를 모은다.
3. 맞추기: ID가 있으면 그 항목 수정. ID가 없으면 새 항목. **삭제는 기본으로 하지 않는다** — 파일에 없는 기존 항목은 그대로 둔다. "이 날짜를 파일 내용으로 교체"는 미리보기에서 날짜별로 사용자가 고른다.
4. 검사: 기간 밖 날짜, 시간 형식·역전·길이 0, 같은 날 겹침, 없는 ID, 중복 ID, `https` 아닌 링크.
5. 미리보기: 추가·수정·삭제를 항목별로 보여 주고 사용자가 일부만 골라 적용할 수 있다.
6. 저장: 확인 뒤에만 저장. 기존 여행은 새 계획 버전이 생기고 이전 버전은 남는다. 미리보기 중 계획이 바뀌었으면 적용을 막고 다시 맞춘다(기존 revision 검사 재사용).

| 선택 | 내용 | 영향 |
|---|---|---|

| 위험 | 대응 |
|---|---|
| 챗봇이 양식을 조금씩 어긴다(칸 순서, 날짜 형식, 표 깨짐) | 안내문에 규칙·예시 포함, 변환기는 칸 이름으로 읽고 순서에 의존하지 않음, 줄 단위 오류 표시, E0에서 실제 챗봇으로 시험 |

| 파일에 개인 정보(예약 번호 등)가 들어간다 | 파일은 기기 안에서만 처리, 서버 전송 없음. 내보내기 때 예약·현장 기록 포함 여부를 고르게 함 |
| md 안의 스크립트·이상 링크 | 글자로만 표시(HTML 실행 안 함), 링크는 `https`만 허용 |
| 양식이 자주 바뀐다 | 버전 줄로 구분, 옛 버전 읽기는 유지 |

## 7. 수용 기준 초안 [제안]

1. 안내문만 넣은 챗봇 2종이 만든 파일이 수정 없이 가져오기 검사를 통과한다(각 3회 중 3회).
2. PC와 iPhone Chrome에서 같은 파일이 같은 결과로 들어간다.
3. 숙소 구역만 있는 파일을 넣어도 일정이 바뀌지 않는다.
4. 내보내기 → 수정 없이 다시 가져오기 = 변경 0건.
5. 가져오기 적용 뒤 이전 계획 버전을 조회할 수 있다.
6. 길이 0·역전 시각과 기간 밖 날짜가 저장되지 않는다(Q-03 결정에 따름).
7. 네트워크가 끊긴 상태에서 가져오기·직접 입력이 된다.

## 8. 제3자 검토 요청 사항

1. md 표 양식(4.2 A안)이 챗봇 출력으로서 충분히 안정적인가. JSON 블록(B안)이나 혼합이 더 나은가.
2. ID 왕복과 "삭제는 기본으로 하지 않음"(4.3의 3)이 항목 맞추기 문제를 충분히 푸는가. 빠진 경우가 있는가.
3. 숙소·이동을 변경안에 넣기 위해 저장 계약을 넓히는 것과 `ChangePlan`을 쓰는 것 중 어느 쪽이 안전한가.
4. 양식 필드가 과하거나 부족한가(개인용 기준). 예: 비용, 예약 번호, 좌표.
