## 1. 배경과 문제

travel-app은 개인용 여행 앱이다(계획·준비 → 현장 기록 → 회고). 브라우저 안 DB(IndexedDB, 기기 안에 저장되는 저장소)에 여행을 보관하고 GitHub Pages로 배포한다. AI는 Cloudflare Worker(작은 서버)를 거쳐 OpenAI를 호출한다.

현재 AI 방식(D 단계): 앱 안에서 날짜 범위와 요청을 적으면 → 서버가 웹 조사 → **기존 일정의 항목 단위 변경안** 생성 → 사용자가 확인 뒤 적용.

| 관찰(사실) | 출처 |
|---|---|
| 지난 여행은 AI로 고칠 필요가 없다. AI는 **새 여행 계획**에 쓰고 싶다 | 사용자 11/11 |
| 현재 방식은 너무 경직돼 있다 | 사용자 11/13 |
| 요청 원문이 조사에 쓰이지 않아 조사 질문을 사용자가 고쳐야 했다 | C3 2회차 |
| 장소가 연결되지 않은 활동은 조사 대상에서 빠졌다 | CL-42 |
| 변경안이 길이 0 시각·겹침을 만들었고 검증이 통과시켰다 | CL-43 |
| 응답 형식 실패 1회(4회 중) | C3 2회차 |
| 실제 여행 호출 4회 $0.15 — 비용은 문제가 아니었다 | C3 |

해석: 문제는 비용이 아니라 **방식**이다. 계획을 짜는 대화는 범용 챗봇(ChatGPT·Claude)이 더 유연하다. 앱은 계획을 받아 저장·실행·기록하는 쪽에 집중하는 편이 맞다.

## 3. 사용 절차 [제안]

```
[챗봇]  ① 양식 안내문 붙여 넣기 → 대화로 계획 → md 파일 받기
[앱]    ② 파일 가져오기 → ③ 검사·미리보기 → ④ 확인 뒤 저장(새 여행 또는 새 계획 버전)
[앱]    ⑤ 화면에서 직접 고치기 · 세부 자료 채우기
[반복]  ⑥ 앱에서 현재 계획을 md로 내보내기 → 챗봇에서 조정 → ②로
```

- ①의 "양식 안내문"은 앱이 제공한다(복사 단추). 규칙과 빈 양식이 들어 있어 어느 챗봇에서도 같은 형식이 나오게 한다.
- R-05 대응: 파일은 **구역별 부분 가져오기**가 된다. 숙소 구역만 있는 파일은 숙소만 반영한다. 없는 구역·없는 항목은 "변경 없음"이지 "삭제"가 아니다. 새 여행도 일정 없이 숙소 구역만으로 시작할 수 있다.
- ⑤ 직접 입력은 기존 편집 화면의 저장 방식(저장 단추 → 새 계획 버전, 이전 버전 보존)을 그대로 쓴다.

## 4. 설계 [제안]

### 4.1 구조

| 구성 | 역할 | 기존 자산 |
|---|---|---|
| 양식 정의 | md 구조·필드·규칙·버전 | 신규 |
| 가져오기 변환기 | md → 내부 계획 연산. 브라우저 안에서 실행(서버·AI 호출 없음) | 신규. `src/transfer`는 SP-FR 원본 전용 |
| 검사·미리보기 | 형식·날짜·참조 검사, 추가/수정/삭제를 항목별로 표시 | 검증(`validate.ts`) 재사용 |
| 저장 | 새 여행은 `CreateTrip`, 기존 여행은 **`ChangePlan` 명령 1회**(활동·숙소·이동을 한 번에, 전부 저장되거나 전부 안 되거나) | 사실: `ChangePlan`은 활동·숙소·이동 연산과 기준 계획 버전 검사를 이미 가진다. 변경안(`proposal`)은 활동 연산만 받는다 |
| 내보내기 | 현재 계획 → 같은 양식의 md | 신규 |
| 직접 입력 | 화면에서 날짜·활동·숙소·이동 편집 | C 단계 작성 화면 재사용·보완 |

용어를 나눈다(검토 15 반영).
- **해석은 결정적**이다: 같은 파일은 언제나 같은 중간 구조로 읽힌다. AI가 변환하지 않으므로 형식 실패·비용·서버 장애가 없고 오프라인에서도 된다.
- **적용 결과는 현재 DB 상태에 따라 달라진다.** 그래서 반복 가져오기의 중복 방지(§4.3)를 따로 규정한다.

| 규칙 | 내용 |
|---|---|
| 정본 | 표가 유일한 정본이다. 표 밖의 글은 읽지 않는다(챗봇의 설명 문장 허용) |
| 양식 버전 | `양식:` 줄이 없거나 모르는 버전이면 가져오기 거부 |
| 여행ID·기준 | 내보내기 때 앱이 넣는다. 다시 가져올 때 여행과 기준 버전을 확인한다(§4.3) |
| ID | 새 항목은 비움. 내보내기 파일에는 앱이 넣는다(내부 ID의 앞부분, 여행 안에서 유일). 챗봇은 ID를 고치지 않는다 |
| 한 줄 = 한 항목 | 칸 안 줄바꿈 금지. 칸 안의 `|`는 `\|`로 쓴다 |
| 열 개수 | 제목 줄과 열 개수가 다른 줄은 **오류**다. 무시하고 넘어가지 않는다. 오류가 하나라도 있으면 그 구역 전체를 적용에서 뺀다 |
| 모르는 열·구역 | 읽지 않고 경고로 보여 준다(값은 버리지 않고 "가져오지 않음"으로 표시) |
| 빈 칸 | ID 없는 줄: 값 없음. **ID 있는 줄: 그 줄이 그 항목의 전체 값**이므로 빈 칸은 "비움"이다. 미리보기에 "값 지워짐"으로 표시한다 |
| 시간 | `HH:MM-HH:MM`. 자정을 넘기면 끝에 `(+1)`. 비우면 "시간 미정"이고 표의 줄 순서가 순서다. 시작만 있으면 `HH:MM` |
| 시간대 | 여행 기본 시간대를 쓴다. 날짜 제목 줄에 `(시간대: Europe/Paris)`를 붙이면 그날만 다르게 본다 |
| 숙소 | 체크인·체크아웃은 날짜다. 박 수 = 체크아웃 − 체크인 |
| 종류 | 권장값: 관광·식사·이동·숙박·쇼핑·기타. 다른 값도 그대로 저장한다 |
| 예약 칸 | **메모 글**이다(`reservationText`). 예약 기록(booking) 자체는 바꾸지 않는다 |
| 삭제 | 지우려는 기존 항목은 `## 삭제` 구역에 ID로만 적는다. 제목은 사람 확인용이다. 다른 방법으로는 삭제되지 않는다 |
| 내부 필드 대응 | 제목→`title`, 종류→`category`, 메모→`summary`, 예약→`reservationText`, 링크→`officialUrl`, 장소→`placeLinks`, 이동→`planLeg`, 숙소→`planStay` |

사실 확인(코드): 내부 시간 모델은 시작·종료가 각각 날짜·현지 시각·시간대를 가진다. 자정 넘김과 날짜별 시간대는 저장 계약 변경 없이 표현된다. 야간 일정 허용(12시간 상한)은 기존 사용자 결정이다.

### 4.3 가져오기 처리

| 단계 | 내용 |
|---|---|
| 1 읽기 | 파일 선택. 글자 수·줄 수 상한. 파일 내용의 지문(해시)을 계산한다 |
| 2 해석 | 구역·표 → 중간 구조. 오류는 줄 번호와 이유를 모은다. 오류가 있는 구역은 통째로 적용 대상에서 뺀다 |
| 3 대상 확인 | **여행ID가 있으면** 그 여행에만 적용한다(다른 여행이면 거부). **기준이 현재 계획보다 오래됐으면 적용을 막고** "다시 내보내서 작업하세요"를 안내한다. 자동 병합은 하지 않는다 |
| 4 맞추기 | ID 있는 줄 = 그 항목 수정(없는 ID·중복 ID는 오류). ID 없는 줄 = 새 항목 후보. 단, 같은 날짜·같은 제목(숙소는 이름·체크인, 장소는 이름·지역)의 기존 항목이 있으면 **기본 선택은 "건너뜀"** 이고 사용자가 추가/기존 항목 수정/건너뜀 중 고른다. 같은 지문의 파일을 같은 여행에 다시 넣으면 먼저 알린다 |
| 5 삭제 | `## 삭제` 구역의 ID만 삭제 후보다. 파일에 없는 항목은 그대로 둔다. "날짜를 파일 내용으로 교체" 기능은 **두지 않는다** |
| 6 검사 | 기간 밖 날짜, 시간 형식·역전·길이 0·겹침(Q-03), `https` 아닌 링크, 이동의 출발·도착이 가리키는 활동, 숙소 체크아웃 ≤ 체크인 |
| 7 미리보기 | 추가·수정(바뀐 칸과 지워지는 값)·삭제(제목·개수)·건너뜀·오류를 항목별로 보여 준다. 사용자가 일부만 고를 수 있다 |
| 8 재검증 | **고른 결과 전체**를 다시 검사한다. 참조가 끊기면(예: 삭제한 활동을 가리키는 이동) 적용하지 않는다 |
| 9 저장 | 확인 뒤 `ChangePlan` 1회로 저장한다. 새 계획 버전이 생기고 이전 버전은 남는다. 실패하면 아무것도 바뀌지 않는다. 사유에 "가져오기: 파일 이름·지문"을 남긴다 |

장소: 장소는 계획이 아니라 콘텐츠(`place`)라 저장 명령이 다르다. 순서는 ① 새 장소 생성 → ② `ChangePlan`. ①만 되고 ②가 실패하면 일정에 연결되지 않은 장소가 남는다(계획은 그대로다). 다시 가져오면 이름·지역 일치로 그 장소를 연결 후보로 제안한다. 기존 장소와의 **자동 병합은 하지 않는다**. 내보내기 파일의 장소 표에는 ID가 들어간다.

한계(알고 가는 것): 미리보기 상태는 저장되지 않는다. 미리보기 도중 앱을 닫으면 처음부터 다시 한다. 변경안(`proposal`) 기록을 남기려면 변경안 스키마에 숙소·이동 연산을 넣어야 하는데, 저장 계약 변경이라 1차에서는 하지 않는다.

### 4.4 세부 자료 채우기 (Q-01 단계안)

| 단계 | 방법 | 추가 개발 | 비고 |
|---|---|---|---|
| 1 | 화면에서 직접 입력 | 작음(기존 편집 화면) | R-04 |
| 2 | 챗봇이 `장소` 구역·메모·링크 칸을 채운 md를 다시 가져오기 | §4.3과 같은 경로 | 추가 비용 없음 |
| 3 | 앱 안 AI가 선택한 항목만 조사 | 기존 Worker 재사용 | CL-42·43 해결이 선행. 1·2를 써 본 뒤 결정 |

### 4.5 기존 AI 기능 (Q-02 선택지)

| 선택 | 내용 | 영향 |
|---|---|---|
| 유지·동결 | 지금 상태로 두고 확장하지 않는다 | 알려진 문제(CL-42·43)가 있는 변경안 적용 경로도 남는다 |
| 유지하되 적용 차단 | Worker는 두고, 앱의 AI 변경안 **적용**만 막는다(조사 결과 보기는 가능) | 검토 9의 제안. 작은 화면 수정 필요 |
| 제거 | Worker·패스키·AI 패널을 뗀다 | 가장 단순. 되돌리려면 재배포 |

제안: 1차 구현 동안은 유지·동결. 적용 차단은 Q-03 결정(길이 0 거부)을 기존 AI 검증에도 넣으면 필요가 줄어든다. 새 여행 1건에 파일 방식을 써 본 뒤, 모자랐던 기능과 AI를 쓴 횟수를 보고 결정한다.
