## 1. 배경과 문제

travel-app은 개인용 여행 앱이다(계획·준비 → 현장 기록 → 회고). 브라우저 안 DB(IndexedDB, 기기 안에 저장되는 저장소)에 여행을 보관하고 GitHub Pages로 배포한다. AI는 Cloudflare Worker(작은 서버)를 거쳐 OpenAI를 호출한다.

현재 AI 방식(D 단계): 앱 안에서 날짜 범위와 요청을 적으면 → 서버가 웹 조사 → **기존 일정의 항목 단위 변경안** 생성 → 사용자가 확인 뒤 적용.

| 관찰(사실) | 출처 |
|---|---|
| 지난 여행은 AI로 고칠 필요가 없다. AI는 **새 여행 계획**에 쓰고 싶다 | 사용자 11/11 |
| 현재 방식은 너무 경직돼 있다 | 사용자 11/13 |
| 요청 원문이 조사에 쓰이지 않아 조사 질문을 사용자가 고쳐야 했다 | C3 2회차 |
| 장소가 연결되지 않은 활동은 조사 대상에서 빠졌다 | CL-42 |
| 변경안이 길이 0 시각·겹침을 만들었고 검증이 통과시켰다 | CL-43 |
| 응답 형식 실패 1회(4회 중) | C3 2회차 |
| 실제 여행 호출 4회 $0.15 — 비용은 문제가 아니었다 | C3 |

해석: 문제는 비용이 아니라 **방식**이다. 계획을 짜는 대화는 범용 챗봇(ChatGPT·Claude)이 더 유연하다. 앱은 계획을 받아 저장·실행·기록하는 쪽에 집중하는 편이 맞다.

## 3. 사용 절차 [제안 — v0.4에서 다시 씀]

원칙(UX 제안 반영): **md 양식은 챗봇과 앱 사이의 교환 형식이고, 사용자는 가능한 한 양식을 의식하지 않는다.** 사용자는 단추 세 개로 일한다. 파일을 직접 다루는 길도 남긴다.

| 시나리오 | 앱에서 | 챗봇에서 | 다시 앱에서 |
|---|---|---|---|
| 0. 계획 준비(선택, §4.8) | 조건·취향 질문에 답하고, 목적지 가이드에서 꼭 포함·관심·제외를 고른다 | (가이드가 없으면) 가이드 요청문을 붙여 넣어 가이드를 받는다 | 고른 결과가 A의 요청서에 들어간다 |
| A. 새 여행 만들기 | **[AI로 계획 만들기]** — 여행지·기간·바라는 점을 적으면 요청문(내 요청 + 양식 안내문)을 만들어 복사 | 붙여 넣고 대화로 계획 → 결과 코드 블록 복사 | **[AI 결과 붙여넣기]** → 미리보기 → 확인 → 새 여행 |
| B. 기존 여행 고치기 | **[AI로 수정하기]** — 현재 계획(여행ID·기준 포함, 규칙 내장) + 수정 요청 틀을 복사. 전체 또는 날짜 범위 | 붙여 넣고 수정 요청 → **바뀐 부분만** 코드 블록으로 받기 | **[AI 결과 붙여넣기]** → 바뀐 것 비교 → 확인 → 새 계획 버전 |
| C. 하루·활동 단위로 고치기 | 날짜 화면의 **[AI에게 요청]** — 그 날짜(와 앞뒤 맥락)만 담은 요청문 복사 | 대안 받기 | 붙여넣기 → 고른 변경만 반영 |

- 입력은 두 가지이고 **같은 변환기·같은 검사·같은 미리보기**를 쓴다: ① 글 붙여넣기(기본, 파일 내려받기·찾기가 필요 없어 iPhone에 유리) ② `.md` 파일 선택.
- 붙여 넣을 때마다 최신 계획을 다시 복사해 가므로 "앱에서 고친 것을 챗봇이 모르는" 문제가 줄어든다. 그래도 오래된 기준이면 적용을 막는다(§4.3-3).
- R-05 대응: 구역별 부분 가져오기. 없는 구역·없는 항목은 "변경 없음"이지 "삭제"가 아니다. 새 여행도 숙소 구역만으로 시작할 수 있다.
- 직접 입력은 기존 편집 화면의 저장 방식(저장 단추 → 새 계획 버전, 이전 버전 보존)을 그대로 쓴다.
- **외부로 나가는 정보**: [AI로 수정하기]·[AI에게 요청]은 여행 계획을 사용자가 고른 챗봇 서비스에 붙여 넣게 한다. 복사 전에 무엇이 들어가는지 보여 주고, 예약 메모·현장 기록은 기본으로 넣지 않는다(결정 6).

## 4. 설계 [제안]

### 4.1 구조

| 구성 | 역할 | 기존 자산 |
|---|---|---|
| 양식 정의 | md 구조·필드·규칙·버전 | 신규 |
| 가져오기 변환기 | md 글 → 내부 계획 연산. 브라우저 안에서 실행(서버·AI 호출 없음). **붙여 넣은 글과 파일이 같은 변환기를 쓴다** | 신규. `src/transfer`는 SP-FR 원본 전용 |
| AI 요청문 만들기 | 새 여행 요청문, 현재 계획 + 수정 요청문(전체·날짜 범위)을 만들어 클립보드에 복사. AI를 부르지 않는다 | 신규(§4.6) |
| 검사·미리보기 | 형식·날짜·참조 검사, 추가/수정/삭제를 항목별로 표시 | 검증(`validate.ts`) 재사용 |
| 저장 | 새 여행은 `CreateTrip`, 기존 여행은 **`ChangePlan` 명령 1회**(활동·숙소·이동을 한 번에, 전부 저장되거나 전부 안 되거나). 새 장소는 그 앞의 **별도 승인 단계**(§4.3 장소) | 사실: `ChangePlan`은 활동·숙소·이동 연산과 기준 계획 버전 검사를 이미 가진다. 변경안(`proposal`)은 활동 연산만 받는다. 장소와 계획을 한 번에 저장하는 일반 명령은 지금 없다 |
| 내보내기 | 현재 계획 → 같은 양식의 md | 신규 |
| 직접 입력 | 화면에서 날짜·활동·숙소·이동 편집 | C 단계 작성 화면 재사용·보완 |

용어를 나눈다(검토 15 반영).
- **해석은 결정적**이다: 같은 파일은 언제나 같은 중간 구조로 읽힌다. AI가 변환하지 않으므로 형식 실패·비용·서버 장애가 없고 오프라인에서도 된다.
- **적용 결과는 현재 DB 상태에 따라 달라진다.** 그래서 반복 가져오기의 중복 방지(§4.3)를 따로 규정한다.

| 규칙 | 내용 |
|---|---|
| 정본 | 표가 유일한 정본이다. 표 밖의 글은 읽지 않는다(챗봇의 설명 문장 허용) |
| 양식 버전 | `양식:` 줄이 없거나 모르는 버전이면 가져오기 거부 |
| 여행ID·기준계획·기준revision | 내보내기 때 앱이 넣는다. 문법은 `- 이름: 값` 한 줄씩이고 값은 **내부 ID 그대로**(기준revision은 정수)다. 셋 중 하나라도 있으면 셋 다 있어야 하고, 형식이 틀리면 거부한다(§4.3) |
| ID | 새 항목은 비움. 내보내기 파일에는 앱이 **내부 ID 전체를 그대로** 넣는다(줄인 ID를 쓰지 않으므로 충돌 처리가 필요 없다). 사실: 내부 ID는 영문·숫자와 `._:-`로 된 최대 160자 글자열이다. 챗봇은 ID를 고치지 않는다 |
| 한 줄 = 한 항목 | 칸 안 줄바꿈 금지. 칸 안의 `|`는 `\|`로 쓴다 |
| 열 개수 | 제목 줄과 열 개수가 다른 줄은 **오류**다. 무시하고 넘어가지 않는다. 오류가 있는 **표 하나 전체**를 적용에서 뺀다(일정은 날짜별 표 단위, 나머지는 구역 단위). 오류 표의 일부만 저장하지 않는다 |
| 모르는 열·구역 | 읽지 않고 경고로 보여 준다(값은 버리지 않고 "가져오지 않음"으로 표시) |
| 빈 칸 | ID 없는 줄: 값 없음. **ID 있는 줄: 빈 칸은 "변경 없음"** 이다(부분 수정). 값을 지우려면 칸에 `(비움)`이라고 적는다. 글자 그대로 "(비움)"을 값으로 쓰려면 `\(비움)`. 줄 전체를 통째로 바꾸는 명령은 두지 않는다 |
| 시간 | 허용 표현은 넷뿐이다: 빈 칸(새 줄은 "시간 미정", ID 있는 줄은 변경 없음) · `HH:MM`(시작만) · `HH:MM-HH:MM` · `HH:MM-HH:MM(+1)`(자정 넘김). 그 밖의 표현(끝만 있는 시간, "오후쯤" 등)은 **오류**다. 시간 미정 항목은 표의 줄 순서가 순서다 |
| 시간대 | 여행 기본 시간대를 쓴다. 날짜 제목 줄에 `(시간대: Europe/Paris)`를 붙이면 그날만 다르게 본다. IANA 이름(예: `Asia/Tokyo`)이 아니면 오류다 |
| 숙소 | 체크인·체크아웃은 날짜다. 박 수 = 체크아웃 − 체크인 |
| 종류 | 권장값: 관광·식사·이동·숙박·쇼핑·기타. 다른 값도 그대로 저장한다 |
| 예약 칸 | **메모 글**이다(`reservationText`). 예약 기록(booking) 자체는 바꾸지 않는다 |
| 삭제 | 지우려는 기존 항목은 `## 삭제` 구역에 종류와 ID로 적는다. 종류는 `활동`·`숙소`·`이동`만 된다(**장소는 파일로 지울 수 없다** — 오류). 종류와 ID가 맞지 않으면 오류다. 제목은 사람 확인용이다. 다른 방법으로는 삭제되지 않는다 |
| 규칙 요약 내장 [제안, E0 1회차 반영] | 내보내기 파일의 머리 줄 아래에 "이 파일을 고치는 규칙" 6줄을 인용 글(`> `)로 넣고, 빈 `## 삭제` 표를 끝에 둔다. 안내문 없이 파일만 챗봇에 줘도 규칙이 전달된다. 변환기는 표 밖 글이라 읽지 않는다 |
| 여행 이름 줄 [제안] | 여행ID가 있는 파일의 `# 여행:` 이름은 읽지 않는다(이름 변경은 앱 화면에서만). 모르는 머리 줄(`- 범위:` 등)은 무시하고 경고로 보여 준다 |
| 내부 필드 대응 | 제목→`title`, 종류→`category`, 메모→`summary`, 예약→`reservationText`, 링크→`officialUrl`, 장소→`placeLinks`, 이동→`planLeg`, 숙소→`planStay` |

사실 확인(코드): 내부 시간 모델은 시작·종료가 각각 날짜·현지 시각·시간대를 가진다. 자정 넘김과 날짜별 시간대는 저장 계약 변경 없이 표현된다. 야간 일정 허용(12시간 상한)은 기존 사용자 결정이다.

대안 비교:

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. md 표(위 안) | 읽기·고치기 쉬움, iPhone에서 보기 좋음 | `|`·줄바꿈·열 개수 규칙을 챗봇이 어길 수 있다 | **E0에서 시험** |
| B. md 안의 JSON 코드 블록 하나 | 기계 해석이 가장 확실 | 사람이 읽고 고치기 어렵다 | A가 E0 기준에 못 미치면 전환 |
| C. 표와 JSON을 함께 정본으로 | — | 두 값이 다를 때 판정 불가 | 채택하지 않음(검토 5) |
| D. 앱이 임의 파일을 AI로 변환 | 가장 편함 | 서버·비용·형식 실패가 남는다 | 사용자 결정으로 제외 |

A→B 전환 기준 [제안]: E0에서 챗봇 2종 × 3회 = 6개 파일 중 **수정 없이 통과가 5개 미만**이거나, **조용한 데이터 손실**(오류 표시 없이 값이 빠지거나 바뀜)이 **1건이라도** 있으면 B로 바꾼다. 시험에는 새 여행 작성뿐 아니라 "내보낸 파일에서 메모만 수정"과 "삭제 요청"을 넣는다. 참고 사실: 검토자 AI가 v0.1 규칙만 보고 만든 3박 4일 파일 1개는 표 형식을 지켰다(변환기 시험은 아님).

### 4.3 가져오기 처리

| 단계 | 내용 |
|---|---|
| 1 읽기 | 파일 선택. 글자 수·줄 수 상한. 파일 내용의 지문(해시)을 계산한다(같은 파일을 다시 넣었음을 알리는 **참고 정보**일 뿐 중복 방지 수단이 아니다) |
| 2 해석 | 구역·표 → 중간 구조. 오류는 줄 번호와 이유를 모은다. 오류가 있는 표는 통째로 적용 대상에서 뺀다(일정은 날짜별) |
| 3 대상 확인 | **여행ID가 있으면** 그 여행에만 적용한다(다른 여행·없는 여행이면 거부). **기준계획·기준revision이 현재 값과 다르면 적용을 막고** "다시 내보내서 작업하세요"를 안내한다. 자동 병합은 하지 않는다 |
| 4 맞추기 | ID 있는 줄 = 그 항목 수정(없는 ID·중복 ID는 오류). ID 없는 줄 = 새 항목 후보. 중복 방지의 기준은 ID와 **사용자가 고른 대응**이다. 단, 같은 날짜·같은 제목(숙소는 이름·체크인, 장소는 이름·지역)의 기존 항목이 있으면 **기본 선택은 "건너뜀"** 이고 사용자가 추가/기존 항목 수정/건너뜀 중 고른다. 같은 지문의 파일을 같은 여행에 다시 넣으면 먼저 알린다 |
| 5 삭제 | `## 삭제` 구역의 종류·ID만 삭제 후보다. 파일에 없는 항목은 그대로 둔다. "날짜를 파일 내용으로 교체" 기능은 **두지 않는다** |
| 6 검사 | 기간 밖 날짜, 시간 형식·역전·길이 0·겹침(Q-03), `https` 아닌 링크, 이동의 출발·도착이 가리키는 활동, 숙소 체크아웃 ≤ 체크인 |
| 7 미리보기 | 추가·수정(바뀐 칸과 지워지는 값)·삭제(제목·개수)·건너뜀·오류를 항목별로 보여 준다. **ID는 있는데 바뀌는 칸이 하나도 없는 줄은 "변경 없음"으로 따로 보여 준다**(챗봇이 `(비움)` 대신 칸을 비워 지우기가 반영되지 않은 경우를 사용자가 알아차리게 — E0 1회차 반영). 사용자가 일부만 고를 수 있다 |
| 8 재검증 | **고른 결과 전체**를 다시 검사한다. 참조가 끊기면(예: 삭제한 활동을 가리키는 이동) 적용하지 않는다 |
| 9 저장 | 확인 뒤 `ChangePlan` 1회로 저장한다. 새 계획 버전이 생기고 이전 버전은 남는다. 실패하면 아무것도 바뀌지 않는다. 사유에 "가져오기: 파일 이름·지문"을 남긴다 |

장소(검토 2차 3 반영): 장소는 계획이 아니라 콘텐츠(`place`)라 저장 명령이 다르고, 둘을 한 번에 저장하는 명령은 지금 없다. 그래서 **승인을 둘로 나눈다.**

| 순서 | 내용 | 실패하면 |
|---|---|---|
| ① 장소 단계 | 파일에 새 장소가 있을 때만 나온다. "새 장소 n개 만들기"를 따로 보여 주고 따로 승인받아 저장한다 | 아무것도 저장되지 않는다 |
| ② 계획 단계 | ①이 끝난 상태를 기준으로 미리보기 → 승인 → `ChangePlan` 1회 | 계획은 그대로다. ①에서 **사용자가 승인해 만든** 장소는 남는다(다시 가져오면 ID로 연결된다) |

- 각 단계는 "전부 저장 또는 전부 안 됨"이고, 사용자가 승인하지 않은 변경은 어느 경우에도 남지 않는다. 새 장소가 없는 파일은 ② 한 번뿐이다.
- 기존 장소와의 **자동 병합은 하지 않는다**. 이름·지역이 같은 기존 장소가 있으면 연결 후보로 보여 준다. 내보내기 파일의 장소 표에는 ID가 들어간다.
- 대안(1차에서는 채택하지 않음): 장소 생성과 계획 변경을 한 트랜잭션으로 묶는 새 저장 명령. 승인이 한 번으로 줄지만 저장 계약을 늘려야 한다. 써 보고 두 번 승인이 불편하면 그때 검토한다.

한계(알고 가는 것): 미리보기 상태는 저장되지 않는다. 도중에 앱을 닫으면 DB는 바뀌지 않고, 같은 파일을 다시 고르면 같은 미리보기가 다시 만들어진다. 변경안(`proposal`) 기록을 남기려면 변경안 스키마에 숙소·이동 연산을 넣어야 하는데, 저장 계약 변경이라 1차에서는 하지 않는다.

### 4.6 AI 요청문 만들기 [제안 — UX 제안 ①⑤⑥ 반영]

| 단추 | 만드는 글 | 단계 |
|---|---|---|
| AI로 계획 만들기 | "(여행지)를 (기간)에 여행한다. (바라는 점). 대화로 계획을 다듬고, 내가 '정리해 줘'라고 하면 아래 양식으로 내 달라" + 양식 안내문 | E1 |
| AI로 수정하기 | "아래는 앱에 저장된 최신 계획이다. 이것을 기준으로 고치고, 바뀐 부분만 같은 형식으로 내 달라" + 내보내기 글(규칙 내장) | E2 |
| AI에게 요청(날짜) | 위와 같되 고른 날짜만. 머리 줄에 `- 범위: 시작 ~ 끝`을 넣어 일부임을 알린다 | E3 |

- 내보내기는 처음부터 **범위(전체·날짜 범위)를 받게** 만든다. E3는 그 위에 단추만 더한다.
- 클립보드 복사가 막히면 글을 펼쳐 보여 주고 직접 복사하게 한다. 파일로 저장하는 길도 둔다.
- 긴 여행(수십 일)은 글이 길어 챗봇 입력 한도를 넘을 수 있다. 복사 전에 글자 수를 보여 주고 날짜 범위를 권한다(한도 값은 E2에서 실측).

### 4.8 계획 준비: 취향 질문 · 목적지 가이드 · 요청서 [제안 — 계획 준비 제안 반영]

목표(제안 원문): AI에게 묻는 방법을 다듬는 것이 아니라, **AI와 대화하기 전에 여행의 큰 그림을 쉽게 정하게** 돕는다. 전부 선택 사항이다(R-11).

**(1) 조건·취향 질문 → 요청서** — 추가 개발이 작다. "AI로 계획 만들기" 화면을 넓힌다.

| 묶음 | 질문(모두 선택, 기본값 없음 = 요청서에 안 들어감) |
|---|---|
| 기본 조건 | 여행지 · 기간 · 동행(혼자/부부·연인/가족/친구) · 인원 |
| 취향 | 중요한 것(복수: 관광·휴식·미식·자연·문화예술·쇼핑·체험) · 속도(여유/보통/알차게) · 방문 경험(처음/재방문) · 이동(도보+대중교통/렌터카/택시/혼합) · 숙소에서 중요한 것(교통/관광지 접근/조용함/가격) · 예산(글) |
| 그 밖 | 꼭 고려할 것·바라는 점(글) |

- 요청서 = 기본 조건 표 + 취향 문장 + (있으면) 고른 가이드 항목 + "AI에게 요청할 작업" 6줄(구도 제안 → 숙소 지역 → 날짜별 일정 → 동선 검토 → 모르는 것은 확정하지 말고 질문 → '정리해 줘'에 양식으로 출력) + 양식 안내문.
- 스타일 프리셋(첫 방문 핵심 관광·여유로운 휴식·미식 중심 등)은 위 질문의 값을 한 번에 채우는 단추로, E3에 둔다.

**(2) 목적지 가이드와 관심 항목** — 값은 크지만 **내용을 어디서 얻느냐**가 관건이다(G-1).

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 목적지별 가이드를 미리 제작 | 품질 관리, 오프라인 | 목적지마다 누군가 써야 한다. 개인용 앱에서 유지가 어렵다 | 1차에서 하지 않음 |
| B. **챗봇이 가이드를 만들고 앱에 붙여넣기** | 새 서버·비용 없음. 계획 가져오기와 같은 방식(요청문 복사 → 붙여넣기). 어떤 목적지든 된다 | 챗봇이 틀릴 수 있다. 사용자가 한 번 더 복사·붙여넣기 한다 | **1차 제안** |
| C. 앱 안 AI(Worker)가 가이드 생성 | 붙여넣기 없음 | 서버·비용·형식 실패가 돌아온다. 기존 AI는 적용을 막아 둔 상태다 | Q-01 3단계와 함께 나중에 |
| D. 내가 쌓은 자료 재사용 | 스페인·프랑스 여행에 가이드·장소 콘텐츠가 이미 있다 | 지금 콘텐츠는 여행 하나에 묶여 있다. 여행 사이 공유는 저장 계약 변경 | 저장 구조 검토 뒤(P2) |

가이드 양식 초안(`travel-app-guide/1`, 계획 양식과 같은 규칙): 머리 줄(목적지·양식·작성 기준일) + 표 하나.

```markdown
# 가이드: 교토
- 양식: travel-app-guide/1
- 기준일: 2026-11-13

## 항목
| 종류 | 이름 | 지역 | 한 줄 설명 | 예상 소요 | 확인 필요 |
|---|---|---|---|---|---|
| 볼거리 | 기요미즈데라 | 히가시야마 | 언덕 위의 큰 절과 전망 | 2시간 | 개장 시간 |
| 코스 | 히가시야마 반나절 | 히가시야마 | 기요미즈데라 → 산넨자카 → 기온 | 반나절 | |
```

- 종류: 볼거리·먹거리·체험·코스·지역(구역 특징). 영업시간·가격 같은 변하는 정보는 넣지 않고 "확인 필요"에 무엇을 확인할지만 적는다(안정적인 정보와 변하는 정보의 분리 — 제안 원문 §6).
- 앱은 가이드를 카드로 보여 주고 항목마다 **꼭 포함 · 관심 · 제외**(기본: 고르지 않음)를 고르게 한다. 요청서에는 고른 것만 들어간다. 고른 항목의 예상 소요 합계를 참고로 보여 주되 가능·불가능을 단정하지 않는다.
- AI가 만든 가이드는 "확인되지 않은 정보"로 표시한다.

**(3) 저장(G-2)** — 1차는 저장 계약을 바꾸지 않는다.

| 대상 | 1차(P1) | 한계 | 뒤(P2) |
|---|---|---|---|
| 기본 여행 프로필(취향 답) | 기기 설정(`localStorage`) | 백업에 들어가지 않고 PC·iPhone 사이에 옮겨지지 않는다 | 저장 계약에 프로필·여행별 설정 추가 검토 |
| 붙여 넣은 가이드와 고른 상태 | 기기 설정에 "계획 준비 초안" 1건 | 같음. 요청서를 복사하면 역할이 끝나는 임시 자료로 본다 | 가이드 항목을 여행 사이에 재사용하는 저장 구조(제안 원문 §7의 Destination·GuideItem·TripSelection) |

제안 원문의 데이터 모델(§7)은 방향으로 받아 두되, **P0·P1로 쓸모가 확인된 뒤** 설계한다. 지금 만들면 저장 계약·백업·이행 검사를 모두 건드리는데, 그만한 값이 있는지 아직 모른다.

## 8. E0에서 실측으로 확인할 것

검토 2차가 답한 v0.2의 질문 4개는 §11에 반영했다. 남은 것은 문서가 아니라 시험으로 정한다.
