# 여행계획앱 벤치마킹: Triple vs Wanderlog

Oct 30, 2026 · @Jason Jeongjae Kim

## 요약

두 앱은 같은 '여행 일정 플래너'지만 사업 구조가 정반대다. 트리플은 예약 커머스(항공·숙소·투어)로 수익을 내는 **플랫폼 내 기능**이고, Wanderlog는 일정·지도 자체를 파는 \*\*독립 SaaS(프리미엄 구독)\*\*다.

- **트리플**: 2017년 출시, 누적 가입자 1,000만(2024.10), 도시 가이드 235개, 장소 데이터 310만 건. AI 일정 추천·동행 협업·가계부·배낭톡(실시간 커뮤니티)이 핵심. **2026-11-03 서비스 종료, NOL 앱으로 통합** — 일정은 이관되지만 배낭톡·여행홈 가이드·저장 내역은 폐기된다.
- **Wanderlog**: Travelchime Inc.(샌프란시스코, YC W19, 시드 약 150만 달러, 소규모 팀). 지도+일정 단일 화면, 실시간 공동 편집, 이메일 예약 자동 수집, 경로 최적화가 핵심. 무료 티어가 넓고 Pro는 연 39.99달러 전후(코호트별 31.99\~59.99달러). 미국 App Store 4.9점, 리뷰 3.4만 건.

travel-app에 주는 시사점은 세 가지다. (1) 일정 객체는 Wanderlog식 **Trip → Day → Stop(장소 참조)** 구조가 DB 전환에 가장 잘 맞는다. (2) 트리플의 종료가 보여주듯 커머스 종속 기능은 플랫폼 사정에 휘둘린다 — SP-FR 가이드북 콘텐츠를 **자체 장소 DB**로 들고 가는 현재 방향이 옳다. (3) 두 앱 모두 '빈 화면에서 시작'이 약점으로 지적된다 — 가이드북 콘텐츠를 \*\*시드 일정(템플릿)\*\*으로 제공하는 것이 차별점이 된다.

## 트리플 (Triple)

트리플은 '나를 아는 여행 앱'을 표방한 **초개인화 여행 플랫폼**으로, 일정 플래너 위에 항공·숙소·투어 예약 커머스를 얹은 구조다. 2026-11-03 독립 앱이 종료되고 놀유니버스의 통합 앱 NOL로 흡수된다.

**회사·규모**

| 항목 | 내용 |
| --- | --- |
| 운영사 | 놀유니버스(구 인터파크트리플, 야놀자 계열). 트리플 법인은 2016년 설립, 2022-08 인터파크에 흡수합병 |
| 출시 | 2017-05 베타, 2017-07 정식 |
| 누적 가입자 | 100만(2018-04) → 500만(2019-09) → 800만(2023-02) → 1,000만(2024-10) |
| 월 사용자 | 약 78만 명(2024-09, 와이즈앱) |
| 데이터 | 도시 가이드 235개, 장소 310만 건, 사용자 생성 일정 700만 건, 리뷰 125만 건(2023-04) |
| 이용자 구성 | 20\~30대가 73.5%(2024-08) |
| 누적 투자 | 약 620억 원(합병 전) |

**핵심 기능**

| 기능 | 동작 방식 |
| --- | --- |
| 일정 생성 | 도시·날짜·여행 스타일(자연/힐링/액티비티/필수관광/먹방) 선택 → 트리플 AI가 일자별 일정 자동 생성. 2023년 GPT 연동으로 일자별 일정 요약 설명 추가 |
| 동선 보기 | 갈 곳을 담으면 지도 위에 동선·일정이 자동 배치. 일정판에 당일 기온·시간별 날씨 표시 |
| 협업 | '일행과 함께 일정 짜기'로 동행 초대, 동시 편집, 일정 링크 공유 |
| 여행 홈 | 일정 등록 시 취향·현재 위치·동선을 분석해 항공·숙소·투어·맛집·관광지를 추천. 추천 사유('내 일정 장소와 함께 많이 가는 곳' 등)를 함께 표시하고 바로 일정에 추가 |
| 가계부 | 동행과 공유하는 경비 정산 |
| 체크리스트 | 준비물·짐 싸기 목록 |
| 배낭톡 | 현지 여행자 간 실시간 채팅(옷차림, 줄서기 현황 등) |
| 도시 가이드 | 235개 도시 가이드 콘텐츠, 오프라인 다운로드 지원 |
| 유틸리티 | 날씨·환율·번역·시차·길찾기 내장, 잠금화면 D-day 위젯 |
| 예약 | 항공·호텔 최저가, 투어·티켓, 셀프 패키지(항공+숙소+투어 조합 구매 시 혜택 증가) |

**수익 모델**: 앱 자체는 무료. 항공·숙소·투어·티켓 예약 수수료와 쿠폰·포인트 기반 커머스가 수익원이다. 일정 플래너는 예약 전환을 위한 유입·체류 장치다.

**강점**

- 한국어·한국인 여행 패턴(오사카·도쿄·후쿠오카·방콕·타이베이)에 최적화된 장소 DB와 리뷰
- 일정 → 추천 → 예약이 한 화면 흐름으로 이어지는 통합 경험
- 310만 장소·125만 리뷰라는 자체 콘텐츠 자산과 가계부·배낭톡 같은 '여행 중' 기능

**약점·리스크**

- 커머스 종속: 플랫폼 통합 결정으로 독립 앱 자체가 사라짐. 배낭톡·가이드·저장 내역은 이관 없이 폐기
- AI 일정 추천은 스타일 선택형이라 자유도가 낮고, 예약 상품 추천과 결합돼 중립성 의심
- NOL 통합 계정 1인 1계정 전환 제한, 블라인드 여행기 이관 제외 등 데이터 이전 마찰

## Wanderlog

Wanderlog는 **지도와 일정을 한 화면에** 두고, 장소를 날짜로 끌어다 놓으면 이동 시간이 자동 계산되는 수동 플래너다. 리뷰어들이 2026년 기준 '가장 완성도 높은 무료 수동 플래너'로 일관되게 평가한다.

**회사·규모**

| 항목 | 내용 |
| --- | --- |
| 운영사 | Travelchime Inc.(샌프란시스코). Y Combinator W19, 시드 약 150만 달러(General Catalyst, Abstract Ventures). 팀 규모 약 5명 |
| 플랫폼 | iOS, Android, 웹(웹이 1급 시민 — 노트북 기획에 적합) |
| 평점 | 미국 App Store 4.9(리뷰 약 34,500건), Google Play 4.7 (2026-07\~10 기준) |
| 수익 | Pro 구독 단일. 웹 공식가 연 39.99달러(정가 49.99), iOS 코호트별 31.99\~59.99달러, 월 5.99\~16.99달러로 A/B 테스트 중 |

**핵심 기능**

- 지도 자동 핀과 이동 시간 표시가 '물리적으로 불가능한 일정'을 막는 실질 기능
- 블로그 언급 집계(Explore)가 단순 평점을 넘는 신뢰 신호

- 대형 일정에서 앱 속도 저하 보고, 기능 과다로 초보자에게 부담
- 가격이 코호트별로 달라 신뢰 이슈

## 기능 비교표

트리플은 '추천→예약', Wanderlog는 '정리→실행'에 강하다. 일정 편집 UX 자체는 Wanderlog가 더 깊고, 콘텐츠(한국어 장소·리뷰)는 트리플이 압도적이다.

| 항목 | 트리플 | Wanderlog |
| --- | --- | --- |
| 일정 생성 시작점 | 도시+날짜+스타일 선택 → AI 자동 생성 | 도시+날짜 → 빈 트립, 검색·가이드·링크로 장소 추가 |
| 일정 편집 | 장소 담기 → 동선 자동 배치 | 장소를 날짜로 드래그, 순서 자유 변경, 구간별 이동 시간 표시 |

## 데이터 모델·UX 패턴 분석

두 앱 모두 공개 스키마는 없지만, 화면 동작에서 역추론되는 일정 구조는 같다: **Trip이 Day를, Day가 순서 있는 Stop을 갖고, Stop은 공유 장소 DB를 참조**한다. 장소 정보를 일정 안에 복사하지 않고 참조하기 때문에, 같은 장소가 여러 일정에 쓰여도 사진·설명·좌표는 한 곳에서 관리된다.

&#91;embedded content: 일정 객체 모델 · 두 앱의 공통 구조를 travel-app 관점으로 정리\]

위 그림의 가운데 줄이 두 앱의 공통 뼈대이고, 좌우의 Collaborator·Expense·Booking·Guide는 각 앱이 그 위에 얹은 확장이다. Guide는 travel-app에서 SP-FR 가이드북 콘텐츠가 들어갈 자리다.

**장소 DB의 차이**

## travel-app 프로젝트 시사점

travel-app의 포지션은 두 앱의 빈자리다: Wanderlog의 **편집 UX**에 트리플이 가진 **편집된 콘텐츠**를 가이드북에서 가져오되, 커머스나 구독 없이 **자체 데이터 소유**로 간다.

**채택할 패턴 (우선순위 순)**

| # | 패턴 | 출처 | 적용 방식 |
| --- | --- | --- | --- |
| 1 | Trip → Day → Stop → Place 참조 모델 | 양쪽 공통 | v2 DB 스키마의 기준. Place는 가이드북 장소 테이블, Stop은 순서·시각·메모만 보유 |
| 2 | 지도+리스트 단일 화면, 양방향 포커스 | Wanderlog | PC 웹 우선 검증 결정과 맞음. 지도 이미지를 DB에 저장하는 현재 결정은 유지하되 Place 좌표는 반드시 숫자 컬럼으로 |
| 3 | 가이드북 챕터 → 시드 일정 템플릿 | 트리플 스타일 선택 + Wanderlog 가이드 붙여넣기 | '빈 화면' 문제의 해법. 챕터를 고르면 Day가 채워진 Trip 생성 — AI 없이 구현 가능 |
| 4 | 구간 이동 시간 표시 | Wanderlog | 외부 API 의존 없이 1차는 직선 거리·도보 환산, 2차에 라우팅 API |
| 5 | 읽기 전용 공유 링크 | 양쪽 공통 | 실시간 협업보다 먼저. 공개 저장소·웹 배포 구조와 비용이 맞음 |
| 6 | PDF·이미지 내보내기 | 트리플 종료 사례 | 데이터 이식성 보험. 가이드북 원본이 PDF였으므로 역방향 내보내기가 자연스러움 |
| 7 | 추천 사유 한 줄 표시 | 트리플 여행홈 | v2 이후 AI 재구현 단계에서 '왜 추천했는지'를 항상 붙이는 규칙으로 |

**피할 것**

- 장소 정보를 일정 안에 복사 저장(트리플 이관에서 드러난 데이터 분리 실패 유형)
- 외부 플랫폼 ID(Google Place ID 등)를 1차 키로 삼기 — 참조 컬럼으로만
- 실시간 동시 편집·오프라인 동기화를 초기 범위에 넣기 — 두 앱 모두 이 기능이 가장 비싼 부분이고, 현재 역할 분담(Claude Code 단독 구현)으로는 과부하
- AI 일정 자동 생성을 핵심 가치로 두기 — Wanderlog 리뷰가 보여주듯 데이터 신선도 문제로 신뢰를 잃기 쉬움. 결정대로 v2 이행 이후

**다음 점검 시 확인할 항목**

- [ ] v2 스키마에 Trip/Day/Stop/Place 4개 테이블과 Stop.order, Stop.place\_id FK가 있는가
- [ ] 가이드북 챕터 → Trip 생성 경로가 작업지시서에 있는가
- [ ] 공유 링크(읽기 전용) 라우트가 계획돼 있는가
- [ ] Place 좌표가 숫자 컬럼으로 저장되는가(지도 이미지와 별개)

**가정(확인 필요)**: 위 우선순위는 travel-app의 1차 사용자가 Jason 본인과 소수 동행이라는 가정 위에 있다. 공개 서비스를 목표로 한다면 협업·오프라인 순위가 올라간다.
