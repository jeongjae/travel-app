## 2. 수정 지시

### R1 · 장거리 이동이 하나인 날 시간 창이 뒤집힌다 (차단: 비용·기능)

`src/ai-v2-context.ts` `deriveDayTimes`는 첫 이동에서 도착, 마지막 이동에서 출발을 얻는다. 이동이 하나면 같은 이동에서 둘 다 얻는다.

재현(13:00 출발 활동 → 16:00 도착 활동, `train`): `arrival 16:00`, `departure 13:00`.

| 제안        | 결과                  |
| ----------- | --------------------- |
| 09:00~10:00 | 거부: 도착 16:00 이전 |
| 14:00~15:00 | 거부: 도착 16:00 이전 |
| 17:00~18:00 | 거부: 출발 13:00 이후 |

시각이 있는 제안은 모두 거부된다. 이동일은 흔하고, 거부되면 작성 호출을 한 번 더 쓴 뒤 실패하므로 **유료 호출이 낭비된다.** 이동 전 오전 활동도 같은 이유로 거부된다.

수정 방향: 그날 첫 활동이 곧 이동 출발일 때만 도착을, 마지막 활동이 곧 이동 도착일 때만 출발을 얻는다. 도착이 출발보다 늦으면 둘 다 비운다. 이 경우들을 시험에 넣는다.

### R2 · 잘못 얻어진 시각을 화면에서 지울 수 없다 (차단: 표시와 전송 불일치)

`entered?.arrival || derived.arrival`이라 입력을 비우면 다시 추정값이 전송된다. 재현: 빈 값 입력 뒤에도 `16:00`, `13:00`이 전송된다. **화면은 비어 있는데 다른 값을 보낸다.** R1의 우회로도 막는다.

수정 방향: 입력이 있으면 빈 값도 "제약 없음"으로 존중하고 시험을 더한다.

### R3 · 작업 결과에 요청 원문·기록이 새로 남는다 (데이터)

`server/ai-v2-jobs.ts:199`가 `planning` 전체를 `job.result`에 넣는다. 그래서 변경 요청 원문, 고른 기록, 활동 요약이 `jobs.json`에 기한 없이 남고, 무인증 list/get 응답으로도 나간다. T-D1 전에는 결과에 원문이 없었으므로 **이번 변경으로 늘어난 보관 범위**이고 설계 §9와 어긋난다. 결과 문서에 적지 못했다.

수정 방향: 브라우저 완성에 필요한 값만 돌려준다(`request`·`records`·요약 제외). 보관 기한은 T-D2 G14.

### R4 · 적용 재시도 때 확인 표시가 다른 항목에 붙을 수 있다 (낮음, 코드 읽기만)

`ProposalReview`의 확인 표시는 항목 번호로 저장된다. `SaveProposal` 성공 뒤 `DecideProposal`이 실패하면 항목이 줄어 번호가 밀리는데 상태는 남는다. 다른 예약 항목이 확인된 것처럼 될 수 있다. 재현은 하지 않았다.

수정 방향: `activityId`로 저장하거나 revision이 바뀌면 초기화한다.

**항목 6 참고**
