## A6 (R5)

- (a) **응답 경로:** `GET /api/ai/v2/jobs/{id}`는 `v2.get` → `toStoredJob(메모리 작업)`을 지난다. 만료가 메모리 작업을 직접 바꾸므로 저장과 응답이 같이 빠진다. **다만** 정리는 시작과 `create()`에서만 돌아 서버가 오래 떠 있고 새 요청이 없으면 24시간 뒤에도 조회 응답에 출력이 남는다. 지시("별도 타이머 금지")대로이며 T-D2 인증 전까지의 노출 창이다. 기록만.
- (b) **만료와 실패 구분:** 코드상 구분이 약하다. 만료된 변경안 대기 작업은 화면에 `실패 · 작성 N회`와 경고 문구 "결과가 만료되어 다시 요청해야 합니다."가 함께 나온다(`src/content/AiPlanner.tsx` 라벨 `failed: '실패'`, `ErrorText`). 문구로는 알 수 있으나 상태 줄이 "실패"라 사용자가 오작동으로 오해할 수 있다. 브라우저에 이미 저장된 변경안은 영향받지 않는다. → **R6 후보(낮음).**
- (c) **화면 표시:** `job.error`를 `ErrorText`가 그대로 출력함을 코드로 확인했다. E2E는 없다.
- (d) **중단 작업 기준 시각:** 재시작으로 `interrupted`가 된 작업은 그 시각을 `updatedAt`으로 기록하고 거기서 24시간을 센다. 완료 시각이 없는 작업의 기준으로 타당하다고 본다.
- (e) **브라우저 적용 결과 시험:** 서버가 브라우저 저장소를 건드리지 않는 구조를 단언할 뿐이며(실제 저장소 통합 시험 아님) 지시서 문구의 최소 충족이다. 서버 코드에 브라우저 저장소 접근이 없어 위험은 낮다. 충분 여부는 Codex 판단.

## 수정 지시 R6 (선택)

만료된 작업은 상태 줄에 "실패"가 아니라 "결과 만료"로 보인다. 서버는 새 필드 없이 기존 `error` 문구로 판별해도 되고(화면이 `error === 결과 만료 문구`로 라벨을 바꾼다), 변경하지 않으면 지금 동작이 문구 안내 수준으로 남는다.
